# 인수 시나리오 — 개정 1

이 문서는 구현할 동작과 관찰 기준이다. **모든 시나리오는 현재 `not_run`이며 S02의 문서 검사와 제품 동작 인수 시험은 다르다.** S03에서 구체 테스트·명령·fixture에 매핑하고 구현 단계별로 실행 결과를 연결한다. 상세 요구는 [인덱스](README.md)에서 찾는다.

## 공통 전제와 검증 책임

- 합성 사례: A는 운영 중인 주문 모듈, B는 신규 정산 모듈, C는 무관한 모듈이다. X는 A/B가 소비하는 공통 데이터 또는 연동 계약이다. 이는 Kit 시험용 사례이며 실제 고객 업무 정책이 아니다.
- 정상·부정·경계 입력을 각 사례 안에서 비교한다. 임의 데이터·사례 수를 채우기 위해 새 제품 요구를 만들지 않는다.
- 구조·참조·개정본·게이트·파일 보존은 자동 행위 검사로 확인한다. 의미적 모순 후보 발견과 화면·문서 이해 가능성은 대표 사례의 AI 수행 결과와 사람 검토를 함께 사용한다.
- 사용자 승인이 필요한 시험은 fixture에 명시적 합성 결정 이벤트를 넣는다. 시험용 승인 레코드를 실제 고객 결정으로 가져오지 않는다.
- 파일 보존은 대상별 내용/해시와 ID·관계 비교로, 범위별 조회는 읽은 본문 목록 계측으로 확인한다. 실행하지 않은 실제 다중 세션·provider·대규모 환경을 통과로 보고하지 않는다.
- 각 ACC의 세 검증 항목은 같은 번호 요구의 AC 1~3에 대응한다. 추가 관찰은 상세 요구 동작의 경계 확인이다.

## ACC-001 — 모듈 주기와 완료 판정

- 연결: AC-001-1~3. 방법: 모듈 생성·현재/과거 상태 조회·부정 게이트 행위 시험.
- A 기준선과 파일을 보존한 상태에서 B를 추가한다. B만 분석을 시작하고 A 운영 결과는 불변이어야 한다.
- A의 다음 변경을 시작한다. 운영 기준선과 활성 변경을 동시에 찾고 같은 모듈의 복수 변경 간 계약 충돌도 구분해야 한다.
- 산출물 없는 빈 모듈을 done으로 선언한다. 완료 근거 부족으로 거부하고 부족한 범위·증거를 알려야 한다.

## ACC-002 — 전체 요구 검토와 범위 변경

- 연결: AC-002-1~3. 방법: 설계 진입 조건과 범위 결정 행위 시험.
- A의 합의 범위에 요구 3건을 두고 1건을 미검토로 남긴다. 설계 진입을 막고 해당 ID를 표시한다. 마지막 검토가 유효해지면 허용한다.
- C에 미완성 요구를 둔다. A의 설계에는 영향이 없어야 한다. 미확정 X를 A가 소비하면 X 때문에 차단되어야 한다.
- 미검토 요구를 단순 제거하거나 보류한다. 범위 변경 결정 없이 통과하지 않아야 한다. 명시적 범위 축소·영향 검토 후에는 새 범위로 판정한다.

## ACC-003 — 적용 항목·초안·미정 구별

- 연결: AC-003-1~3. 방법: 초안 저장/재개와 검토 준비 검사.
- 예외·인수 기준이 비어 있는 요구를 저장·다시 읽는다. 초안은 보존하고 검토 준비에서는 누락 항목을 지적한다.
- 화면 없는 배치 요구와 수량 상한이 중요한 작은 변경을 비교한다. 배치에는 화면 비적용이 가능하지만 수량 경계는 생략할 수 없어야 한다.
- 모르는 값에 근거 없이 해당 없음을 붙이고, 측정 기준 없는 성능 NFR을 완료로 요청한다. 보완 사유를 표시하고 완료로 인정하지 않는다.

## ACC-004 — 의미 정합성과 검토 범위

- 연결: AC-004-1~3. 방법: 합성 결함을 넣은 AI 검토 수행·사람 평가 + 기록 유효성 자동 검사.
- 주문 취소 이후 정산 취소/환불 연결이 없는 두 요구를 제공한다. 검토가 연결 누락을 후보로 설명하고 미결을 해당 요구와 연결하는지 확인한다. 해결 정책은 사용자가 결정한다.
- 범위·개정본·검토 결과 없이 reviewed만 적는다. 유효한 검토가 아니어야 한다. 후보 발견만으로 요구 정책을 자동 수정하지 않아야 한다.
- 무관한 C 요구 추가와 X 규칙 변경을 각각 적용한다. 전자는 기존 검토를 보존하고 후자는 관련 검토의 재확인을 요구한다. 이 사례 성공으로 모든 의미 결함 탐지를 보증하지 않는다.

## ACC-005 — 분석 목록과 추적성

- 연결: AC-005-1~3. 방법: ID/관계 조회·설계 입력 포괄성 검사.
- 한 요구에서 기능·메뉴/화면·데이터 속성·접점 목록을 만들고 각 방향으로 조회한다. 원인 요구와 설계 후보를 찾되 후보를 상세 설계 완료로 표시하지 않는다.
- 근거 없는 업무 화면, 범위가 있는 공통 NFR, 화면 없는 배치를 넣는다. 첫 항목은 보완 대상으로 나오고 나머지 둘은 화면 부재만으로 실패하지 않는다.
- A/B가 X를 참조하고 B의 소비 관계를 변경한다. X 정의는 한 개이며 역조회가 변경을 반영해야 한다.

## ACC-006 — 묶음 검토와 결정 재개

- 연결: AC-006-1~3. 방법: 결정 기록·준비도 검사 + 새 세션 재개 수행 확인.
- 사용자에게 3건을 제시하고 2건 수용·1건 보완을 기록한다. 개별 귀속과 미완료가 유지되어야 한다.
- 승인 근거 없이 상태만 approved로 바꾼다. 유효한 사용자 검토로 인정하지 않는다. 기록 검사일 뿐 실제 신원 인증 시험은 아니다.
- 질문에 답하지 않은 상태를 저장하고 대화 문맥 없이 새 세션에서 재개한다. 미응답·대상 개정본·독립 작업을 찾고 질문을 삭제하거나 전체 승인으로 확대하지 않아야 한다. 실제 계정 전환 미실행 시 그 한계를 별도 표시한다.

## ACC-007 — 과거 사실과 현재 유효성

- 연결: AC-007-1~3. 방법: 개정 전후 게이트 및 정본 불변 비교.
- 승인·구현된 요구의 인수 기준을 바꾼다. 과거 승인·실행 결과는 조회되지만 현재 변경의 설계/개발 진입에는 재검토가 필요해야 한다.
- 같은 입력으로 상태·게이트를 반복 조회한다. 같은 판정이 나오며 정본과 이력이 수정되지 않아야 한다.
- 내용이 같은 파일 이동과 의미가 달라진 '오탈자 수정'을 비교한다. 이동은 ID·연결을 보존하고, 후자는 이름만으로 검토를 면제하지 않아야 한다.

## ACC-008 — 소유 정본과 분할

- 연결: AC-008-1~3. 방법: 소유/참조/분할 조회·중복 검사.
- A/B/공통에 요구·설계·작업·테스트를 분리한다. A의 소유 기록과 소비 공통 계약을 구별해서 찾는다.
- 같은 ID를 다른 소유 파일에 복제한다. 충돌 경로를 보고하고 임의 파일을 정답으로 선택하지 않아야 한다.
- 큰 항목을 의미 단위로 나누고 이동한다. 이전 ID·하위 요소 참조·검토 대상을 유지하거나 실제 의미 변경과 재검토를 명시해야 한다.

## ACC-009 — 인덱스 효율·누락·오류 격리

- 연결: AC-009-1~3. 방법: 본문 읽기 계측·인덱스 재생성·범위/전역 검증 비교.
- 여러 모듈을 만들고 A를 조회한다. 메타데이터 탐색과 본문 읽기를 구분해 A와 실제 의존 본문만 읽는지 확인한다. 대표 규모·읽은 수를 보고한다.
- 새 요구 파일을 추가하되 인덱스를 갱신하지 않고 파일 이동도 수행한다. 누락/이동을 발견하고 갱신하거나 해당 준비 판정을 막아야 한다.
- 무관한 B 본문을 잘못된 JSON으로 만든다. A 상세 조회는 불필요하게 중단되지 않고 전체 검사에서는 B 오류가 나와야 한다. A가 B를 실제 의존하면 미확인 원인을 표시하고 안전한 준비 판정을 보류한다.

## ACC-010 — 저장 충돌과 부분 실패

- 연결: AC-010-1~3. 방법: 두 프로세스의 동일/독립 대상 수정과 중간 실패 주입.
- 동일 개정본을 읽은 두 작업을 순차 저장한다. 뒤 저장에서 충돌을 검출하고 앞 결과를 보존한다.
- 연결된 파일 갱신 도중 실패시킨다. 원복 또는 명시적 재개 상태를 남기고 중간 데이터를 준비 완료로 보고하지 않는다.
- 독립 A/B 저장과 정본 저장 뒤 인덱스 실패·재시도를 수행한다. 유실·중복 승인/이력이 없어야 하고 인덱스를 재생성할 수 있어야 한다. 실제 편집기/AI 동시 실행 범위와 시험 프로세스 범위를 구별한다.

## ACC-011 — 기능 정본과 상세 계약

- 연결: AC-011-1~3. 방법: 기능 개정·참조·개발 준비도 검사.
- 같은 기능을 두 변경 주기에서 수정한다. 기능 ID와 소유 정본은 하나이고 각 주기가 다룬 개정본을 찾을 수 있어야 한다.
- 여러 화면을 가진 기능, 여러 기능을 연결한 화면, 비UI 배치를 작성한다. 적용 상세 규칙·입출력·예외·데이터·테스트 연결을 확인한다.
- 기능 설계에서 원래 요구에 없는 정산 규칙을 추가한다. 요구 검토로 돌려 보내고 미검토 상태에서는 개발 준비가 성립하지 않아야 한다.

## ACC-012 — 화면 명세와 검토 가능한 목업

- 연결: AC-012-1~3. 방법: 실제 목업 렌더·흐름/상태 확인·검토 유효성 검사.
- 대표 입력 화면의 진입·입력·정상 결과·오류 상태를 목업에서 확인하고 해당 입력/결과 개정본에 사용자 검토를 연결한다.
- 제목만 있는 목업, 정상 화면이지만 미검토인 목업, 변경 전 승인만 가진 화면을 비교한다. 모두 해당 부족 이유로 개발 준비를 통과하지 않아야 한다.
- 사용 중인 공통 스타일/컴포넌트가 표현을 바꾸는 경우와 미사용 요소 변경을 비교한다. 관련 검토 영향만 판정한다. 비UI 배치는 화면/목업 비적용 사유로 진행 가능해야 한다.

## ACC-013 — 작업별 준비와 선행 결과

- 연결: AC-013-1~3. 방법: 같은 주기 작업의 개발 게이트 비교.
- 주기 전체 요구 검토를 완료하고 W1만 설계를 준비한다. W1은 개발 가능, 미검토 화면을 가진 W2는 차단되어야 한다.
- W1이 실제 결과를 요구하는 선행 WRK를 blocked로 둔다. 후속을 막아야 한다. 별도 작업은 합의된 계약만 필요하면 상대 구현 완료 전에도 진행할 수 있다.
- 테스트 계획 또는 관련 기능 연결을 누락한다. 보완 대상을 도출해야 한다. 계획은 준비됐지만 아직 코드가 없어 테스트를 실행하지 못한 상태 자체는 개발 진입을 막지 않는다.

## ACC-014 — 전이 영향과 선택적 재개

- 연결: AC-014-1~3. 방법: 관계 그래프·영향 판정·복귀 후 상태/이력 비교.
- X의 속성을 변경한다. X→기능→화면→작업/테스트/문서의 후보 경로와 이유를 찾는다. 실제 영향은 근거를 남겨 확정한다.
- 관련 요구의 의미 변경을 확정한다. 필요한 요구·설계·목업/테스트만 재개하고 C와 과거 운영 기준선·증거는 유지한다.
- 순환 참조, 빠진 의존, 아직 영향 판단하지 않은 후보를 넣는다. 유한하게 탐색하며 오류/불확실성을 표시하고 해당 준비도에서 숨기지 않는다.

## ACC-015 — 현재 게이트와 범위별 출시

- 연결: AC-015-1~3. 방법: 게이트 실행 이력·입력 개정·릴리스 차단 비교.
- 같은 대상에서 passed 뒤 failed를 기록한다. 과거 passed로 통과시키지 않는다. 이후 입력 변경으로 기존 통과도 현재 증거가 아니게 되는지 확인한다.
- A 릴리스에 무관한 B OI/DRQ와 A가 소비하는 X OI를 각각 넣는다. B는 비차단, X는 차단이어야 한다.
- 필요한 게이트를 요청 목록에서 빼거나 다른 범위의 예외를 제출하고 미확인 의존을 추가한다. 누락·부적합을 지적하며 통과하지 않아야 한다.

## ACC-016 — 상태 일치와 재개

- 연결: AC-016-1~3. 방법: 같은 입력의 다중 출력 비교·새 문맥 재개·불변 검사.
- A 운영/B 분석 및 관련 변경 상태를 CLI·브리핑·생성 문서로 확인한다. 판정·차단 대상·원인이 일치해야 한다.
- 대화 내용을 제공하지 않고 인덱스와 기록에서 B의 다음 작업과 미결 질문을 찾는다. 승인받지 않은 다음 단계로 자동 진입하지 않아야 한다.
- 조회 전후 정본 해시를 비교한다. 변경이 없어야 하며 상태 미확인을 완료율 추정·과거 대화 승인으로 대체하지 않아야 한다.

## ACC-017 — 문서 분리·전체 비교·출력 소유

- 연결: AC-017-1~3. 방법: 전체/범위별 생성·파일 목록/내용/링크 비교·독자별 결과 검토.
- 여러 기능·화면·데이터·사용자 절차를 생성한다. 요약 인덱스와 상세 문서가 분리되고 정본/상세 연결 및 적용 오프라인 탐색이 유효해야 한다.
- 정본 추가·삭제·개정 후 이전 출력을 남긴다. 최신 정본의 전체 생성 결과 비교로 누락·낡은 내용·잔여 출력이 검출되어야 한다.
- A만 재생성한다. B 및 사용자 파일은 불변이어야 한다. 제출 대상 개정본·DLP 포함 범위·목업/실제 화면의 증거 구분을 확인한다.

## ACC-018 — 지침·도구·훅 일관성

- 연결: AC-018-1~3. 방법: 전체 파일 인벤토리 대조·구조/격리 검사·대표 provider 수행.
- 공개/관리 스킬과 연결 references, 훅·도구·가이드·템플릿·manifest·생성기를 목록과 대조한다. 누락 없이 유지/수정/교체 판단과 요구 연결을 확인한다.
- 대표 요구 검토→설계→개발→브리핑을 지침대로 수행한다. 같은 정본/준비 조건을 사용하고 어댑터 동기화·구조 검사가 통과해야 한다.
- 특정 훅만 변경한 전후 다른 훅 명령·실행 파일·등록 항목·승인 해시의 불변과 로그 경계를 확인한다. 실제 provider 동작이 환경상 미실행이면 자동 검사 통과와 분리해서 기록한다.

## ACC-019 — 프로젝트 생성과 배포

- 연결: AC-019-1~3. 방법: 실제 임시 신규 프로젝트·추가 모듈·폴더/ZIP export 시험.
- 새 프로젝트를 생성하고 초안 작성부터 대표 흐름을 수행한다. 샘플/기본값을 실제 요구 승인으로 해석하지 않아야 한다.
- A 운영 상태에 B를 추가한다. 기존 A 파일/기준선을 보존하고 B만 분석에서 시작해야 한다.
- 동일 입력으로 폴더/ZIP payload를 비교한다. 관리·fixture·대화 자료는 없어야 하며 같은 출력 대상으로 재생성하면 덮어쓰기를 거부해야 한다.

## ACC-020 — 명시적 채택과 복구

- 연결: AC-020-1~3. 방법: 지원 구형 입력 대조·부분 실패/재적용·원본 불변 검사.
- 구형 done/implemented와 결정·검증 이력이 있는 fixture를 명시적으로 전환한다. ID/참조/이력은 보존하고 새 요구 검토·목업 조건은 근거가 없으면 미완료여야 한다.
- 미지원 확장·충돌·실패·재적용 입력을 준다. 누락 정보를 보고하고 조용한 삭제나 이중 쓰기 정본을 만들지 않아야 한다.
- 전환을 실행하지 않은 경우와 채택 후 되돌림을 비교한다. 원본 보존과 이후 사용자 변경 보호, 채택 범위·한계·후속 검토를 확인한다.

## ACC-021 — 공통 계약과 실제 통합

- 연결: AC-021-1~3. 방법: 기준선 채택·계약/실구현 의존·통합 게이트 시험.
- B가 유효한 공통 기준을 채택한다. 공통 내용을 복제하거나 전체 재승인하지 않고 적용 적합성을 확인해야 한다.
- X 계약에 따라 B 개발과 stub 검증을 마치되 실제 상대 연동은 미실행으로 둔다. 개발 가능과 실제 통합이 필요한 릴리스 차단을 구별해야 한다.
- 공통 또는 외부 계약 개정본을 변경한다. 소비 범위의 준비도를 재판정하고 C·과거 운영 기록을 유지해야 한다.

## E2E-001 — 운영 공존→신규 분석→개발→공통 변경→선택적 재개

- 연결: 전체 001~021 중 단일 흐름의 연결성을 확인한다. 개별 실패·배포·전환 사례는 ACC를 대신하지 않는다.
- 1. 신규 프로젝트를 만들고 합성 A의 운영 기준선·유효한 공통 X를 구성한다. B를 추가해 요구분석을 시작한다. A 결과가 불변인지 확인한다.
- 2. B 요구를 작은 정본으로 작성하고 목록·인덱스를 생성한다. 의도적으로 예외 규칙과 취소/정산 연결을 미완성으로 둔다. 초안 저장은 되고 설계 진입은 차단되어야 한다.
- 3. 개별·관련·전체 흐름 검토와 사용자 결정을 기록한다. 한 항목의 보류를 전체 승인으로 확대하지 않는다. 합의 범위 전체가 준비된 뒤 설계 진입을 허용한다.
- 4. B의 UI/비UI 기능을 상세화하고 UI 화면·목업을 검토한다. 인수 테스트 계획과 선행 계약을 갖춘 작업만 개발한다. 미준비 작업이 다른 작업과 구분되어야 한다.
- 5. 개발/검증 뒤 X 변경을 제안한다. 직접·간접 후보를 분석하고 사용자 결정이 필요한 의미 변경은 요구검토로 돌린다. 실제 이전 배포를 자동 변경하지 않는다.
- 6. 영향받는 기능·화면·목업·테스트를 갱신/재검토하고 실제 통합을 확인한다. 무관한 C의 미결은 B 출시를 막지 않고 X 미결은 막아야 한다. 과거 passed로 현재 failed를 우회하지 않는다.
- 7. 같은 현재 입력에서 상태·문서·인덱스·제출물을 대조한다. 운영/활성 주기와 역사적 증거를 유지하고 새 세션이 인덱스로 다음 작업을 찾아야 한다.
- 관찰 결과: 각 단계의 대상 ID·개정본·판정 사유·필요한 사용자 결정·검증 결과를 기존 변경/테스트 이력에 연결한다. 별도 대화 원문이나 중복 evidence 체계는 만들지 않는다.
