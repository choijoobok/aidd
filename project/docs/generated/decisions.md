## ADR-001 — 구조화된 JSON 레지스트리를 정본으로 사용

- 상태/일자: `승인됨` / 2026-09-17
- 요구사항: REQ-001, REQ-002, REQ-003
- 대체 대상: -

**맥락:** 독립적으로 편집하는 여러 문서를 안정적으로 동기화할 수 없다.

**선택지:** 서술형 문서를 동등한 정본으로 사용; 구조화된 레지스트리와 생성 뷰 사용; 외부 프로젝트 관리 데이터베이스 사용

**결정:** 초기 기반에서는 저장소로 버전 관리하는 JSON 레지스트리와 자동 생성 Markdown 뷰를 사용한다.

**결과:** 참조를 결정적으로 검증할 수 있다; 관리 대상 사실은 구조화된 레코드에서 수정해야 한다; 향후 데이터베이스는 ID와 내보내기 호환성을 보존해야 한다

**롤백·대체 경로:** 안정적인 ID를 유지하면서 JSON 레코드를 대체 저장소로 내보내고 생성기를 변경한다.

## ADR-002 — 생성 문서는 읽기 전용 투영으로 관리

- 상태/일자: `승인됨` / 2026-09-17
- 요구사항: REQ-002, REQ-015
- 대체 대상: -

**맥락:** 파생 문서를 사람이 직접 수정하면 서로 다른 정의가 생긴다.

**선택지:** 양방향 동기화; 수동 조정; 단방향 결정적 생성

**결과:** 생성 파일을 재현할 수 있다; 정교한 사실은 정본 레코드에 모델링해야 한다; 변경 비교가 계속 유용하다

**롤백·대체 경로:** 새 결정을 통해 권위와 조정 규칙을 정의한 경우에만 생성 뷰를 직접 작성하는 산출물로 승격한다.

## ADR-003 — 이식 가능한 스킬 코어와 생성형 AI 어댑터

- 상태/일자: `승인됨` / 2026-09-17
- 요구사항: REQ-013
- 대체 대상: -

**맥락:** Codex와 Claude Code는 프로젝트 스킬 검색 경로가 다르지만 SKILL.md 규약을 공유한다.

**선택지:** 독립적인 스킬 세트 두 개 유지; 심볼릭 링크 사용; 하나의 정본 스킬 트리에서 복사하고 동일성 검증

**결정:** .ai/skills에서 작성하고 두 어댑터 트리를 생성하며 네이티브 훅 설정은 얇게 유지한다.

**결과:** 의미 내용이 동일하다; 동기화를 명시적으로 수행하고 CI에서 검증할 수 있다; 다른 AI가 플랫폼 전용 메타데이터를 무시할 수 있다

**롤백·대체 경로:** 지원하는 모든 플랫폼과 도구가 일관되게 처리할 수 있을 때 복사본을 심볼릭 링크로 대체한다.

## ADR-004 — 역할을 증거 생성 관점으로 취급

- 상태/일자: `승인됨` / 2026-09-17
- 요구사항: REQ-014, REQ-017
- 대체 대상: -

**맥락:** 독립된 AI 역할은 중복되거나 모순되는 문서를 만들 수 있다.

**선택지:** 직무마다 분리된 에이전트 사용; 구분 없는 범용 에이전트 사용; 공유 정본에 조합 가능한 역할 관점 적용

**결정:** 관련 역할 관점을 공유 변경에 적용하고 역할별 정본 대신 명시된 증거를 요구한다.

**결과:** 여러 분야의 고려사항이 명시적으로 남는다; 하나의 AI가 여러 관점을 다룰 수 있다; 고위험 작업에는 여전히 독립 검토를 요구할 수 있다

**롤백·대체 경로:** 같은 정본을 유지하면서 선택한 품질 게이트에 독립 에이전트를 도입한다.

## ADR-005 — 변경 등급에 따라 엄격성 조정

- 상태/일자: `승인됨` / 2026-09-17
- 요구사항: REQ-017, REQ-018
- 대체 대상: -

**맥락:** 일률적인 절차는 작은 수정에 너무 무겁거나 위험한 변경에 너무 약하다.

**선택지:** 모든 변경에 전체 절차 적용; 정책 없이 AI 판단에 위임; 최소 증거가 정의된 네 개의 위험 등급 사용

**결정:** 영향 범위, 불확실성, 민감도와 가역성에 따라 C0~C3 변경 등급을 사용한다.

**결과:** 작은 작업은 빠르게 유지된다; 고위험 작업은 강한 게이트를 거친다; 분류 자체도 감사 가능하다

**롤백·대체 경로:** 전달 지표와 장애를 검토한 뒤 대체 결정으로 등급 기준과 게이트를 조정한다.

## ADR-006 — 기술 스택과 개발 기반을 기능 개발 전에 게이트로 확정

- 상태/일자: `승인됨` / 2026-09-18
- 요구사항: REQ-011, REQ-016, REQ-017
- 대체 대상: -

**맥락:** 기술 선택, UI·개발 표준과 공통 컴포넌트가 기능 개발과 동시에 임의로 결정되면 AI와 사람의 구현이 분산되고 되돌림 비용이 커진다.

**선택지:** 팀별 자율 선택 후 사후 통합; 기술 스택만 선결하고 기반 표준은 기능과 함께 개발; 품질 속성 기반 기술 스택 게이트와 개발 기반 준비도 게이트를 순서대로 적용

**결정:** 분석·설계에서 품질 속성과 제약을 확정한 뒤 TG-001로 기술 기준선을 승인하고, TG-002로 UI·아키텍처·보안·테스트·관측성·배포 공통 기반을 검증한 후 기능 증분을 개발한다.

**결과:** 분산 개발의 일관성과 재사용성이 높아진다; 초기 기반 작업과 증거 비용이 추가된다; UI가 없는 프로젝트는 UI 증거를 적용 대상 아님으로 기록할 수 있다; 현행 기준선 변경은 명시적인 재평가가 필요하다

**롤백·대체 경로:** 게이트가 과도하면 C0~C1 변경의 증거를 축소하는 대체 결정을 작성하되 기술 기준선·보안·테스트·롤백 확인은 유지한다.

## ADR-007 — 단일 방법론 대신 상황 적응형 혼합 통제 사용

- 상태/일자: `승인됨` / 2026-09-18
- 요구사항: REQ-017, REQ-019
- 대체 대상: -

**맥락:** 예측형, 애자일, 시스템공학, DevSecOps, SRE와 AI 주도 방법론은 서로 다른 문제에 강하며 어느 하나도 전체 생애주기의 모든 위험을 충분히 다루지 않는다.

**선택지:** 하나의 표준 방법론을 모든 프로젝트에 적용; 프로젝트마다 통제 없이 자유롭게 선택; 정본·추적성·증거 규칙은 고정하고 상황에 맞는 방법론 통제를 조합

**결정:** 요구 안정성, 불확실성, 규제·안전, 변경 비용, 전달 주기와 운영 책임을 기준으로 방법론 통제를 조합하고 선택 근거를 정본에 기록한다.

**결과:** 프로젝트 맥락에 맞는 절차를 선택할 수 있다; 테일러링 근거를 설명하고 검토해야 한다; AIDD 공통 정본·추적성·고객 결정·증거 게이트는 면제되지 않는다

**롤백·대체 경로:** 반복 지표에서 혼합 경로가 일관성을 해치면 특정 프로젝트 유형에 표준 프로필을 정의하는 대체 결정을 작성한다.

## ADR-008 — 기술 선택 전에 배포·운영 맥락을 게이트로 확인

- 상태/일자: `승인됨` / 2026-09-18
- 요구사항: REQ-020, REQ-021
- 대체 대상: -

**맥락:** DBMS, 인스턴스 토폴로지, 자동 확장, 상태·세션, 가용성·복구와 운영 제약을 늦게 발견하면 단일 서버 가정과 로컬 동기화가 설계에 고착되고 광범위한 재작업이 발생한다.

**선택지:** 기술 스택을 기획 초기에 바로 고정; 상세 설계 때 배포 환경을 확인; 기획·요구분석에서 환경 범주와 품질 제약을 확인하고 TG-001에서 구체 기술을 선택

**결정:** DG-001에서 설계를 바꾸는 배포·운영 조건과 미결사항을 먼저 확정하고, 측정 가능한 품질·동시성 불변 조건을 만든 뒤 TG-001에서 기술 스택과 인프라를 선택한다.

**결과:** 성급한 제품명 고정을 피하면서 구조적 재작업 위험을 줄인다; 고객은 초기 단계에 운영·인프라 질문에 참여해야 한다; 세부 용량 값은 가정과 재평가 조건을 두고 늦출 수 있다; TG-002는 다중 스레드·다중 인스턴스·부하·장애 검증 증거를 요구한다

**롤백·대체 경로:** 저위험 단일 사용자 도구에서는 적용 대상 아님 근거와 재평가 조건을 기록해 질문 깊이를 줄이되 환경 프로필 자체는 유지한다.

## ADR-009 — 모듈별 요구사항 조각과 생성 명세 사용

- 상태/일자: `승인됨` / 2026-09-18
- 요구사항: REQ-001, REQ-002, REQ-003, REQ-009, REQ-024
- 대체 대상: -

**맥락:** 단일 요구사항 파일과 전체 생성 문서가 커지면 특정 모듈의 상태와 명세를 분석하기 위해 관련 없는 내용을 함께 읽어야 한다.

**선택지:** 전역 요구사항 파일과 전체 문서만 유지; 모듈마다 전체 요구사항을 복제; 요구사항을 모듈 정본 조각에 한 번 저장하고 모듈별 뷰를 생성

**결정:** 사용자 요청에 따라 모듈 카탈로그는 전역 인덱스로 유지하고, 각 요구사항은 하나의 `project/.aidd/ssot/modules/MOD-ID.json` 조각에 저장한다. 다중 모듈 영향은 복제 대신 ID 링크로 표현하고, 모듈별 생성 명세를 제공한다.

**결과:** 모듈별 분석은 작은 정본 조각 또는 생성 명세로 제한할 수 있다; 교차 모듈 요구사항도 한 번만 수정한다; 새 모듈은 카탈로그와 빈 조각을 추가한 뒤 독립 상태로 진행할 수 있다; 로더와 검증기는 조각 파일명·소속·중복을 확인해야 한다

**롤백·대체 경로:** 안정적인 ID와 모듈 링크를 유지한 채 조각을 전역 requirements.json으로 병합하고 모듈 문서 생성을 중단한다.

## ADR-010 — 개발 기반 정본과 모듈별 UI 조각을 분리해 생성

- 상태/일자: `승인됨` / 2026-09-18
- 요구사항: REQ-011, REQ-015, REQ-025, REQ-031, REQ-032, REQ-033
- 대체 대상: -

**맥락:** 프로젝트마다 기술 스택은 달라지지만 AI 개발 워크플로, 표준의 분류와 검증, UI 합의와 공통 컴포넌트 관리, 운영·제출 산출물 계약은 일관돼야 한다.

**선택지:** 프로젝트별 Markdown 가이드를 자유 작성; 특정 기술 스택의 규칙을 AIDD 공통에 고정; 기술 독립 메타 정본과 프로젝트·모듈별 조각에서 파생물 생성

**결정:** STD·GPH·EXC, UXB·UIP·CMP, SCR·MAN, RUN·DLP를 구조화된 정본으로 도입한다. 전역 기반과 모듈별 UI 조각을 분리하고 사람이 읽는 표준·목업·매뉴얼·런북·제출 manifest는 결정적으로 생성한다.

**결과:** 새 기술 스택은 같은 메타 구조에 프로젝트 고유 규칙과 검증기를 연결할 수 있다; UI가 없는 모듈은 별도 UI 조각이 필요 없다; 생성기와 검증기의 관리 범위가 넓어진다; 실제 사용자 사이트·ZIP 패키지·화면 캡처 자동화는 후속 실행 자산으로 남는다

**롤백·대체 경로:** 안정 ID와 정본을 내보내 보존하고 기존 guides·deliverables 뷰로 축소한다. 모듈 요구사항 구조와 기존 산출물은 유지한다.
