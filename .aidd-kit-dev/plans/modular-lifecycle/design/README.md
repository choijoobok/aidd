# S03 구조 설계 — 사용자 검토본

- 설계 묶음: `KIT-DBL-018-S03-01`, 개정 1. 현재 승인 상태는 [status.json](../status.json)이 정본이다.
- 입력: 사용자 수용 완료 `KIT-RBL-018-S02-01@1`, APR-003. 요구사항 제출 당시의 25개 파일은 변경하지 않았다.
- 범위: 구조·계약·자산 영향·검증·전환 설계. 여기에 제시한 새 경로와 명령은 **아직 구현되지 않은 목표 계약**이다.
- 구현 전략: 기존 CLI 진입점·기록 ID·유효한 동작을 보존하고 내부 저장/판정을 점진 교체한다. 새 서비스·DB·프레임워크·플러그인·런타임 훅은 추가하지 않는다.

## 설계 결론

1. 개발 주기는 기존 `CHG`를 사용한다. 모듈은 업무 소유 경계, `WRK`는 기능/화면별 작업이다. 프로젝트 전체 단일 단계와 모듈 `done` 문자열은 진입 근거에서 제외한다.
2. 현재 정본은 모듈/공통 소유의 레코드 파일 하나로 둔다. `FEAT`를 지속되는 기능 상세 명세로 승격하고 업무 데이터 `DAT`·메뉴 `NAV`도 명시적으로 식별한다.
3. 요구·설계·검토는 개정본에 연결한다. `RVW`는 검토 결과, `BSL`은 고정한 범위/입력 묶음, `IMP`는 변경 영향 판정이다. 과거 승인·운영 버전은 현재 편집본과 별도로 복원 가능하다.
4. 인덱스는 재생성 가능한 탐색 자료다. 일반 조회는 필요한 본문만 읽고, 엄격한 진입 검사는 해당 범위의 실제 내용을 확인한다. 전역 오류와 부분 조회 결과를 구분한다.
5. 설계 진입은 합의한 주기 전체 요구의 준비도, 개발 진입은 해당 작업의 명세·목업·선행 결과, 릴리스는 현재 대상의 실제 검증 증거로 각각 계산한다.
6. 영향 분석은 관계별 경로를 따라 후보를 찾고 의미 판정을 거친다. 관련 항목만 앞 단계로 돌아가며 운영 배포를 자동 변경하지 않는다.

## 용어 경계

- 주기: 합의한 변경 범위를 분석부터 검증/전달까지 수행하는 `CHG`. 별도 일정/스프린트 시스템이 아니다.
- 정의: 무엇을 해야 하는지에 관한 현재 계약. 구현·실행 결과와 구분한다.
- 유효성: 특정 검토/실행 결과를 현재 내용과 의존 입력에도 적용할 수 있는지에 대한 계산 결과.
- 기준선: `BSL`이 고정한 ID·내용·적용 입력의 묶음. 해시만으로 업무 의미의 동등성을 보증하지 않는다.
- 모듈 공통: 한 모듈 내부 여러 기능의 공통 항목은 그 모듈 소유다. 여러 모듈이 소비하는 항목도 소유 모듈이 명확하면 그대로 참조하며, 반드시 project 공통으로 옮기지 않는다.

새 접두사는 AIDD 공통 모델 변경 제안이다. 제품 프로젝트 용어를 임의 생성하지 않으며, 구현 시 공통 용어 manifest·정책·워크시트·가이드를 함께 갱신한다.

## 기존 ID·이력 보존의 정확한 대상

새 FEAT JSON 정본은 새 ID를 부여한다. 구형에는 FEAT 정본이 없으므로 보존할 기존 FEAT ID도 없다. '기존 ID·이력 보존'은 이미 수행 중인 **제품 프로젝트가 새 형식을 명시적으로 채택할 때** REQ/SCR/TC/CHG/HIS/EVD 등의 연결과 역사적 사실을 유지한다는 뜻이다. 구형·신형 정본을 두 벌로 계속 운영한다는 뜻이 아니다. 신규 프로젝트에는 이전 데이터가 없고 새 구조로 시작한다. 현재 kit-source에는 실제 제품 정본이 없으며 fixture는 회귀 입력일 뿐이다. KIT-CHG/KIT-ADR 관리 기록 보존은 이 제품 전환과 별개의 책임이다.
