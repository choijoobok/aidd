# AIDD 프로젝트 운영 청사진

## 목적

AIDD는 제품 의도에서 구현·검증·출시·운영까지의 실행 산출물을 안정 ID로 연결한다. 팀의 인력과 역할을 관리하는 도구가 아니라, 무엇을 왜 만들고 어떻게 검증했는지를 재현할 수 있게 하는 개발 계약이다.

## 경계

프로젝트의 인력 구성, 역할, PM 위임, 일정, 작업 배정, 휴가, 승인 권한과 계정 관리는 회의나 별도 프로젝트 관리 도구에서 다룬다. AIDD는 이 데이터를 정본으로 요구하거나 개발·릴리스 조건으로 검사하지 않는다. 보안 또는 신원 검증이 제품 요구사항이면 그때 별도 설계·테스트 범위로 다룬다.

## 실행 구조

1. `REQ`와 `OUT`으로 의도와 검증 가능한 결과를 정의한다.
2. `MOD`, `SURF`, `ADR`로 시스템 경계와 되돌리기 어려운 선택을 설명한다.
3. `CHG`와 `WRK`로 작은 실행 범위와 필요한 설계·구현·테스트·문서·마이그레이션·운영 영역을 묶는다.
4. `TC`, `EVD`, `GTR`로 실행 결과와 품질 판단을 기록한다.
5. `REL`, `DLP`, 운영 런북으로 전달과 운영 준비를 확인한다.

WRK는 담당자나 일정 배정을 강제하지 않는다. 누가 수행할지는 프로젝트 운영에서 정하고, AIDD는 무엇이 완료되어야 하는지와 어떤 증거가 필요한지를 추적한다.

## 결정 기억

현재 정본에는 현재 상태와 핵심 근거를 둔다. 의미 있는 분석·설계·용어·소스·범위·상태 결정은 월별 `HIS` 파일에 append-only로 기록한다. 각 이력은 대상 안정 ID, 결정 주체, 결정, 이유, 이전 상태, 영향과 출처를 가진다. 장기 설계는 ADR, 실행 범위는 CHG, 용어는 TCH로 더 풍부하게 표현하고 HIS가 이들을 연결한다.

이 구조는 현재 상태를 읽기 쉽게 유지하면서도 시간이 지난 뒤 “왜 이렇게 했는가”와 변경 영향 범위를 복원하게 한다. Git은 정확한 코드 차이를, HIS는 의사결정 맥락을 담당한다.

## 자동화 원칙

- 구조 검증은 참조 무결성, 상태, 증거와 생성 문서 일치를 확인한다.
- 검증 통과는 사람의 권한 승인을 뜻하지 않는다.
- provider 훅은 대화 원문 보존과 빠른 진단을 담당하며 팀 운영 절차를 강제하지 않는다.
- Codex와 Claude는 같은 공통 스킬 정본을 사용하고 행동 동등성은 공통 시나리오와 증거로 검토한다.
- 저장소 보호 설정과 원격 활성화 증거는 구분한다.
