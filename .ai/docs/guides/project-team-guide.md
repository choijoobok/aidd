# AIDD 프로젝트 수행팀 가이드

이 문서는 AIDD Kit으로 생성한 프로젝트를 시작하고 완료할 때까지 사용하는 프로젝트 팀용 진입점이다. AIDD는 프로젝트 실행과 산출물에 집중한다. 팀 구성, 역할, PM 위임, 작업 배정과 일정은 회의나 별도 프로젝트 관리 도구에서 운영한다.

## 무엇을 먼저 읽어야 하나

시스템 개요와 사용자 역할을 정한 뒤, 요구사항을 확정하기 전에 [접속·인증·접근 정책](../../spec/system-access.md)을 결정한다. 로그인 자체가 필수인 것이 아니라 공개/인증 범위·초기 화면·권한 확인·거부 동작의 결정과 사용자 검토가 필수다.

## 전체 흐름

1. 배포받은 `kit-template`에서 Git과 훅을 준비하고 `project-bootstrap`으로 제품 정본을 만든다.
2. 시스템 개요·목적·범위 → 핵심 업무 → 업무 사용자/역할 → 유즈케이스 ↔ 프로세스를 정리한 뒤 요구사항을 도출한다. v2에서는 [모듈형 정본 작업 안내](owned-records-workflow.md)의 선행 분석·사용자 검토·연결 누락 검사를 적용한다. 요구 초안은 병행 작성할 수 있다.
3. 모듈·배포 맥락·아키텍처·기술 기준선·UI와 운영 조건을 필요한 깊이만큼 결정한다.
4. `CHG`와 `WRK`로 작은 실행 단위를 만들고 요구·설계·코드·테스트·문서를 같은 증분에서 갱신한다.
5. 의미 있는 결정은 관련 안정 ID와 함께 `HIS`에 기록한다. 장기 설계는 `ADR`, 용어 변경은 `TCH`도 사용한다.
6. 영향 범위의 생성·검증·테스트를 실행하고 게이트와 미결 위험을 확인한다.
7. 병합 후 영향을 재확인하고 `release-check`가 준비된 경우에만 출시 준비 완료로 표시한다.

## 사람과 AI의 경계

- 프로젝트 책임자는 제품 의도, 우선순위, 위험 수용과 되돌리기 어려운 결정을 프로젝트가 정한 방식으로 결정한다.
- 프로젝트 운영자는 인력, 역할, 일정, 배정과 의사결정 절차를 AIDD 밖에서 관리한다.
- AI는 질문, 대안 비교, 구현, 검증과 기록을 돕지만 결정이나 실제 실행 결과를 꾸며내지 않는다.
- `decided_by`, `performed_by` 같은 필드는 추적용 자유문자이며 인증·권한 부여 수단이 아니다.

## 매 세션의 최소 시작

```powershell
node .ai/tools/aidd_hook.mjs self-test --hook
node .ai/tools/aidd.mjs status --level executive
node .ai/tools/aidd.mjs integration-status
```

명령의 옵션·필수 입력·예시는 `node .ai/tools/aidd.mjs --help`와 `node .ai/tools/aidd.mjs <명령> --help`로 확인한다. 도움말은 현재 작업공간(역할·정본 형식)에서 쓸 수 있는 명령만 사용 가능으로 표시하고, 알 수 없는 명령이나 지금 쓸 수 없는 명령은 실행하지 않고 오류로 끝난다.

## 중요한 결정을 남기는 예

```powershell
node .ai/tools/aidd.mjs record-history `
  --id HIS-20260921-001 `
  --occurred-at 2026-09-21T12:00:00.000Z `
  --type design `
  --subject REQ-001 --subject ADR-001 `
  --change CHG-001 `
  --decided-by "프로젝트팀 오프라인 협의" `
  --decision "현재 정본과 별도 결정 이력을 함께 유지한다" `
  --reason "장기 영향 분석에서 과거 선택의 이유를 복원하기 위해서다"
```

오탈자나 서식 정리는 기록하지 않는다. 제품 동작, 범위, 설계, 용어, 운영 방식 또는 검증 해석이 바뀌는 경우에 기록한다.

## 일상 수행 원칙

- 대화에서 확인한 사실은 정본에, 미확정 내용은 가정 또는 미결사항에 기록한다.
- 결정이 필요하면 먼저 영향 소유자의 OI에 질문·상태·차단 여부를 기록하고 REQ·ADR·CHG·GTR·REL 등 실제 대상 정본을 링크한다. 사용자에게 실제로 제시할 질문은 보내기 전에 소유자별 `DRQ/<ID>.json`로 저장한다.
- 상태 브리핑에서는 OI와 실제 답변 대기 DRQ의 건수·묶음 수를 구분하고, 기록된 다음 작업을 설명한 뒤 차단·우선순위·대기 시각 기준의 권장 질문 묶음을 마지막에 표시한다.
- 사용자가 답하지 않고 독립적인 다른 작업을 요청하면 기존 OI와 DRQ는 유지하고 해당 작업을 진행한다. 새 결정이 필요하면 새 OI·대상 링크와 DRQ 묶음을 추가하며 기존 질문을 덮어쓰지 않는다.
- 현재 정본에는 현재 상태와 핵심 근거를 두고 상세 결정 이력은 소유자별 `HIS/<ID>.json`에 누적한다.
- `project/docs/generated/`는 직접 수정하지 않는다.
- 코드나 정본을 바꾼 뒤 `document-impact`, `generate`, `validate`와 영향받은 테스트를 수행한다.
- 보안·권한·신원 검사는 프로젝트 요건이나 사용자의 명시 요청이 있을 때만 별도 품질 범위로 다룬다.

## 문서 체계

- `.ai/spec/`: AIDD 행동 명세
- `.ai/docs/guides/`: 프로젝트 수행 가이드
- `.ai/docs/methodology/`: 산출물 모델과 방법론 설명
- `.ai/skills/`: AI 수행 절차
- `project/.aidd/ssot/`: 현재 제품 정본과 공통·모듈별 `HIS/` 결정 이력
- `project/docs/generated/`: 정본에서 재생성하는 문서
- `project/src/`: 제품 소스와 테스트
- `chat-history/`: Git에 넣지 않는 로컬 대화 원문
새 프로젝트는 [모듈형 정본 작업 안내](owned-records-workflow.md)를 따른다. v2 경로·명령은 기존 전역 배열 예제보다 우선하며, 마이그레이션 없이 두 형식을 혼합하지 않는다.
