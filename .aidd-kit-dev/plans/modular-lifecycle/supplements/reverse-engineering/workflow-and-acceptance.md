# 수행 흐름과 인수 계획

이 문서는 구현 전 시험 계획이다. 실제 프로젝트나 자동 변환 결과가 아니다.

## 사용자가 경험할 흐름

1. 소스·문서 위치와 도입할 모듈/업무 범위를 선택한다. 원본은 그대로 둔다.
2. 자료 목록·관측 근거와 처리하지 못한 부분을 만든다. 분석 기준을 고정한다.
3. 구조화 관측과 AI 분석에서 정본 초안을 작성한다. 항목별 근거·미정·모순과 연결을 생성한다.
4. 프로젝트를 처음 정의하듯 앞단부터 설명·검토한다. 근거가 명확한 항목은 빠르게 수용하고 불확실성이 큰 항목부터 질문한다.
5. 사용자 답변을 정본과 현재 검토에 반영한다. 목표 변경과 현행 차이를 별도 작업으로 연결한다.
6. 선택 범위의 구조/출처/검토·동작 검증 현황을 확인하고 모듈별로 정본을 채택한다.
7. 이후 소스/문서 변경은 차이와 영향을 재분석하고 필요한 항목만 보완한다. 신규 개발은 일반 AIDD 절차로 이어간다.

분석은 소스의 상세에서 상위 업무로 역추적하지만 검토는 시스템 목적부터 상세로 내려간다. 이 두 방향을 구분해야 구현 세부가 곧 요구사항이라는 오류를 피할 수 있다.

문서/자료 수집 자체의 인수와 기술 스택별 파서 품질·실제 실행 검증을 구분한다. fixture 통과를 특정 고객 시스템 도입 성공으로 표현하지 않는다. 첫 단계에서 실제 대상 스택을 지정받지 않으면 일반화된 텍스트/구조화 관측 회귀만으로 범위를 명시한다.

## 현재 발견된 구현 간극

- 기존 legacy 스킬은 SURF/LDP·문서화 작업 중심이며 SYS부터 요구/설계까지의 자동 초안 계약은 없다.
- typed 정본 외피와 사용자 검토는 있으나 항목별 관측 근거·초안 매핑·재분석 충돌의 명시적 계약이 필요하다.
- 현재 stagedDocumentation은 project/src로 대상을 제한한다. 선언한 레거시 루트의 읽기 범위·매핑·영향 검사로 확장해야 한다.
- 운영/실제 증거 규칙은 이미 있으므로 새 기능이 이를 우회하거나 과거 승인·테스트를 만드는지 부정 시험이 필요하다.

사용자 검토 시간이나 자동 작성 비율의 수치는 실제 자료 없이 약속하지 않는다. 근거로 채운 항목, 확인 질문 수, 재검토 범위와 처리하지 못한 부분으로 효율을 확인한다.
