# 수행 생명주기

AIDD는 정해진 단계 문서를 모두 채우는 방식이 아니라, 제품 의도에서 운영까지 연결이 끊기지 않도록 작은 변경을 반복하는 방식이다. 변경 크기와 위험에 맞춰 필요한 기록과 검증을 선택한다.

## 1. 의도와 성과

기능 목록보다 먼저 해결할 문제, 대상 사용자, 기대 결과와 하지 않을 범위를 합의한다. 확인되지 않은 내용은 사실처럼 채우지 않고 가정이나 `OI`로 남긴다.

> 사용자가 겪는 문제와 기대 성과를 인터뷰해줘. 확정 사실, 가정, 미결사항을 나누고 중요한 선택은 대안·장단점·가역성과 함께 제시해줘. 아직 구현하지 마.

제품 의도와 성과 기준이 합의되면 `BEN-TRIAGE`로 벤치마킹 필요성을 판단한다. 필요할 때만 조사 질문, 비교 대상, 평가 기준, 출처 품질과 제외 범위를 합의하고 조사한다. 필요 없으면 이유와 다시 판단할 조건을 남긴다.

## 2. 요구사항과 범위

성과를 검증 가능한 제품 요구사항 `REQ`로 구체화하고 품질 수준·제약은 `NFR`로 구분하며, 범위를 모듈 `MOD`와 구현 표면 `SURF`로 나눈다. 화면, API, 배치, 이벤트, 외부 연동, 데이터와 마이그레이션을 빠뜨리지 않되 아직 선택하지 않은 기술을 요구사항에 숨기지 않는다.

이후 개발 단계에서는 요구사항이라는 이름을 다시 쓰지 않는다. 기능 단위의 흐름·업무 규칙·예외·검증은 `기능 상세 명세`로 구체화하고, 화면의 상태·정보·행동·오류·접근성 계약은 `화면 명세(SCR)`로 기록한다. 기능 상세 명세는 기존 `REQ/UC/MOD/CHG/SCR/TC`를 연결하며 별도 `FEAT` 정본을 만들지 않는다.

AI는 분석 중 반복될 새 업무 명사나 사람마다 다르게 해석할 표현을 발견하면 기존 용어집을 먼저 확인한다. 요구사항이나 인수 기준이 정의에 따라 달라질 때만 읽기 전용 용어 확인 카드를 만든다. 프로젝트가 회의나 자체 절차로 결정하면 `decided-by`에 결정 주체를 자유문자로 기록하고 용어집과 관련 요구사항을 함께 현행화한다.

- 요구사항에는 사용자 가치와 인수 기준을 둔다.
- 범위 밖 항목과 의존성을 명시한다.
- 미결 결정은 단계와 무관하게 판단 조건·필요 시점·영향 범위를 가진 프로젝트 전체 공통 `OI`로 먼저 기록하고 관련 `REQ`, `ADR`, `CHG`, `GTR`, `REL` 등의 상태·결정 조건·영향에 연결한다.
- 사용자에게 실제 결정을 요청할 때는 먼저 `DRQ`를 작업 보드에 저장하고 열린 OI와 실제 대상을 연결한다. 한 번에 같은 결정을 위한 1~3건으로 묶되 여러 시점의 미응답 묶음을 함께 보존할 수 있다.
- 사용자가 답하지 않은 채 독립적인 다른 작업을 요청하면 기존 OI와 DRQ를 유지하고 그 작업을 수행한다. 새 결정이 필요하면 새 OI·대상 링크와 DRQ 묶음을 추가하며, 현재 작업이 기존 결정에 의존하거나 게이트를 넘으려 할 때 관련 질문을 다시 제시한다.
- 기존 시스템은 현재 소스와 문서를 조사하되 어느 한쪽을 자동으로 정답으로 취급하지 않는다.

> 합의한 성과를 검증 가능한 요구사항과 범위 밖 항목으로 정리해줘. 화면·API·배치·이벤트·외부 연동·데이터·마이그레이션 중 적용되는 표면을 확인하고, 모르는 내용은 OI로 남겨줘.

## 3. 배포 맥락과 아키텍처

사용자 수, 데이터 민감도, 가용성, 지연, 복구, 운영 조직과 배포 제약을 먼저 확인한다. 그 뒤 선택지가 실제로 달라지는 항목만 ADR로 결정한다.

아키텍처는 모듈 경계, 인터페이스, 데이터 소유권, 장애 격리와 운영 책임을 다룬다. 기술 스택은 결정된 요구와 배포 맥락을 충족하는지 비교한다. 고객이 요구하지 않은 규제, 보안 등급이나 기술을 새 요구사항으로 만들지 않는다.

설계에서 새 제품·기술 개념이나 비슷한 이름의 다른 경계가 나타나면 AI가 기존 용어와 충돌·영향을 확인한다. 명확화가 필요하면 프로젝트의 오프라인 결정 뒤 용어집, 설계 정본, API·데이터·화면·소스 명명을 같은 흐름에서 갱신한다.

> 현재 요구와 운영 조건에 영향을 주는 아키텍처 선택만 찾아줘. 대안, 장단점, 가역성, 마이그레이션과 롤백을 비교하고 내 결정 전에는 ADR을 확정하지 마.

## 4. 개발 기반과 사용자 경험

기술 기준선 `TSB`, 개발 표준 `STD`, 골든 패스 `GPH`는 해당 프로젝트의 선택에 맞게 작성한다. 화면이 있으면 사용자 여정과 `SCR`, 공통 UI 기준선, 접근성·반응형 조건을 정한다. 설계용 HTML 목업은 의사결정 자료이지 구현 완료 증거가 아니다.

모든 분야를 처음부터 완성할 필요는 없다. 첫 구현 조각에 필요한 계약과 되돌리기 어려운 선택을 먼저 확정하고 나머지는 다음 증분으로 남긴다.

## 5. 변경과 작업 계획

변경은 `CHG`, 실행 단위는 `WRK`로 관리한다. 작업에는 연결 요구사항, 영향 모듈, 설계·코드·테스트·문서·운영 영향과 완료 기준을 둔다. 담당자와 일정은 프로젝트 운영에서 정한다.

구현 전에 다음을 확인한다.

- 해결할 실패 또는 원하는 결과가 명확한가
- 적용 요구사항과 인수 기준이 연결되었는가
- 필요한 결정과 미결사항이 분리되었는가
- 호환성, 마이그레이션과 롤백이 필요한가
- 검증 방법이 변경 위험에 비례하는가

기능 규모 변경은 필요한 `development-check`가 통과한 뒤 시작한다.

> 이 변경을 검토 가능한 작은 작업으로 나누고 요구사항·모듈·문서·테스트·운영 영향을 연결해줘. 구현 전에 남은 결정과 development-check 차단 항목을 먼저 보여줘.

```powershell
node .ai/tools/aidd.mjs development-check --change CHG-001
```

## 6. 작은 증분 구현

하나의 증분에서 관련 정본, 구현, 테스트, 사용자·운영 문서를 함께 갱신한다. 거대한 일괄 구현보다 실제로 확인할 수 있는 수직 조각을 선호한다.

> 범위가 결정된 첫 수직 조각만 구현해줘. 기존 동작을 보존하고, 바뀐 정본·코드·테스트·문서를 함께 갱신한 뒤 변경 영역 검사와 파생 문서 비교 결과를 보고해줘.

```powershell
node .ai/tools/aidd.mjs document-impact --path project/.aidd/ssot/requirements.json
node .ai/tools/aidd.mjs generate
node .ai/tools/aidd.mjs validate
```

테스트는 변경된 계약과 실패 가능성을 확인하는 가장 작은 관련 집합을 실행한다. 전체 테스트, 전체 fixture, 보안·권한 검토는 정본 또는 변경 범위가 요구할 때만 추가한다.

## 7. 검토, 병합과 출시

검토자는 요구사항과 구현, 테스트 결과, 생성 문서와 잔여 위험의 연결을 본다. 병합 뒤에는 두 부모와 결과 사이에서 계약·정본·테스트가 달라졌는지 평가하고 필요한 `MRC`만 만든다.

출시 전에는 필수 게이트, 미결 위험, 운영·사용자 문서, 롤백과 배포 프로필을 확인한다.

> 이 변경의 요구사항 충족, 테스트, 생성 문서와 잔여 위험을 검토해줘. 병합 영향과 출시 차단 항목을 분리하고 확인되지 않은 내용은 통과로 간주하지 마.

```powershell
node .ai/tools/aidd.mjs release-check --release REL-001
```

명령이 준비 상태를 확인했다고 해서 실제 배포가 자동 수행되지는 않는다. 배포와 외부 시스템 변경은 프로젝트의 권한·승인 절차를 따른다.

## 8. 운영과 개선

운영 중 장애, 관측 결과와 사용자 피드백을 해당 `REQ`, `CHG`, `RUN`, 위험과 연결한다. 이전 결정을 삭제하지 않고 새 ADR로 대체 관계와 영향, 롤백을 남긴다. 다른 Kit나 프로젝트의 개선은 자동 병합하지 않고 현재 환경의 별도 변경으로 평가·수용한다.

> 운영에서 발견한 문제와 사용자 피드백을 기존 요구·릴리스·런북에 연결해줘. 긴급하다는 이유로 범위를 넓히지 말고, 가장 작은 안전 변경과 롤백을 제안해줘.

## 첫 주의 현실적인 목표

1. 해결할 문제와 성공 기준 하나
2. 첫 사용자 여정과 범위 밖 항목
3. 아직 모르는 운영 조건과 확인할 사람
4. 첫 모듈과 가장 작은 수직 구현 조각
5. 해당 조각의 인수 기준과 검증 방법

매일 “확정된 것, 아직 모르는 것, 오늘 확인할 가장 작은 다음 조각”을 갱신하면 된다.

## 상태 확인과 결정 재개

“현재 상태를 브리핑해줘”라고 요청하면 AI는 정본 검증 결과, 단계와 진행 상태, 차단사항·위험, OI와 DRQ를 구분한 개수와 답변 대기 묶음 수, 기록된 다음 작업과 권장 흐름을 설명한다. 마지막에는 차단·우선순위·대기 시각으로 고른 `awaiting_decision` 질문 묶음을 보여주되 상태 확인만 요청했다면 즉답을 강요하지 않는다. 상세 현황에서는 나머지 미응답 묶음도 확인할 수 있다.
