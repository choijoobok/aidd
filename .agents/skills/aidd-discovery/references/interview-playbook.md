# 인터뷰와 반대 검토 지침

역할을 정한 직후 `.ai/spec/system-access.md`의 접속 정책을 먼저 확인한다. “접속하면 누구에게 어떤 화면이 보이나 → 로그인 없이 가능한 일은 무엇인가 → 인증이 필요한 일과 인증 후 복귀 위치는 어디인가 → 같은 로그인 사용자라도 역할·조직·소유 데이터에 따라 무엇이 달라지나 → 누가 언제 무엇으로 권한을 확인하고 회수하나 → 직접 URL/API 호출·권한 부족·만료 시 어떻게 되나”를 의미 있는 묶음으로 묻는다. 초기 화면의 목적/전이 정책과 상세 UI 설계는 구분한다. 공통 정책은 재사용하고 모듈 차이만 분리한다. 사용자 결정 전 기본 로그인·권한 모델을 임의로 확정하지 않는다.

v2 착수 인터뷰는 `.ai/spec/business-discovery.md`의 SYS/CAP/ACT/UC/BPR로 업무 이해를 먼저 정리한다. “이 시스템이 무슨 일을 하나 → 누가 어떤 목표로 쓰나 → 한 업무가 어떻게 시작·종료되나 → 사람/시스템/외부의 인계와 실패가 무엇인가 → 지켜야 할 요구가 무엇인가” 순서로 질문한다. 사용자 검토는 목적·역할, 시나리오·흐름, 요구·분석 목록의 의미 있는 묶음으로 제시하고, 답변별 수용 범위는 개별 정본에 기록한다. 이미 검토된 공통 정의를 신규 모듈마다 다시 작성하게 하지 않는다.

목적에서 동작, 제약, 예외 순서로 진행한다. 먼저 확인된 모든 미결 결정을 영향 소유자의 OI에 기록하고 실제 대상 정본을 링크한다. 그중 가장 큰 설계 분기나 되돌리기 어려운 결정을 골라 한 배치에 같은 결정을 위한 1~3개의 질문만 두고, 질문 전에 `aidd-decision-management`에 따라 DRQ를 저장한다. 각 질문에는 답이 바꾸는 범위, 미응답 시 영향과 가능한 기본값을 짧게 밝힌다. 사용자가 답하지 않고 독립적인 작업을 요청하면 기존 OI와 DRQ를 보존하며, 새 작업에 별도 결정이 필요하면 새 OI와 묶음을 추가한다. 낮은 비용으로 되돌릴 수 있는 세부사항은 가정과 재검토 조건을 기록해 뒤로 미룬다. 유용한 질문은 다음과 같다.

- 어떤 결정이나 행동이 더 쉽고, 빠르고, 안전해지거나 새로 가능해져야 하는가?
- 누가 문제를 겪으며, 해결할 가치가 있다는 증거는 무엇인가?
- 어떤 측정 가능한 성과가 중요하며, 무엇을 실패로 볼 것인가?
- 무엇이 그대로 유지되어야 하는가? 명시적인 제외 범위는 무엇인가?
- 가장 작은 유용한 범위는 무엇이며, 어떤 미래 선택 가능성을 보존해야 하는가?
- 거짓으로 드러날 경우 설계를 무효화하는 가정은 무엇인가?
- 악의적이거나 급하거나 오프라인이거나 권한이 없거나 실수한 사용자가 어떻게 시스템을 깨뜨릴 수 있는가?
- 시간 초과, 재시도, 중복 입력, 부분 쓰기, 롤백 또는 의존 시스템 장애 시 어떤 일이 일어나는가?
- 실제 배포 대상은 온프레미스·클라우드·하이브리드 중 무엇이며, VM·컨테이너·Kubernetes·서버리스·기존 WAS 제약이 있는가?
- DBMS와 버전·운영 방식이 정해졌는가? 단일·복제·클러스터·샤딩과 읽기 지연 중 무엇을 예상하는가?
- 단일·대기·다중 활성 인스턴스 중 무엇이 필요한가? 자동 확장과 인스턴스 교체 시 유지할 상태가 있는가?
- 평균·최대 부하, 동시 사용자, 데이터 크기·증가율, 응답시간·처리량 목표와 배치 시간창은 무엇인가?
- 가용성 SLO와 RTO·RPO는 무엇이며, 무중단 배포·복원 연습·부분 장애 저하 동작이 필요한가?
- 세션·캐시·파일·락·스케줄을 인스턴스 로컬에 둘 수 있는가? 여러 서버에서 같은 업무 자원을 동시에 바꿔도 지킬 불변 조건은 무엇인가?

최종 인스턴스 수, 풀 크기와 자동 확장 임계값은 상세 설계까지 미룰 수 있다. 그러나 배포 유형, DBMS 제약, 단일·다중 인스턴스, 확장 가능성, 성능·복구 목표처럼 아키텍처를 바꾸는 범주는 `DG-001` 전에 확인한다. 답을 얻지 못하면 기본값으로 확정하지 말고 미결사항으로 추적한다.

모든 상상 가능한 질문에 답했을 때가 아니라, 선택한 변경 등급에 비해 남은 불확실성이 충분히 낮을 때 인터뷰를 종료한다.
