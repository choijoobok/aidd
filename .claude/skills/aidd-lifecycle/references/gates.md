# 생애주기 게이트

발견 → 범위화 → 분석 → 배포·운영 맥락 확인 → 설계·기술 스택 선정 → 개발 기반 준비 → 계획 → 개발 → 검증 → 출시 → 운영·개선을 의무적인 폭포수 단계가 아니라 반복 가능한 상태로 사용한다.

프로젝트 시작 또는 중대한 변경에서 `.aidd/ssot/methodologies.json`을 사용해 수행 경로를 선택한다. 안정된 계약·규제 작업은 예측형 통제를, 불확실한 제품은 적응형 통제를, 기술 위험은 위험 우선 반복을 강화한다. 모든 경로에서 정본·추적성·고객 결정·증거 규칙은 유지한다.

- `DG-001 배포·운영 맥락 확인`: 제품 성과와 사용자 범위가 입력이다. 온프레미스·클라우드, DBMS, 단일·다중 인스턴스와 확장 방식, 워크로드, SLO·RTO·RPO, 일관성 불변 조건, 상태·운영 제약을 담은 배포 프로필과 미결 결정이 출력이다.
- `TG-001 기술 스택 선정`: 유효한 배포 프로필, 품질 속성과 제약이 입력이다. 현행 유지안을 포함한 대안·ADR·기술 기준선이 출력이다.
- `TG-002 개발 기반 준비도`: 승인된 기술 기준선과 적용되는 설계 위험 패턴이 입력이다. UI 적용 시 디자인 시스템·공통 컴포넌트, 그리고 모든 제품의 코딩·보안·테스트·관측성·배포·롤백 표준, 경쟁·부하·장애 검증과 실행 가능한 골든 패스가 출력이다.

기능 규모 개발은 유효한 기존 배포·기술 기준선을 재사용하거나 세 게이트를 통과한 뒤 시작한다. 배포 대상, DBMS, 인스턴스 구조, 부하 또는 가용성 요구가 바뀌면 `DG-001`부터 재평가한다.

- C0: 되돌릴 수 있는 문서 또는 국소 리팩터링. 추적 링크와 집중 검증이 필요하다.
- C1: 단일 모듈 동작 변경. 인수 기준, 테스트와 롤백이 필요하다.
- C2: 모듈 횡단, 데이터, 인터페이스 또는 보안 변경. ADR·영향도 맵과 회귀 계획을 추가한다.
- C3: 비가역, 규제 또는 대규모 영향 변경. 고객 게이트, 독립 감리, 사전 연습과 복구 증거를 추가한다.

증거를 피하기 위해 등급을 낮추지 않는다. 명시된 증거가 존재하거나 예외·위험 수용이 기록되어야 단계를 종료할 수 있다.
