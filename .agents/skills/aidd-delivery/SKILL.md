# AIDD 개발·전달

1. 변경 ID와 등급, 영향 요구사항·모듈, `WRK` 작업과 선행 의존성, 현재 협업 프로필·활성 참여자, 승인된 설계, 유효한 배포 프로필·기술 기준선, `TG-002` 기반 준비도, 적용 설계 위험, 테스트 전략, 마이그레이션과 롤백을 확인한다.
2. 작업을 검토 가능한 요구사항 크기의 증분으로 나누고 `MLS`·`WRK`·`IFC`·`DPN`에 연결한다. 요구사항이 명시적으로 바꾸지 않은 기존 동작은 보존한다.
3. 승인된 기술 스택, UI 패턴과 공통 컴포넌트를 재사용한다. 공통 AIDD 용어와 현재 프로젝트 `TRM`을 코드·API·데이터·화면·테스트·문서에서 일관되게 사용하고, 용어 추가·변경·제거가 필요하면 `aidd-terminology` 스킬을 사용한다. 모듈별 지침과 실행 가능한 계약을 따르며 재검토 조건이 발생하면 기능 개발을 계속하기 전에 기술 기준선을 다시 평가한다.
4. CHG의 `delivery_path`와 영향 `SURF`를 확인한다. 신규 기능은 요구분석·설계·문서를 선행하고, 기존 문서가 있는 기능 변경은 문서를 같은 변경에서 갱신한다. 문서가 없는 기존 기능의 후속 작성은 고객 결정과 기한 있는 WRK가 있을 때만 허용한다. `node .ai/tools/aidd.mjs development-check --change CHG-ID`와 `branch-check`가 통과한 뒤 기능 구현을 시작한다. pre-commit의 `documentation-check --staged`도 통과시킨다.
5. 위험 기반 테스트를 사용한다. 경계에는 단위·계약 테스트, 의존성·데이터에는 통합 테스트, 핵심 여정에는 종단 간 테스트, 영향 동작에는 회귀 테스트를 적용한다. 배포 프로필과 설계가 요구하면 스레드 전환, 다중 프로세스 경쟁, 중복·재시도·순서 역전, 대표 데이터 부하·포화·복구, 의존 장애 주입과 보안 테스트를 수행한다.
6. 병합 충돌이 있으면 각 해결이 올바른 이유, 영향받는 모듈·파일, 달라졌을 수 있는 가정과 추가 테스트 결정을 기록한다.
7. 출시 전에 추적성, 테스트 결과, 보안 발견사항, 마이그레이션 연습, 롤백, 관측성, 지원 준비도, 필수 게이트 승인과 잔여 위험 수용을 검증한다.
8. 생성·검증과 관련 빌드·테스트를 실행한다. 결과를 수행자·명령·시각·커밋과 함께 `EVD`로 기록하고 테스트·게이트와 양방향 연결한다. 필수 게이트가 승인되지 않은 C2·C3 변경은 완료 처리하지 않는다.
9. 검토 통제는 현재 협업 프로필을 따른다. 1인 프로젝트의 C2·C3는 별도 AI 검토 세션 또는 Codex·Claude 교차 검토 증거를 남기고, 팀 프로젝트는 작성자 외 활성 사람 참여자의 승인을 받는다. 가상의 참여자나 자기 승인을 독립 검토로 기록하지 않는다.
10. 커밋 전후 `identity-check`로 Git 작성자·커미터를 대조한다. 미등록 신원은 고객 확인 없이 자동 등록하지 않으며, 기존 참여자의 별칭·새 사람·봇으로 분류될 때까지 C2·C3와 릴리스를 진행하지 않는다.

완료와 릴리스 게이트는 [references/done-and-release.md](references/done-and-release.md)를 읽는다. 기능 슬라이스, 런북과 개발자·운영자·사용자 가이드는 [references/slice-runbook-guides.md](references/slice-runbook-guides.md)를 함께 적용한다.
