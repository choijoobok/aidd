# 프로젝트 수행 생명주기

프로젝트 수행 생명주기는 루트 `AGENTS.md`와 `.ai/skills/`의 계약을 따른다. 제품 정본은 `project/.aidd/ssot/`, 파생 문서는 `project/docs/generated/`, 제품 소스는 `project/src/`에 둔다.

수행팀은 의도·성과·범위 확인, 필요한 외부 조사, 요구·설계·표면 문서화, 위험 비례 게이트, 작은 구현 증분, 검증 증거, 출시·운영의 순서로 일한다. 배포된 Kit 파일도 프로젝트 상황에 맞게 바꿀 수 있지만 변경 이유, 영향과 검증 결과를 프로젝트 정본과 결정 이력에 남긴다.

AI는 변경의 실제 제품 동작·계약·범위 영향을 보고 C0~C3을 분류한 뒤 필요한 검토·테스트·영향 분석을 선택한다. 등급 예시는 현재 정본의 요구·사용자 검토·게이트를 자동 면제하지 않는다. 이전 결과는 대상 해시와 범위가 현재에도 유효할 때만 재사용한다.

인력 구성, 역할, PM 위임, 작업 배정, 일정과 승인 권한은 AIDD 밖의 프로젝트 운영 사항이다. AIDD는 이를 위한 사람·신원·권한 정본을 만들거나 실행 조건으로 검사하지 않는다. 프로젝트가 정한 결과를 제품 범위·우선순위·게이트 상태에 반영할 때는 결정 주체를 자유문자로 기록할 수 있지만 이는 인증이나 권한 검증이 아니다.

## 결정 기록

현재 항목에는 현재 상태와 핵심 근거를 둔다. 분석·설계·용어·소스·범위·상태를 바꾸는 의미 있는 결정은 `record-history`로 `HIS`에 기록하고 관련 `REQ`, `ADR`, `CHG`, `TRM`, `SURF`, `WRK` 등의 안정 ID를 연결한다. 정확한 파일 차이는 Git에서 확인하며 HIS는 누가 또는 어떤 협의체가 왜 결정했고 어떤 영향이 예상되었는지를 설명한다. 장기 아키텍처 선택은 ADR, 실행 범위는 CHG, 용어 변경은 TCH를 함께 사용한다.

## 결정 요청과 세션 재개

사용자나 프로젝트 결정권자의 답이 필요한 선택은 요구분석·설계·개발·검증·통합·출시·운영 단계와 무관하게 먼저 소유자별 `OI/<ID>.json`로 만든다. OI는 결정할 질문, 상태, 차단 여부와 실제 `REQ`, `ADR`, `CHG`, `GTR`, `REL`, `TRM` 등의 대상 ID를 연결하며 대상 전문 정본에도 필요한 상태·결정 조건·영향을 반영한다. 열린 OI 중 사용자에게 실제로 제시할 질문은 소유자별 `DRQ/<ID>.json`에 `DRQ`로 저장한다. DRQ는 최종 결정이나 미결 대상 자체를 복제하지 않고 질문·선택지·권장안·미응답 영향·차단 여부·우선순위·질문 시각·재개 순서를 보존하는 상호작용 큐다.

AI는 미결 대상을 정본에 기록하고 DRQ를 저장하기 전에 사용자에게 결정 질문을 보내지 않는다. 같은 `asked_at`의 질문 묶음은 일관된 1~3건으로 제한하지만 서로 다른 시점의 미응답 묶음은 함께 유지할 수 있다. 사용자가 답하지 않고 독립적인 다른 작업을 요청하면 기존 DRQ를 보존하고, 새 작업에 별도 결정이 필요하면 새 미결 대상과 DRQ 묶음을 추가한다. 상태·resume·compact·계속 진행에서는 전체 미응답 건수와 묶음 수를 보고하고 차단 여부·명시적 우선순위·오래 기다린 순서로 권장 답변 묶음을 골라 마지막에 복원한다. 현재 요청이 미응답 결정에 의존하거나 그 결정이 차단하는 게이트를 넘으려 하면 해당 질문과 차단 영향을 제시한다.

답변을 받으면 대상 정본과 필요한 `HIS`를 먼저 갱신하고 OI를 해결 내용이 있는 `closed`로 바꾼 뒤 DRQ를 `resolved`로 종료한다. 사용자가 보류하면 OI는 열린 상태로 유지하고 DRQ에는 재검토 조건이 있는 `deferred`를 기록하며, 질문이 무효가 되면 이유가 있는 `withdrawn`으로 바꾼다. `chat-history/`는 복구 참고용 원문이며 OI·DRQ나 제품 결정을 대신하지 않는다. 훅은 응답 문장을 해석해 정본을 자동 변경하지 않는다.

## 용어 변경

공통 AIDD 용어는 `.ai/manifests/terminology.json`의 뜻을 사용한다. 프로젝트 용어는 개념 유형, 범위, 별칭, 사용 예, 관련 용어와 혼동 구분을 기록한다. 새롭거나 모호한 용어는 기존 용어를 먼저 검색하고, 필요하면 읽기 전용 `term-review`로 영향 카드를 만든다. 프로젝트가 오프라인 절차로 결정한 뒤 `term-apply --decided-by "결정 주체" --summary "이유와 요약"`를 실행한다. AI는 현재 `TRM`과 전후 값·영향·결정 주체·적용·검증을 담은 `TCH`를 저장하고 용어집과 관련 파생 문서를 다시 생성한다. 특정 PM 역할이나 Git 계정 일치를 요구하지 않는다.

수식어 없는 요구사항은 사용자 가치와 관찰 가능한 결과·인수 기준을 가진 `REQ`를 뜻하고 품질 수준·제약은 `NFR`로 구분한다. 개발 단계의 구체화 문서는 요구사항이라는 이름을 다시 쓰지 않고 `기능 상세 명세`와 `화면 명세(SCR)`로 부른다. 기능 상세 명세는 `FEAT` JSON 정본이며 `REQ/UC/MOD/CHG/SCR/TC`를 연결한다.

Kit 원본과 개별 프로젝트는 서로 자동 동기화하지 않는다. 개선은 각 환경에서 별도 변경으로 영향 분석·구현·검증한다.
