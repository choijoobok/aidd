# 생애주기 게이트

발견 → 범위화 → 분석 → 배포·운영 맥락 → 설계·기술 기준선 → 계획 → 개발 → 검증 → 출시 → 운영·개선을 반복 가능한 상태로 사용한다.

프로젝트 시작 또는 중대한 변경에서 CHG의 `delivery_path`와 `POL`으로 수행 경로를 선택한다. 모든 경로에서 정본, 추적성, 결정 이력과 실제 증거 규칙을 유지한다. 팀 구성·역할·일정·승인 권한은 프로젝트 운영에서 정하며 게이트 검증기는 사람 명부나 Git 신원을 요구하지 않는다.

- `DG-001`: 배포 위치, DBMS, 인스턴스·확장, 워크로드, SLO·RTO·RPO, 일관성과 운영 제약을 확인한다.
- `TG-001`: 배포 프로필과 품질 속성에 맞는 대안·ADR·기술 기준선을 결정한다.
- `TG-002`: 기술 기준선, 개발 표준, 골든 패스, 테스트·관측성·배포·롤백과 필요한 경쟁·부하·장애 검증 준비도를 확인한다.

기능 규모 개발은 유효한 기존 기준선을 재사용하거나 필요한 게이트를 통과한 뒤 시작한다. 배포 대상이나 핵심 운영 제약이 바뀌면 `DG-001`부터 재평가한다.

`development-check --change CHG-ID`는 WRK별 준비도를 집계한다. 개별 착수는 `--work WRK-ID`로 확인한다. 요구사항의 실제 사용자 수용 RVW는 필수지만 수행팀의 신원·권한은 검사하지 않는다. DG/TG/FG/RL 범위와 정본 필드는 `.ai/spec/specialty-integration.md`를 따른다. 기록된 통과와 현재 입력의 재판정을 구분한다.

- C0: 되돌릴 수 있는 문서 또는 국소 리팩터링. 추적 링크와 집중 검증이 필요하다.
- C1: 단일 모듈 동작 변경. 인수 기준, 테스트와 롤백이 필요하다.
- C2: 모듈 횡단, 데이터, 인터페이스 또는 보안 변경. ADR·영향도와 회귀 계획을 추가한다.
- C3: 비가역, 규제 또는 대규모 영향 변경. 독립 검토, 사전 연습과 복구 증거를 강화한다.

AI는 요청의 표현이나 파일 수만으로 등급을 정하지 않는다. 변경 전후의 제품 동작, 정본 의미, 모듈·데이터·인터페이스 영향, 배포·복구 위험을 확인해 CHG의 `change_class`와 `delivery_path`에 근거를 남긴다. 문서만 바뀌어도 요구나 계약의 뜻이 달라지면 C0으로 분류하지 않는다. 기존 RVW·BSL·EVD는 대상 정의 해시와 적용 범위가 현재일 때만 재사용한다.

등급은 AI가 검토 깊이와 테스트 범위를 정하는 기준이다. 실제 단계 진입은 해당 `*-check`와 현재 필수 게이트가 판정한다. 위 표만을 근거로 사용자 수용, 목업 검토, 실제 통합 증거 또는 게이트를 면제하지 않는다. 차단되면 누락된 정본·검토·증거를 보완하고 다시 판정한다. AIDD는 결정자의 직책·권한이나 일감 배분을 검사하지 않는다.

게이트 정의와 실행을 구분한다. `DG`·`TG`는 재사용 정책이고 `GTR`은 특정 변경의 실행 결과다. 통과한 GTR에는 기준별 EVD 또는 이유·만료·보완 통제가 있는 예외와 불변 커밋이 있어야 한다. 필수 GTR이 통과하지 않으면 완료와 릴리스 준비를 차단한다. 중요한 게이트 해석·예외 결정은 관련 ID와 HIS에 주체·이유·영향을 기록한다.
