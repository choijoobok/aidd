# AIDD 방법론 청사진

## 지향점

AIDD는 예측형 프로젝트 통제, 시스템공학의 요구-검증 대응, 반복·애자일 피드백, 아키텍처 의사결정 기록, DevSecOps, 테스트 증거와 SRE 운영 피드백을 하나의 저장소 중심 통제 순환으로 결합한다. AI는 여러 역할을 수행하고 작업을 제안하지만, 의도·우선순위·위험 수용·릴리스 결정의 책임은 고객에게 있다.

이 방법론은 GitHub Spec Kit의 산출물 전개와 수렴 개념, BMAD의 역할·경로 관점, 예측형 방법의 기준선·승인, 시스템공학 V 모델의 요구-검증 추적, RUP의 위험 우선 반복, 애자일·스크럼의 검사와 적응, SSDF의 보안 통제와 SRE의 운영 학습을 차용한다. 여기에 정규화된 레지스트리를 정본으로 두고 서술형 문서를 생성된 뷰로 취급하는 원칙을 추가한다.

## 생애주기

| 단계 | 핵심 질문 | 필수 증거 | 종료 게이트 |
|---|---|---|---|
| 발견 | 왜 필요한가? | 이해관계자, 성과, 제약, 가정 | 측정 가능한 목적과 책임자가 명확하다 |
| 범위화 | 무엇을 포함하고 제외하는가? | 범위, 모듈, 품질 프로필, 위험 | 경계와 수행 방식이 승인되었다 |
| 분석 | 시스템이 무엇을 해야 하는가? | 요구사항, 유즈케이스, 비기능 요구, 미결사항 | 요구사항이 검증 가능하고 우선순위가 있다 |
| 운영 맥락 | 어디에서 어떤 부하와 장애 조건으로 실행되는가? | 배포 프로필, DBMS·인스턴스·확장 제약, 워크로드, SLO, RTO·RPO, 동시성 불변 조건 | DG-001을 통과해 설계를 바꾸는 환경 가정이 명시되었다 |
| 설계 | 어떻게 동작하고 어떤 기술이 적합한가? | 아키텍처, 데이터, 보안, UX 패턴, 품질 속성, ADR | 주요 트레이드오프와 기술 기준선이 TG-001을 통과했다 |
| 기반 준비 | 누가 개발해도 일관되고 운영 조건에서 안전한가? | UI 패턴·공통 컴포넌트, 코딩·테스트·보안·관측성·배포 표준, 동시성·부하·장애 검증, 골든 패스 | TG-002가 통과되어 기능 개발을 시작할 수 있다 |
| 계획 | 어떻게 전달할 것인가? | 증분, 의존성, 테스트 전략, 롤백 | 작업이 작고 순서·담당·가역성이 정해졌다 |
| 개발 | 구현이 설계와 일치하는가? | 코드, 마이그레이션, 설정, 가이드 | 표준과 컴포넌트 계약을 통과했다 |
| 검증 | 올바르고 안전하다는 증거가 있는가? | 테스트, 리뷰, 스캔, 추적성 | 인수·회귀·보안·감리 게이트를 통과했다 |
| 출시 | 안전하게 변경할 수 있는가? | 출시 계획, 전환, 롤백, 매뉴얼 | 고객이 잔여 위험과 출시 여부를 승인했다 |
| 운영·개선 | 가치가 지속되는가? | SLO, 장애, 피드백, 변경 | 학습 결과가 요구사항·결정 백로그로 돌아갔다 |

각 단계는 폭포수 절차가 아니라 상태다. 작은 수정은 유효한 기술 기준선과 공통 기반을 재사용해 하나의 변경 레코드 안에서 전 단계를 빠르게 거칠 수 있고, 대규모 프로그램은 모듈별로 순환을 독립 수행할 수 있다. 공통 인터페이스, 기술 기준선과 릴리스 게이트는 전체 수준에서 조정한다.

모듈 실행은 `MLS` 마일스톤, `WRK` 작업, `IFC` 인터페이스와 `DPN` 의존성으로 관리한다. 단일 모듈 상태는 요약일 뿐이며 완료 작업의 증거, 선행 의존성과 인터페이스 호환성을 함께 보아야 한다.

## 가변 협업 운영

프로젝트 규모와 검토 통제는 고정하지 않는다. `project/.aidd/ssot/collaboration.json`의 활성 사람 참여자가 1명이면 1인 프로필을, 2명 이상이면 팀 프로필을 적용한다. 합류와 이탈은 `HUM` 참여자의 상태와 `CBT` 전환 이력으로 남기며, 과거 작업과 승인 기록은 삭제하거나 새 인원에게 소급하지 않는다.

- 1인 프로젝트에서는 풀 리퀘스트와 CI를 유지하되 다른 사람의 승인을 필수화하지 않는다. C2·C3 변경의 독립 보증은 같은 구현 흐름과 분리된 AI 검토 세션 또는 Codex·Claude 교차 검토 결과로 입증하며, 자기 검토를 독립 검토로 표시하지 않는다.
- 팀 프로젝트에서는 작성자가 아닌 활성 사람 참여자 최소 1명의 승인을 요구한다. 마지막 푸시 이후 승인과 오래된 승인 무효화 정책을 적용하고 필요하면 AI 보증을 추가한다.
- 팀원이 합류하면 팀 프로필과 저장소 규칙을 재생성하고 역할·모듈 책임·미결사항 담당을 배정한다. 팀원이 이탈하면 소유권·비밀정보·접근 권한·진행 중 작업을 인계하고, 책임자 1명만 남으면 1인 프로필로 되돌린다.
- 활성 참여자는 항상 1명 이상이어야 하며 최소 1명은 소유자 역할을 가진다. 인원 변경 직후 `generate`, `validate`와 원격 저장소 보호 적용 여부 확인을 수행한다.

Git 신원은 참여자 수의 증거 후보이지 참여자 그 자체가 아니다. 모든 도달 가능한 커밋의 작성자·커미터 이름과 이메일을 `IDM`으로 기존 `HUM` 참여자 또는 봇에 연결한다. 등록되지 않은 조합을 발견하면 기존 참여자의 다른 이메일, 새 사람 또는 자동화 계정인지 고객에게 확인하고, 확인 전에는 팀원을 자동 생성하지 않는다. 봇과 동일인의 별칭은 활성 사람 수에서 제외한다. 미등록 신원과 참여자 이탈 시점 뒤의 새 커밋은 C2·C3 개발 진입과 릴리스를 차단한다. 이탈 전 과거 커밋은 정상 이력으로 보존한다.

Git 커밋은 실제 push 행위자를 증명하지 않는다. GitHub 같은 호스팅 서비스의 PR 작성자·승인자·push 행위자는 제공자 API 또는 감사 로그에서 얻은 증거와 `hosting_accounts`를 대조한다. 이 연결이 없는 동안에는 원격 행위자 검증을 완료로 주장하지 않는다.

## 방법론 수행 경로

프로젝트 시작과 중대한 변경에서 요구 안정성, 불확실성, 변경 비용, 규제·안전 중요도, 배포 빈도와 운영 책임을 평가한다. 그 결과로 예측형, 적응형 또는 혼합형 수행 경로를 선택하되 정본·추적성·증거·고객 결정 규칙은 항상 유지한다.

- 안정된 계약·규제 범위에는 예측형 기준선, 승인과 변경 통제를 강화한다.
- 불확실한 제품에는 짧은 증분, 고객 피드백과 회고를 강화한다.
- 높은 기술·통합 위험에는 RUP식 위험 우선 반복과 실행 가능한 아키텍처를 강화한다.
- 안전·검증 중요 시스템에는 V 모델식 요구-검증 대응과 독립 검토를 강화한다.
- 모든 소프트웨어에는 SSDF 보안 통제를, 운영 서비스에는 SRE 신뢰성·사후학습 통제를 추가한다.
- AI 구현에는 명세 우선, 명확화, 작업 분해, 교차 산출물 분석과 구현 후 수렴 검사를 적용한다.

구조화된 비교와 선택 규칙은 `project/.aidd/ssot/methodologies.json`, 사람이 읽는 비교표는 `project/docs/generated/methodology-comparison.md`에 둔다.

## 기술 스택과 개발 기반 게이트

기술 스택은 요구사항이나 배포 맥락보다 앞서 정하지 않는다. 먼저 성과, 기능·비기능 요구, 품질 속성과 제약을 확정한 다음 다음 순서로 진행한다.

1. `DG-001`에서 온프레미스·클라우드, DBMS, 단일·다중 인스턴스, 자동 확장, 상태, 워크로드, SLO·복구와 운영 제약을 확인한다.
2. `TG-001`에서 현행 유지안을 포함한 후보를 적합성, 보안·공급망, 지원 수명, 역량, 비용, 운영, 종속과 가역성으로 비교한다.
3. 추천과 고객 결정을 분리한 ADR과 버전·책임자·재검토 조건이 있는 기술 기준선을 승인한다.
4. `TG-002`에서 UI 적용 시 디자인 토큰·레이아웃·상태·접근성·공통 컴포넌트를, 모든 제품에서 코딩·오류·보안·테스트·관측성·배포·롤백 표준과 개발자 가이드를 준비한다.
5. 대표 골든 패스 또는 얇은 수직 절편에서 적용되는 트랜잭션·AOP·스레드·다중 인스턴스·재시도·스케줄·성능·장애 위험을 검증한 뒤 기능 증분 계획과 개발로 이동한다.

게이트 정의는 재사용 정책이며 통과 주장이 아니다. 각 변경은 적용 게이트별 `GTR` 실행을 만들고, 기준별 `EVD`와 별도 승인을 연결한다. 진행 중 변경은 미승인 실행을 가질 수 있지만 C2·C3 완료와 릴리스 준비 완료는 모든 필수 실행 승인 전까지 차단한다.

상세 기준과 현재 기준선은 `project/.aidd/ssot/technology.json`, 생성 뷰는 `project/docs/generated/technology-gates.md`에서 관리한다.

기능 구현 진입은 `development-check`로, 릴리스 진입은 `release-check`로 별도 확인한다. 전자는 변경별 필수 게이트 승인을, 후자는 테스트·변경·위험·미결사항·산출물과 게이트를 종합한다.

개발 기반은 기술 스택을 AIDD 공통 규칙으로 고정하지 않고 프로젝트 정본으로 작성한다. `STD`는 실행 실패로 드러나는 계약과 별도 검사 없이는 조용히 위반되는 정책을 구분하며, `GPH`는 대표 구현·테스트 경로를, `EXC`는 기한 있는 예외와 보완 통제를 기록한다. UI가 적용되면 사용자와 `UXB` 기준선과 대표 `SCR` 목업을 먼저 합의하고, 반복되거나 접근성·보안·오류 일관성이 중요한 요소를 `UIP`·`CMP`로 승격한다. 모듈은 공통 기반을 복사하지 않고 안정 ID로 참조한다.

`SCR`에서 생성한 HTML은 설계 검토용 목업이며 실제 구현 증거가 아니다. `MAN`이 검증·출시 상태가 되거나 `DLP`가 실제 캡처를 요구하면 화면 ID·커밋·환경과 연결된 `EVD`가 필요하다. `RUN`은 운영 절차를, `DLP`는 대상별 포함·제외와 목업 허용 여부를 정의한다. 현재 CLI는 정본과 결정적 manifest까지만 제공하며 실제 사용자 사이트·ZIP 패키지·브라우저 캡처는 프로젝트 실행 자산으로 확장한다.

## 배포 환경과 설계 위험 예방

기획 단계에서는 특정 제품을 성급히 고정하지 않고 설계를 바꾸는 환경 범주를 확인한다. 온프레미스·클라우드, DBMS 제약, 단일·다중 인스턴스, 자동 확장, 데이터·부하 규모, SLO·RTO·RPO, 상태·세션·캐시·스케줄러와 운영 책임을 배포 프로필로 기록한다. 인스턴스 수·세부 사양·풀 크기 같은 값은 범위와 재평가 조건을 두고 늦출 수 있다.

설계에서는 업무 불변 조건을 먼저 정의한다. 예를 들어 재고가 음수가 되지 않음, 결제가 한 번만 반영됨, 한 작업을 한 실행 주체만 처리함과 같은 조건이다. 그 후 트랜잭션 경계, 프록시 기반 AOP, 스레드 전환, 다중 인스턴스 경쟁, 재시도·중복·순서 역전, 스케줄 중복, 자원 병목과 의존 시스템 장애 전파를 검토한다. 각 적용 위험에는 통제와 부정·경쟁·부하·장애 검증을 연결한다.

정본은 `project/.aidd/ssot/deployment.json`, 생성 뷰는 `project/docs/generated/deployment-and-runtime.md`에서 관리한다.

## 역할 관점

역할은 서로 분리된 인격이 아니라 검토 관점이다. 하나의 AI가 여러 관점을 적용할 수 있지만 각 관점이 만든 증거를 명시해야 한다.

- PM/제품: 성과, 범위, 우선순위, 이해관계자 합의, 가치 측정.
- BA/도메인 분석: 요구사항, 규칙, 유즈케이스, 예외, 용어.
- UX: 사용자 여정, 정보 구조, 접근성, 레이아웃·상호작용 패턴.
- AA/솔루션 아키텍처: 경계, 인터페이스, 품질 속성, ADR, 의존 방향.
- DA/DBA: 개념·논리·물리 데이터, 소유권, 계보, 보존, 마이그레이션, 복구.
- 보안: 위협, 오용 사례, 통제, 비밀정보, 개인정보, 공급망, 잔여 위험.
- 인프라/DevOps/SRE: 환경, IaC, CI/CD, 관측성, SLO, 용량, 롤백.
- 개발: 구현, 코딩 표준, 공통 컴포넌트, 자동 검사.
- QA/테스트: 위험 기반 테스트 설계, 커버리지, 증거, 결함 확인.
- 감리/독립 검토: 추적성, 증거 분리, 통제 예외, 게이트 무결성.
- 운영/지원: 런북, 경보, 진단, 복구, 사용자·관리자 지침.

## 사람의 의사결정 규약

의미 있는 트레이드오프에서는 가능한 경우 현상 유지를 포함하여 둘 이상의 실행 가능한 대안을 제시한다. 각 대안은 성과 적합성, 비용, 기간, 운영 부담, 보안·개인정보 영향, 종속성, 가역성과 불확실성을 포함한다. AI의 추천과 고객의 최종 결정은 분리해서 기록한다. 결정을 번복할 때는 과거 기록을 삭제하지 않고 대체 관계를 남긴다.

## AI 플랫폼과 저장소 통제 검증

Codex와 Claude는 공통 스킬 정본을 사용하지만 파일 동일성은 행동 동일성의 충분조건이 아니다. 같은 `EVS` 픽스처와 루브릭으로 플랫폼별 결과를 기록하고 금지 행동과 점수 차이를 검토한다. GitHub Actions와 ruleset 파일도 원격 보호 활성화의 충분조건이 아니므로 원격 조회 결과를 별도 증거로 남긴다. 협업 프로필 전환으로 생성된 승인 수 역시 로컬 기준일 뿐이며 원격 규칙이 갱신되었다는 증거와 구분한다.

## 기존 시스템과 유지보수

기존 시스템을 변경하기 전에 코드, 테스트, 실행 증거와 문서로 현재 동작을 기준선화한다. 충돌은 불일치로 표시하며 코드나 문서 중 어느 하나가 자동으로 정답이라고 가정하지 않는다. 모든 변경은 변경 ID, 영향 모듈·요구사항, 전환·롤백과 회귀 범위를 가진다. 새 모듈은 독립적으로 진행할 수 있지만 공통 인터페이스와 릴리스 의존성은 명시적으로 관리한다.
