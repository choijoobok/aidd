# AIDD 문서 정합성 검토

1. 범위와 기준 시점을 먼저 정한다. 구현된 현재 동작은 `project/src/`의 코드·실행 증거, 제품·설계 의도는 `project/.aidd/ssot/`, `project/docs/generated/`는 재생성 대상이라는 역할을 구분한다. 코드와 정본이 다르면 어느 쪽도 자동 정답으로 정하지 않고 불일치로 기록한다.
2. `node .ai/tools/aidd.mjs validate`, `node .ai/tools/aidd.mjs document-impact`와 관련 테스트를 먼저 실행해 끊어진 ID, 정본-파생물 드리프트, 소스 변경 후보, 구조 오류를 의미 검토와 분리한다. 자동 검사 결과를 의미 모순으로 중복 집계하지 않는다.
3. 영향 ID·용어·참조를 검색해 후보를 좁힌 뒤, 범위·책임, 업무 규칙·예외·수용 기준, 모듈·인터페이스 계약, 데이터·권한, 비기능·운영, ADR·가정·게이트·상태 전이를 대조한다. 용어 변경이면 PM의 `term-review` 확인 카드가 요구사항·모듈·설계·데이터·API·화면·테스트·문서·소스 주석 사용처를 다뤘는지, PM 확인 뒤 관련 위치가 함께 현행화됐는지, 현재 `TRM`의 개념 유형·분류·범위·예시·관련 용어·혼동 구분이 실제 사용과 일치하는지, `TCH` 전후 이력이 일치하는지, 공통 AIDD 용어를 재정의하지 않았는지 확인한다. 정상 흐름뿐 아니라 재시도·취소·부분 실패 뒤의 다음 경로를 확인한다.
4. 발견사항을 `모순`, `낡음`, `정의 중복`, `경계 불명확`, `흐름 단절` 중 하나로 판정한다. 각 항목에 사실, 근거 경로, 영향 ID, 판정, 권장 처리와 확인하지 못한 전제를 붙여 보고한다.
5. 검토만으로 정본·코드·게이트를 자동 변경하지 않는다. 승인된 사실의 의미 변경은 `CHG`로, 확인 불가 사실은 `ASM` 또는 `OI`로, 파생물 불일치는 정본 수정 뒤 생성으로 처리한다.
6. 병합 뒤 수행하면 `MRG`의 양쪽 부모와 해결 결과를 비교한다. 필요한 재검토·재테스트는 담당자를 미리 지정하지 않은 `MRC`로 기록한다. PM·관리자가 오프라인으로 조율하며, 완료 시에만 실제 수행자(`HUM`), 시각, 결과와 `EVD` 증거를 기록한다. 필수 `MRC`가 남으면 현재 릴리스 준비가 차단됨을 보고한다.
7. 프로젝트 문서 포맷을 바꾸는 경우에는 먼저 `documentation.json`의 문서 유형·독자·필수 항목·근거·대상 생성물을 사용자와 합의한다. 새 필수 항목은 대상 패턴의 기존 문서 전체에 소급 생성하고, 자동 근거가 없으면 미작성 표시와 OI를 남긴다. 기존 문서를 조용히 삭제·축소하거나 빈칸을 사실처럼 채우지 않는다.

## 결과 형식

```markdown
## 문서 정합성 검토

| 판정 | 사실 | 근거 | 영향 ID | 권장 처리 |
|---|---|---|---|---|
| 모순 | 승인 주체가 두 곳에서 다름 | 경로 A · 경로 B | REQ-… · IFC-… | 정본 한 곳을 사용자와 확정 |
| 흐름 단절 | 승인 결과가 실행 입력으로 전달되지 않음 | 경로 A · 경로 B | REQ-… · TC-… | 상태·권한·예외 경로 확정 |
```

문제가 없을 때도 검토 범위와 확인하지 못한 전제를 함께 남긴다. “발견사항 없음”은 위험이 없다는 뜻이 아니다.
