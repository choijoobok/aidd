# 프로젝트 수행 생명주기

프로젝트 수행 생명주기는 루트 `AGENTS.md`와 `.ai/skills/`의 계약을 따른다. 제품 정본은 `project/.aidd/ssot/`, 파생 문서는 `project/docs/generated/`, 제품 소스는 `project/src/`에 둔다.

수행팀은 의도·성과·범위 합의, `BEN-TRIAGE` 벤치마킹 필요성 판단, 필요한 경우 고객과 합의한 범위·기준의 외부 조사와 추천·결정, 요구·설계·표면 문서화, 위험 비례 게이트, 작은 구현 증분, 검증 증거, 출시·운영의 순서로 일한다. 벤치마킹 필요성 판단은 필수지만 외부 조사는 자동 또는 무조건 수행하지 않는다. 조사 관측은 보조 `research-note`에 출처·한계·우리 환경과의 차이를 남기며 고객이 수용한 내용만 ADR·REQ·OI에 반영한다. 배포된 Kit 파일도 프로젝트 상황에 맞게 바꿀 수 있지만, 변경 이유와 영향·검증 결과를 프로젝트 정본에 기록한다.

요구분석부터 공통 AIDD 용어는 `.ai/manifests/terminology.json`의 뜻을 그대로 사용한다. 프로젝트 용어는 `business`(업무), `product`(제품 동작·정책), `technical`(구현·운영), `external`(외부 표준·제품 어휘)의 개념 유형과 프로젝트별 `category`로 분류한다. 각 용어는 정의뿐 아니라 적용 범위, 별칭, 올바른 사용 예, 관련 용어와 실제로 혼동 가능한 용어의 차이·판단 규칙을 가질 수 있다. 외부 어휘는 출처를 기록하고 프로젝트 명명의 기준과 구분한다.

요구분석·설계 중 AI가 반복될 새 개념, 기존 용어와 범위가 다른 표현, 사람마다 다르게 해석할 표현 또는 정의에 따라 요구·설계가 달라지는 표현을 발견하면 기존 공통·프로젝트 용어를 먼저 검색한다. 같은 뜻이면 새 용어 대신 별칭을 검토하고, 명확화가 필요하면 `term-review`를 읽기 전용으로 수행해 영향 후보와 함께 한 확인 카드로 PM에게 묻는다. PM의 동의는 해당 용어 변경 승인으로 보며 별도 용어 관리 요청이나 두 번째 확인을 요구하지 않는다. AI는 관련 정본·문서·소스 주석을 먼저 현행화하고 `term-apply`로 현재 `TRM`과 전후 값·영향·PM 확인·적용·검증을 담은 `TCH`를 함께 저장한다. 통합 Markdown과 독자별 오프라인 HTML 용어집을 다시 생성하고 `validate`를 통과해야 완료된다. 일회성 표현과 일반적인 일상어는 등록하지 않으며 팀원 제안, 승인 대기와 반려를 위한 별도 용어 상태도 만들지 않는다.

Kit 원본의 변경을 발견했다고 해서 프로젝트에 자동 적용하지 않는다. 반대로 프로젝트의 개선을 원본에 코드로 자동 반영하지 않는다. 필요한 경우 변경 정보를 검토하고 각 환경에서 별도 변경으로 구현한다.
