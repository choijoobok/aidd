# AIDD 용어 관리

1. 새 용어 후보가 나오면 `.ai/manifests/terminology.json`의 AIDD 공통 용어와 `project/.aidd/ssot/terminology.json`의 현재 프로젝트 용어를 먼저 검색한다. 공통 용어는 프로젝트에서 수정하거나 다른 뜻으로 재정의하지 않는다.
2. 요구·설계·데이터·API·화면·소스 명명에 반복되거나, 사람마다 다르게 해석할 수 있거나, 정의에 따라 계약과 인수 기준이 달라지는 표현만 관리 후보로 삼는다. 일회성 표현과 일반적인 일상어는 등록하지 않는다.
3. 기존 용어와 뜻이 같으면 새 용어보다 별칭을 검토한다. 비슷하지만 범위·책임·상태가 다르면 별도 용어로 구분하고 선택 판단 규칙을 명시한다. 외부 표준·프레임워크 어휘는 `external`로 분류하고 출처를 남긴다.
4. 후보의 용어·key, 개념 유형, 프로젝트 분류, 정의, 적용 범위, 별칭, 사용 예, 관련 용어, 혼동되는 용어와 판단 규칙, 독자, 공개 범위 및 요구사항·설계·데이터·API·화면·테스트·문서·소스 주석 영향 후보를 정리한다.
5. 현재 Git 신원에 연결된 활성 팀원으로 읽기 전용 `term-review`를 실행한다. 활성 PM이 여러 명이면 `--target-pm`을 지정한다. 이 단계는 정본을 수정하거나 제안·승인 대기·반려 상태를 만들지 않는다.
6. 같은 세션에 PM이 없으면 `term-review` 결과 전체를 팀원이 복사해 오프라인으로 PM에게 전달하도록 안내한다. 카드는 승인이나 정본이 아니며 PM은 내용을 확인·수정할 수 있다.
7. PM이 자신의 AI 세션에서 카드 내용과 승인 의사를 전달하거나 용어 변경을 직접 요청한 경우에만 실제 변경을 수행한다. 현재 Git 신원이 승인한 활성 PM과 일치하지 않으면 `term-apply`를 실행하지 않는다.
8. 승인 뒤 영향받는 정본·문서·소스 주석을 먼저 현행화하고 PM 신원으로 `term-apply`를 실행한다. 현재 `TRM`, 전후 값·영향·PM 확인·적용·검증을 담은 `TCH`, Markdown과 독자별 오프라인 HTML 용어집 생성 및 `validate`를 한 흐름으로 완료한다.
9. `term-apply`가 실패하면 용어 변경 완료를 선언하지 않는다. 남은 충돌·잔존 표현·누락된 영향 위치를 설명하고 해결한 뒤 같은 승인 범위에서 다시 적용한다.
10. 최종 사용자 용어집에는 `visibility: customer`이고 독자에 `end_user`가 포함된 프로젝트 용어만 공개한다. 생성된 `project/docs/generated/glossary.md`와 HTML은 직접 수정하지 않는다.

확인 카드의 항목과 자연어 예시는 [용어 확인 카드](../../templates/artifact/terminology-workbook.md), 팀 수행 절차와 명령 예시는 [문서 관리 가이드](../../docs/guides/project-team/03-document-management.md)를 따른다.
