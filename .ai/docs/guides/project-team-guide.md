# AIDD 프로젝트 수행팀 가이드

이 문서는 AIDD Kit으로 생성한 프로젝트를 시작하고 완료할 때까지 사용하는 **프로젝트 팀용 단일 진입점**이다. Kit 자체를 변경·export·출시하는 절차는 배포되지 않는 관리자 가이드에서 다룬다.

## 무엇을 먼저 읽어야 하나

| 상황 | 읽을 문서 |
|---|---|
| 템플릿을 받아 새 프로젝트를 만드는 중 | [프로젝트 준비와 시작](project-team/01-project-setup.md) |
| 요구사항부터 운영까지 전체 순서를 알고 싶음 | [수행 생명주기](project-team/02-lifecycle.md) |
| 정본·생성 문서·작업 기록·용어 사전을 관리하고 싶음 | [문서 관리](project-team/03-document-management.md) |
| AI 스킬과 훅이 언제 무엇을 하는지 알고 싶음 | [스킬과 훅](project-team/04-skills-and-hooks.md) |
| 1인 또는 팀 Git 작업·인계·병합을 운영함 | [팀 작업 흐름](project-team/05-team-workflow.md) |
| 완료·출시·운영 전 확인 항목이 필요함 | [완료와 출시](project-team/06-completion-and-release.md) |

처음 사용하는 팀은 위 순서대로 읽는다. 진행 중인 팀은 이 문서의 전체 흐름을 확인한 뒤 필요한 장만 찾아가면 된다.

## 전체 흐름 한눈에 보기

1. 배포받은 `kit-template`에서 Git과 훅을 준비하고 `project-bootstrap`으로 제품 정본을 만든다.
2. 최초 소유자 `HUM`과 현재 Git 신원 `IDM`을 등록해 작업자를 식별한다.
3. 해결할 문제·사용자·성과·하지 않을 범위를 합의하고 요구사항과 미결사항을 기록한다.
4. 모듈·배포 맥락·아키텍처·기술 기준선·UI와 운영 조건을 필요한 깊이만큼 결정한다.
5. `CHG`와 `WRK`로 작은 구현 단위를 만들고, 요구·설계·코드·테스트·문서를 같은 증분에서 갱신한다.
6. 영향 범위의 생성·검증·테스트를 실행하고, 필수 게이트와 미결 위험을 확인한다.
7. 병합 후 영향을 재확인하고 `release-check`가 준비된 경우에만 출시 준비 완료로 표시한다.
8. 운영 결과와 피드백을 새 요구·변경·결정으로 연결한다.

모든 단계가 항상 필요한 것은 아니다. 변경 크기와 위험에 비례해 적용하되, 확인하지 않은 내용을 사실이나 완료로 기록하지 않는다.

## 명령보다 자연어 요청이 먼저다

사용자가 AIDD ID나 CLI 문법을 외울 필요는 없다. 해결하려는 문제, 원하는 결과, 제약과 알고 있는 사실을 자연어로 말하면 AI가 현재 역할과 정본을 확인하고 적절한 스킬·기록·명령으로 연결한다. 코드 블록은 자동화, 재현과 문제 해결을 위한 참고다.

새 프로젝트를 시작할 때:

> 이 템플릿에서 고객 문의 관리 프로젝트를 시작하고 싶어. 아직 구현하지 말고 프로젝트 이름과 ID, 신규 구축인지 먼저 확인해줘. 기존 파일을 덮어쓰지 말고 초기화 결과와 다음 질문을 설명해줘.

진행 중인 프로젝트를 이어갈 때:

> 현재 프로젝트의 확정된 목표와 범위, 내 작업자 신원, 진행 중 작업, 막힌 결정과 통합 위험을 정본에서 확인해 브리핑해줘. 오늘 처리할 가장 작은 다음 작업을 제안해줘.

기능 변경을 요청할 때:

> 고객 검색 결과를 저장할 수 있게 바꾸고 싶어. 관련 요구사항·모듈·화면·데이터·테스트·문서 영향을 먼저 분석하고, 필요한 결정과 작은 구현 계획을 보여준 뒤 내 확인을 받아 진행해줘.

검증과 출시를 요청할 때:

> 이번 변경이 승인된 요구사항을 충족하는지 확인해줘. 변경 영역의 테스트와 파생 문서 전체 비교만 수행하고, 확인하지 않은 항목과 잔여 위험을 구분해줘. 출시 준비 여부는 release-check 결과와 함께 설명해줘.

## 사람과 AI의 책임

- 고객 또는 제품 책임자는 제품 의도, 우선순위, 위험 수용과 되돌리기 어려운 결정을 승인한다.
- PM은 범위, 팀 프로필, 작업 배정, 게이트와 인계를 조율한다.
- 구성원은 배정된 작업의 요구·설계·구현·시험·문서·운영 영향을 함께 책임진다.
- AI는 질문, 대안 비교, 구현, 검증과 기록을 돕지만 승인이나 실제 실행 결과를 꾸며내지 않는다.
- 1인 프로젝트도 같은 구조를 쓸 수 있다. 독립 검토가 필요한 경우에만 별도 세션이나 다른 검토자를 둔다.

## 매 세션의 최소 시작

AI에게 “세션 시작 점검을 하고 현재 상태를 브리핑해줘”라고 요청하면 아래 명령과 현재 프로젝트 정본을 확인한다. 직접 확인할 때는 다음을 실행한다.

```powershell
node .ai/tools/aidd_hook.mjs self-test --hook
node .ai/tools/aidd.mjs current-actor
node .ai/tools/aidd.mjs status --level executive
node .ai/tools/aidd.mjs integration-status
```

아직 최초 참여자와 Git 신원을 등록하지 않았다면 `current-actor`보다 [프로젝트 준비와 시작](project-team/01-project-setup.md)의 최초 등록 절차를 먼저 수행한다. `self-test --hook`은 런타임과 계약·provider 이벤트 배선을 확인하는 빠른 진단이며, 프로젝트 전체 테스트나 보안·권한 감사를 대신하지 않는다.

## 일상 수행의 기본 원칙

- 대화에서 합의한 사실은 구조화 정본에 기록하고, 미확정 내용은 가정 또는 미결사항으로 남긴다.
- `project/docs/generated/`는 정본에서 만든 결과다. 직접 수정하지 않는다.
- 코드나 정본을 변경한 뒤 `document-impact`, `generate`, `validate`와 영향받은 테스트만 수행한다.
- AIDD 요건·스펙 구현 검증 요청에는 `aidd-requirement-verification` 스킬을 사용한다.
- 보안·권한·신원·서명 검사는 프로젝트 정본이 요구하거나 사용자가 명시적으로 요청한 경우에만 범위에 넣는다.
- 원본 Kit과 프로젝트는 export 뒤 자동으로 동기화되지 않는다. 개선 설명을 검토해 프로젝트의 별도 변경으로 수용한다.

## 문서 체계

- `.ai/spec/`: 프로젝트에도 적용되는 AIDD 행동 명세
- `.ai/docs/guides/`: 사람이 읽는 프로젝트 수행 가이드
- `.ai/docs/methodology/`: 산출물 모델과 방법론의 설명 자료
- `.ai/skills/`: AI가 특정 작업에서 따르는 수행 절차
- `.ai/templates/`: 정본 또는 상세 문서를 작성할 때 쓰는 입력 양식
- `project/.aidd/ssot/`: 현재 제품의 구조화 정본
- `project/docs/generated/`: 정본에서 재생성하는 파생 문서
- `work-log/`: 수행 이유·결과·다음 행동을 남기는 작업 기록
- `chat-history/`: Git에 넣지 않는 로컬 대화 원문

이 문서군은 서로를 복제한 것이 아니다. 사람의 사용법은 이 가이드에, 규범적 행동은 명세에, AI 절차는 스킬에, 프로젝트 사실은 제품 정본에 한 번만 둔다.
