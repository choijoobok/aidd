# AI와 대화하며 시작하는 AIDD 프로젝트 가이드

이 안내서는 AIDD를 처음 쓰는 고객·프로젝트 책임자가 Codex 또는 Claude와 대화하며 프로젝트를 시작하고 진행하는 방법을 설명한다. 명령어와 JSON을 먼저 배울 필요는 없다. 먼저 문제와 목표를 자기 말로 설명하고, AI에게 질문·정리·선택지·기록을 맡긴다. 중요한 선택과 승인만 사람이 한다.

## 먼저 기억할 세 가지

1. **사람은 방향과 선택의 책임자다.** 무엇을 만들지, 어디까지 할지, 비용·위험을 감수할지는 고객이 정한다.
2. **AI는 질문자·정리자·실행자다.** 빠진 정보를 묻고, 선택지를 비교하고, 합의한 내용을 정본과 작업 계획으로 옮기고, 구현·검증을 수행한다.
3. **대화가 곧바로 확정 사실은 아니다.** 확정한 내용은 AI가 정본에 기록하고, 불확실한 내용은 가정 또는 미결사항으로 남겨 다음 대화에서 다시 확인한다.

따라서 “아직 잘 모르겠다”는 훌륭한 시작 정보다. 예를 들어 배포 환경이나 사용량을 모르면 AI에게 추측해서 정하지 말고, 확인할 질문과 결정 시점을 정리해 달라고 요청하면 된다.

## 시작 전 준비와 제약

AIDD는 제품을 대신 호스팅하거나 개발 언어·클라우드·데이터베이스를 제공하는 서비스가 아니다. **프로젝트의 결정과 증거를 Git 저장소에 남기고, AI가 그 저장소를 읽고 갱신하도록 돕는 방법론·도구 묶음**이다. 따라서 아래 조건을 먼저 확인한다.

| 구분 | 필요한 것 | 알아둘 제약 |
|---|---|---|
| 필수 | Git과 `python` 명령을 실행할 수 있는 로컬 환경 | AIDD CLI는 Python 표준 라이브러리만 사용한다. Git은 변경 이력·훅·협업 통제에 사용하므로 설치되어 있고 경로(PATH)에서 실행 가능해야 한다. |
| 필수 | Codex **또는** Claude Code 중 하나 | 둘 다 설치할 필요는 없다. 선택한 AI가 프로젝트 폴더를 읽고, 사용자의 승인 아래 파일·터미널 작업을 수행할 수 있어야 한다. AIDD는 두 도구용 지침 어댑터를 함께 제공한다. |
| 필수 | 프로젝트 폴더에 대한 읽기·쓰기 권한 | AI가 정본·코드·생성 문서를 갱신하고 `generate`, `validate`를 실행할 수 있어야 한다. 중요한 외부 작업, 커밋·푸시·배포 권한은 별도로 통제한다. |
| 처음 한 번 | 별도 프로젝트 루트, Git 초기화와 제품 정본 골격 | 복사한 Kit은 다른 Git 저장소 안에 중첩되지 않은 폴더에서 시작한다. `project/`는 복사하지 않고 `project-init` 뒤 `project-bootstrap`으로 새 제품 정본을 만든다. 두 명령 모두 커밋·신원 등록·기존 소스 이동을 자동으로 하지 않는다. |
| 선택 | GitHub 같은 원격 저장소·CI·브랜치 보호 | 로컬에서 대화·기록·생성·검증을 시작하는 데 원격 저장소나 인터넷은 필수가 아니다. 다만 팀 협업·PR·원격 보호·CI를 쓰려면 해당 서비스 계정과 권한, 실제 적용 확인이 필요하다. |
| 프로젝트별 | 클라우드, DBMS, 외부 API, 비밀정보, Node·Docker 등 | 이것들은 AIDD의 선행 조건이 아니다. 만들 시스템의 기술 기준선에서 선택한다. 필요한 계정·네트워크·라이선스·보안 승인은 AI가 추측해 만들거나 우회할 수 없다. |

PowerShell 예시는 Windows 기준이다. 다른 운영체제에서는 같은 `python .ai/tools/aidd.py ...` 명령을 해당 터미널에서 실행하면 된다. 명령이 `python` 또는 `git`을 찾지 못하면 설치·PATH 설정은 사용자 또는 조직의 IT 정책에 따라 해결해야 한다.

AI에게 처음 환경을 점검하게 하려면 이렇게 말하면 된다.

> AIDD를 시작하기 전에 이 컴퓨터와 저장소에서 가능한 것과 불가능한 것을 점검해줘. Git, Python, 선택한 AI의 저장소 접근 권한, Git 훅 상태를 확인하고, 없는 권한·도구·외부 계정은 우회하지 말고 준비 목록으로 분리해줘.

## 0. 새 대화의 첫 메시지

Codex 또는 Claude에서 프로젝트 폴더를 열고, `project/`가 없다면 먼저 `project-bootstrap`으로 제품 정본 골격을 만든다. 예를 들어 기존 시스템이라면 다음처럼 요청한다.

> `ERP-CORE`라는 기존 ERP를 AIDD로 관리하려고 해. 현재 소스 위치는 `D:\workspace\legacy-erp`야. 먼저 정본 골격을 만들고, 소스는 이동하지 말고 분석·이동 계획부터 제안해줘.

그 뒤 아래처럼 대화를 시작한다. 같은 문장을 매번 정확히 쓸 필요는 없다.

> AIDD 방식으로 새 프로젝트를 시작하고 싶어. 아직 구현하지 말고, 내가 해결하려는 문제와 목표를 이해하기 위한 인터뷰부터 해줘. 답하지 못한 내용은 가정이나 미결사항으로 구분하고, 중요한 선택은 대안과 추천 이유를 보여준 뒤 내 결정을 받아 기록해줘.

기존 시스템이라면 다음과 같이 시작한다.

> 기존 시스템에 새 모듈을 추가하려고 해. 먼저 현재 구조, 영향받는 사용자·모듈·인터페이스·데이터·운영 제약을 파악할 질문을 해줘. 기존 동작을 추측해서 바꾸지 말고, 확인되지 않은 내용은 미결사항으로 남겨줘.

AI는 시작할 때 프로젝트 상태와 정본을 확인한다. `bootstrap` 상태에서는 일반 진척을 추정하지 않고, 제품 의도·범위·모듈·배포 맥락을 먼저 합의하도록 안내한다. 필요하면 로컬 Git과 훅을 준비하지만, 파일을 임의로 커밋하거나 Git 신원을 등록하지는 않는다.

## 매 세션의 시작: 1분 브리핑과 병합 알림

새 대화를 열거나 며칠 뒤 다시 시작할 때는 바로 구현 요청부터 하지 않는다. AI가 정본 기준으로 현재 단계, 진행·차단 작업, 다음 결정과 병합 알림을 짧게 알려 주어야 한다.

> 오늘 작업을 시작하기 전에 AIDD 정본 기준으로 현재 진행 상황을 짧게 브리핑해줘. 평가하지 않은 병합이나 아직 끝나지 않은 병합 후 재검토가 있으면 먼저 알려주고, 오늘 내가 결정하거나 확인할 가장 작은 다음 일을 제안해줘.

병합 때문에 재검토가 필요하면 AI는 **누구에게 할당하지 않은** `MRC` 항목을 만든다. PM 또는 관리자가 회의·메신저 등 오프라인 방식으로 팀원에게 요청하고, 실제 검토가 끝난 뒤에만 AI에게 수행자, 시각, 결과와 처리 내용을 기록하게 한다.

> `MRG-001`의 문서 정합성 재검토와 회귀 테스트를 기록해줘. 담당자는 지정하지 말고, 릴리스 전에 반드시 끝나야 하는지와 확인할 모듈·테스트를 구분해줘. 완료 보고를 받으면 누가 언제 검토했고 어떤 결과였으며 어떻게 처리했는지 증거와 함께 남겨줘.

평가 대기 `MRG` 또는 필수 대기 `MRC`가 있으면 AI는 “기존 작업이 모두 끝났다”고 말하거나 출시 준비 완료를 선언하면 안 된다.

## 전체 흐름 한눈에 보기

프로젝트는 다음 흐름을 반복한다. 한 번에 끝내는 폭포수 과정이 아니다. 새 사실이 생기면 앞 단계로 돌아가 보완한다.

| 단계 | 사람과 AI가 함께 답할 질문 | 이 단계에서 남기는 것 |
|---|---|---|
| 1. 의도 찾기 | 누구의 어떤 문제를 왜 지금 해결하는가? 성공은 어떻게 알 수 있는가? | 목표, 범위·제외 범위, 이해관계자, 가정·미결사항 |
| 2. 범위와 모듈 | 무엇을 이번에 하고 무엇을 하지 않는가? 어떤 모듈로 나누면 이해·변경이 쉬운가? | 요구사항, 모듈, 우선순위, 변경 범위 |
| 3. 운영 맥락 | 어디서 운영하는가? 데이터·보안·사용량·복구 조건은 무엇인가? | 배포 프로필, 위험, 확인할 결정 |
| 4. 기술 선택 | 어떤 대안이 있고 왜 이 선택이 맞는가? 현행 유지는 어떤가? | 대안 비교, ADR, 기술 기준선 |
| 5. 공통 기반 합의 | UI는 어떤 원칙·패턴을 따르는가? 공통 컴포넌트와 개발 표준은 무엇인가? | UI 기준선·패턴·컴포넌트, 개발 표준, 골든 패스 |
| 6. 작은 단위 구현 | 이번에 사용자에게 보이는 가장 작은 가치가 무엇인가? 어떻게 실패를 검증할까? | 작업, 테스트, 코드, 운영·사용자 가이드, 증거 |
| 7. 검토와 출시 | 정말 준비되었는가? 남은 위험은 누가 수용하는가? 문제가 나면 어떻게 되돌리는가? | 검토 결과, 게이트, 릴리스 결정, 런북 |
| 8. 운영과 개선 | 실제로 성과가 났는가? 다음에 무엇을 바꿀까? | 운영 지표, 피드백, 후속 변경 |

## 1. 의도 찾기: 답을 주기보다 AI에게 인터뷰를 요청한다

처음부터 완성된 요구사항을 작성하려 애쓰지 않아도 된다. 아래 정도의 설명이면 충분하다.

> 사내 영업팀이 고객 상담 내용을 여기저기 흩어 놓고 있어서, 누락 없이 후속 조치할 수 있는 도구가 필요해. 처음에는 20명 정도가 쓰고, 상담 등록과 담당자별 할 일 확인이 가장 중요해. 성공 기준과 범위부터 함께 정리해줘.

이 단계에서 AI에게 기대할 행동은 다음과 같다.

- 모호한 단어를 구체적인 사용자 행동과 결과로 바꾸어 질문한다.
- “이번에는 하지 않을 것”도 함께 정리한다.
- 성과를 측정할 기준을 제안하되, 임의로 확정하지 않는다.
- 모르는 항목은 `가정` 또는 `미결사항`으로 구분한다.
- 여러 방향이 가능하면 선택지·비용·위험·되돌리기 쉬운 정도를 비교한 뒤 추천한다.

사람이 이 단계에서 결정할 것은 제품의 목적, 우선순위, 투자 가능한 범위, 그리고 어떤 불확실성을 먼저 확인할지다. AI가 만든 문장이 마음에 들지 않으면 “그 표현은 고객의 언어가 아니야”, “이번 단계에서는 관리자 기능을 제외해줘”처럼 바로 수정 방향을 말하면 된다.

## 2. 범위와 모듈: 큰 요구를 함께 나눈다

문제가 정리되면 AI에게 기능 목록을 바로 개발하게 하지 말고, 모듈과 우선순위를 먼저 제안하게 한다.

> 지금까지 합의한 내용을 기준으로 모듈 후보를 제안해줘. 각 모듈의 책임, 다른 모듈과의 의존성, 이번 릴리스에 포함할지 여부를 표로 보여줘. 중복되거나 너무 큰 모듈이 있으면 대안도 알려줘.

좋은 모듈은 화면 메뉴 이름이 아니라 **변경 이유와 책임**으로 나뉜다. 예를 들어 “상담 관리”, “후속 조치”, “사용자·권한”, “알림”처럼 나눌 수 있다. 처음에는 작게 시작해도 된다. 운영 중 새 모듈이 생기면 AI에게 이렇게 요청한다.

> 알림 기능을 기존 모듈에 억지로 넣지 말고 새 모듈로 추가할지 검토해줘. 기존 모듈과의 인터페이스·영향·작업 순서를 정리한 뒤, 내가 승인하면 정본에 추가해줘.

모듈마다 진행 상태가 다를 수 있다. AI에게 “상담 관리만 구현 준비가 되었고 알림은 나중에 할 거야”라고 말하면, 모듈별 계획과 상태를 분리해 관리해야 한다.

## 3. 운영 맥락: 기술보다 먼저 현실 조건을 확인한다

기술 스택을 고르기 전에 다음을 대화로 확인한다. 정확한 답을 모르면 AI가 질문 목록을 만들어 고객·인프라 담당자에게 확인할 수 있게 한다.

> 구현 전에 운영 조건을 정리하고 싶어. 배포 위치, 로그인·개인정보, 데이터베이스, 예상 사용량, 장애 허용 범위, 백업·복구, 외부 연동을 인터뷰해줘. 아직 모르는 것은 결정하지 말고 누가 언제 확인해야 하는지 정리해줘.

이 단계는 “클라우드로 할까?” 같은 한 줄 선택보다 넓다. 사용자 수, 업무 시간, 개인정보, 다중 인스턴스 여부, 데이터 손실 허용 범위, 장애 시 수동 업무 방식이 기술과 비용을 바꾼다. AI는 위험을 발견해도 과장하지 말고, 영향을 설명하고 필요한 선택만 요청해야 한다.

## 4. 기술 선택: AI의 추천을 결정으로 바꾼다

먼저 **아키텍처**와 **기술 스택**을 구분한다. 아키텍처는 모듈 경계, 데이터 소유권, 통신 방식, 배포·장애 대응처럼 시스템이 작동하는 구조다. 기술 스택은 그 구조를 구현하는 언어·프레임워크·DBMS·클라우드 도구의 조합이다. 같은 아키텍처도 여러 스택으로 구현할 수 있으므로, 프레임워크 이름부터 정하지 않는다.

### 자주 쓰는 아키텍처를 비교하는 법

아래는 서로 배타적인 제품 목록이 아니다. 예를 들어 **모듈형 모놀리스**를 기본 구조로 삼고, 내부는 **계층형 구조**로 만들며, 알림은 **이벤트 기반**으로 분리할 수 있다.

| 구조 | 주로 잘 맞는 분야·상황 | 장점 | 주의할 점 |
|---|---|---|---|
| 모듈형 모놀리스 | 사내 업무 시스템, 초기·중간 규모 B2B 서비스, 한 팀이 빠르게 검증할 제품 | 한 번의 배포와 단순한 운영, 한 DB 트랜잭션 처리, 코드 안의 모듈 경계를 명확히 관리하기 좋다 | 경계를 지키지 않으면 큰 덩어리가 되고, 일부 기능만 독립 확장·배포하기 어렵다 |
| 마이크로서비스 | 독립된 업무 도메인이 많고 여러 팀이 각자 출시·확장해야 하는 대규모 플랫폼 | 서비스별 배포·확장·장애 격리가 가능하고 소유 팀을 분명히 할 수 있다 | 서비스 간 통신, 분산 데이터 일관성, 관측성, CI/CD, 장애 분석 비용이 크게 늘어난다. 작은 팀의 첫 선택으로는 과할 수 있다 |
| 계층형(프레젠테이션·응용·도메인·데이터) | 전통적인 업무·거래 시스템, 규칙과 데이터 처리가 많은 백엔드 | 역할이 명확해 검토·테스트·온보딩이 쉽고, 모듈형 모놀리스의 내부 구조로 쓰기 좋다 | 모든 요청이 불필요하게 많은 층을 지나거나, 공통 계층이 업무 규칙을 독점하면 변경이 느려질 수 있다 |
| 이벤트 기반 | 알림, 주문·정산 후속 처리, 외부 연동, 높은 비동기 처리량이 필요한 시스템 | 생산자와 소비자를 느슨하게 연결하고, 일시적 부하를 흡수하며 후속 처리를 분리할 수 있다 | 즉시 일관성이 아닐 수 있고 중복·순서 역전·재시도·실패 추적을 설계해야 한다. 보통 전체 구조의 보완 수단으로 사용한다 |
| 서버리스·관리형 백엔드 | 트래픽 변동이 크거나, 짧은 API·이벤트 작업을 소규모로 빠르게 시작할 때 | 서버 운영 부담과 초기 인프라 구성이 줄고 수요에 따라 확장하기 쉽다 | 실행 시간·연결·디버깅 제약, 관측성·테스트 난이도, 특정 클라우드 종속과 비용 예측을 함께 검토해야 한다 |

일반적인 신규 업무 시스템이라면, 명확한 독립 배포·확장 근거가 나오기 전에는 **모듈형 모놀리스 + 필요한 곳에 계층형 구조**를 출발점으로 검토하는 것이 보통 가역적이다. 이후 알림·연동처럼 비동기성이 분명한 영역만 이벤트 기반으로 보완한다. 이것은 자동 결정이 아니라, 사용량·팀 구성·보안·통합·가용성 조건을 확인한 뒤 AI가 제시할 수 있는 기본 추천이다.

다음과 같이 요청하면 AI가 현재 시스템에 맞게 추천해야 한다.

> 지금까지 확인한 사용자 수, 업무 경계, 외부 연동, 데이터 일관성, 팀 규모, 배포 빈도와 운영 역량을 기준으로 모듈형 모놀리스·마이크로서비스·이벤트 기반·서버리스의 적합성을 비교해줘. 추천 구조와 보완 구조를 구분하고, 추천하지 않는 대안의 이유·위험·나중에 전환할 조건도 알려줘. 근거가 부족하면 결론을 내리지 말고 질문이나 짧은 검증 실험을 제안해줘.

### 기술 스택을 고르는 대화

아키텍처 후보가 좁혀진 뒤 기술을 이미 선호해도 대안을 비교해 달라고 요청하는 편이 좋다.

> 운영 조건과 요구사항을 기준으로 기술 스택 대안을 2~3개 비교해줘. 현재 방식을 유지하는 선택도 포함하고, 비용·개발 속도·운영 난이도·보안·성능·팀 역량·되돌리기 쉬운 정도를 비교해 추천해줘. 내가 선택하기 전에는 확정하지 마.

AI는 “이 프레임워크가 유행한다”가 아니라 선택한 아키텍처를 구현할 수 있는 **스택 프로필**부터 설명해야 한다. 예를 들면 다음과 같다.

| 시스템 성격 | 검토할 스택 방향 | 함께 확인할 것 |
|---|---|---|
| 화면·업무 규칙·관계형 데이터가 중심인 B2B 시스템 | 프런트엔드와 API, 관계형 DB, 인증·권한, 관리형 배포를 한 운영 모델로 묶는 조합 | 팀이 주 언어를 하나로 통일할지, 기존 조직 표준·DBMS·보안 제품과 맞는지 |
| 기존 기업 플랫폼·복잡한 거래 규칙이 중심인 시스템 | 조직의 검증된 서버 플랫폼과 관계형 DB를 우선하고, 필요한 웹 UI를 결합하는 조합 | 기존 운영·보안·모니터링 체계 재사용, 장기 지원, 통합·배치 요구 |
| AI·데이터 처리·실험이 핵심인 시스템 | API 계층과 비동기 작업자, 모델·데이터 처리 환경을 분리하는 조합 | 데이터 보호, 모델 호출 비용·지연, 재현성, 작업 큐·관측성, 제품 기능과 실험 코드의 경계 |
| 모바일·외부 사용자·실시간 상호작용이 중심인 시스템 | 클라이언트, API/BFF, 인증, 푸시·실시간 통신을 분리해 검토하는 조합 | 기기·네트워크 차이, 오프라인·동기화, 개인정보, 앱 배포·장애 대응 |

구체적인 언어·프레임워크·버전·클라우드 상품은 지원 수명, 보안 공지, 라이선스, 조직 표준이 바뀔 수 있으므로 **결정하는 시점에** 확인한다. AI에게 최신성 확인이 필요하면 공식 문서와 조직 정책을 근거로 검증해 달라고 요청하고, 비교표·선택·재검토 조건을 ADR로 남기게 한다.

AI의 답을 볼 때는 “가장 최신인가?”보다 다음을 확인한다.

- 우리 사용량과 운영 인력에서 감당할 수 있는가?
- 데이터·보안·통합 제약을 만족하는가?
- 나중에 변경할 때 어떤 비용이 생기는가?
- 선택하지 않은 대안은 왜 제외했는가?

사람이 선택하면 AI는 선택 이유, 예상되는 단점, 재검토 조건과 롤백 방향을 기록한다. 이 기록이 나중에 다른 AI나 개발자가 같은 결론을 이해하는 근거가 된다.

## 5. UI와 개발 공통 기반: 기능을 만들기 전에 함께 합의한다

UI가 있는 제품은 첫 화면을 바로 코딩하기보다, 대표 사용자 여정 하나를 골라 함께 설계한다.

> 상담 등록부터 담당자의 오늘 할 일 확인까지를 대표 사용자 여정으로 잡자. 먼저 사용자가 무엇을 보고·입력하고·확인하는지 질문해줘. 그 뒤 레이아웃과 상호작용 대안을 제안하고, 공통으로 쓸 컴포넌트 후보를 구분해줘. 내가 승인한 내용만 UI 기준선과 화면 명세로 기록해줘.

함께 정할 내용은 다음과 같다.

- 전체 레이아웃, 메뉴, 목록·상세·입력의 기본 패턴
- 로딩·빈 화면·오류·권한 없음 상태에서 사용자에게 보일 내용
- 색·문구보다 먼저 정할 접근성, 권한, 저장 실패와 복구 방식
- 여러 화면에서 반복될 입력 폼, 검색, 표, 알림, 확인 창 같은 공통 컴포넌트
- 검토용 목업과 실제 구현 화면의 구분

AI가 목업을 만들면 **“이것은 합의를 돕는 목업이며 실제 구현 증거가 아니다”**라는 점을 유지한다. 구현이 끝난 뒤의 사용자 매뉴얼과 출시 판단에는 실제 환경·커밋과 연결된 화면 캡처가 필요하다.

UI가 없는 백엔드·배치 프로젝트라면 “이 프로젝트는 UI가 적용 대상이 아니다. 대신 API 계약, 오류 형식, 관측성과 운영 절차를 공통 기반으로 합의하자”라고 요청하면 된다.

## 6. 구현: 큰 기능이 아니라 검증 가능한 한 조각씩

이제 AI에게 구현을 요청한다. 좋은 요청은 기능 이름만 던지지 않고 대상 모듈, 사용자 결과, 제외 범위와 확인 방법을 함께 말한다.

> 상담 관리 모듈에서 “상담을 등록하면 담당자의 오늘 할 일에 표시된다”는 가장 작은 흐름부터 구현해줘. 먼저 인수 기준·테스트 전략·영향받는 인터페이스·실패 시 동작을 제안해줘. 승인된 UI·개발 표준을 재사용하고, 구현·테스트·운영 영향·사용자 안내를 같은 변경에서 갱신해줘.

AI는 보통 다음 순서로 일해야 한다.

1. 연결된 요구사항과 이미 합의한 표준·UI 패턴·인터페이스를 확인한다.
2. 가장 작은 관찰 가능한 동작과 실패 조건을 테스트로 정의한다.
3. 코드와 필요한 데이터 변경·설정·관측성·문서를 함께 바꾼다.
4. 단위·통합·사용자 흐름·회귀 중 필요한 검증을 실행한다.
5. 실행 명령과 결과를 증거로 연결하고, 변경된 사실을 정본과 생성 문서에 반영한다.

중간에 요구가 바뀌면 “그냥 고쳐줘” 대신 다음처럼 말한다.

> 기존 합의와 비교해서 이 변경이 요구사항·UI·데이터·운영·일정에 미치는 영향을 먼저 보여줘. 지금 반영, 다음 단계로 미루기, 반영하지 않기 세 선택지를 비교하고 내가 고른 뒤에 변경을 시작해줘.

## 7. 검토와 출시: “테스트 통과”보다 넓게 확인한다

출시 준비를 요청할 때는 다음처럼 말한다.

> 이번 변경을 출시 후보로 검토해줘. 요구사항·테스트·보안·데이터 변경·복구 방법·운영 관측성·사용자 매뉴얼·남은 위험을 점검하고, 출시를 막는 것과 내가 결정해야 할 것을 구분해줘. 준비되었다고 단정하지 말고 근거와 미결사항을 보여줘.

AI는 다음을 확인해야 한다.

- 요구사항별 테스트와 검증 증거가 있는가
- 운영 중 실패했을 때 중단·복구·롤백할 방법이 있는가
- 사용자 가이드가 실제 구현과 일치하는가
- 보안, 개인정보, 데이터 이전, 권한과 외부 연동에 남은 위험이 있는가
- 변경 규모에 맞는 독립 검토와 사람이 해야 할 승인이 있는가

특히 큰 변경(C2·C3)은 AI가 구현한 뒤 별도 AI 검토 또는 팀의 다른 사람이 검토해야 한다. “AI가 검토도 했으니 괜찮다”가 아니라, 구현 흐름과 분리된 관점에서 무엇을 찾아냈는지 기록하는 것이 목적이다.

## 8. 운영과 다음 대화

출시 후에는 “끝났다” 대신 성과와 문제를 확인한다.

> 출시 후 2주 동안 무엇을 관찰해야 목표 달성 여부를 알 수 있을지 정리해줘. 사용자 피드백, 오류, 처리 시간, 운영 부담을 어떻게 기록하고 어떤 조건에서 다음 변경을 시작할지 제안해줘.

새 기능·결함·운영 개선은 이전 기록을 지우지 않고 새 변경으로 이어 간다. AI에게 “지난 결정과 현재 운영 증거를 기준으로 이 요청의 영향부터 분석해줘”라고 말하면 같은 맥락을 이어가기 쉽다.

| 개발 시작 | “구현 전에 범위·인수 기준·테스트·롤백을 확인하고, 준비되지 않은 게이트가 있으면 알려줘.” |
| 변경 요청 | “기존 합의 대비 영향과 지금/나중/하지 않음 선택지를 먼저 보여줘.” |
| 검토 요청 | “내가 놓쳤을 반대 관점과 실패 시나리오를 찾아줘. 발견사항을 숨기지 말아줘.” |
| 문서 최신화 | “합의한 변경을 정본에 반영하고, 필요한 문서를 생성·검증해줘.” |
| 세션 재개·병합 확인 | “오늘의 짧은 현황 브리핑과 병합 알림을 먼저 보여줘. 대기 중인 재검토는 담당자 없이 목록으로 알려줘.” |

## AI가 하지 말아야 할 일

AI가 다음처럼 행동하면 멈추고 바로잡아 달라고 요청한다.

- 확인하지 않은 가정을 사실처럼 확정한다.
- 고객의 선택이 필요한 기술·범위·비용 결정을 대신 내린다.
- 생성 문서를 직접 고쳐 정본과 다르게 만든다.
- 테스트나 검토 근거 없이 “완료” 또는 “출시 가능”이라고 말한다.
- 검토용 목업을 실제 화면이나 출시 증거처럼 취급한다.
- 기존 합의·사용자 영향·롤백을 보지 않고 대규모 변경을 바로 구현한다.

이때는 간단히 “그 결정의 근거와 대안을 보여줘”, “확인되지 않은 부분을 미결사항으로 되돌려줘”, “정본과 검증 결과를 갱신한 뒤 다시 보고해줘”라고 요청하면 된다.

## 명령어는 언제 필요한가

대부분은 AI에게 자연어로 요청하면 된다. AI가 상태 확인, 생성, 검증 명령을 적절한 시점에 실행한다. 다만 아래 명령은 사용자가 결과를 직접 보고 싶을 때 유용하다.

```powershell
python .ai/tools/aidd.py status --level executive
python .ai/tools/aidd.py status --level module --module MOD-ID
python .ai/tools/aidd.py generate
python .ai/tools/aidd.py validate
python .ai/tools/aidd.py release-check --release REL-ID
```

명령이 실패했을 때는 출력 전체를 AI에게 보여 주고 “원인과 안전한 다음 조치를 설명해줘”라고 말한다. 오류를 없애기 위해 정본·증거·승인 상태를 억지로 바꾸지 않는 것이 중요하다.

## 첫 주의 현실적인 목표

첫 주에 완벽한 전체 설계를 끝내려 하지 않아도 된다. 다음만 합의해도 좋은 출발이다.

1. 해결할 문제와 성공 기준 하나
2. 첫 사용자 여정 하나
3. 이번에 하지 않을 범위
4. 운영 조건에서 아직 모르는 항목과 확인 담당자
5. 첫 모듈과 가장 작은 구현 조각 하나

그 뒤 AI와 매일 “지금까지 확정된 것, 아직 모르는 것, 오늘 검증할 가장 작은 다음 조각은 무엇인가?”를 확인하며 진행하면 AIDD 기록은 부담이 아니라 프로젝트 기억이 된다.
