## 요구사항 상세

### REQ-009 — 모듈 단위 수행

프레임워크는 공통 인터페이스와 릴리스 의존성을 보존하면서 모듈을 독립적으로 계획·개발·추적하고, 모듈별 정본 조각과 생성 명세로 분석할 수 있어야 한다.

- 우선순위/상태: `필수` / `정의됨`
- 담당: 아키텍처
- 연결 모듈: MOD-ARCH, MOD-STATUS
- 검증: TC-001
- 출처: USER-2026-09-17; USER-2026-09-18

인수 기준:

- 각 모듈에 범위, 상태, 의존성과 요구사항 링크가 있다
- 상태를 단일 모듈로 좁힐 수 있다
- 요구사항은 하나의 모듈 정본 조각에만 저장되고 다중 모듈 영향은 ID 링크로 유지된다
- 신규 모듈은 기존 모듈의 요구사항을 다시 쓰지 않고 카탈로그·빈 정본 조각·생성 명세를 추가할 수 있다

- 기존 시스템 충돌을 불일치로 기록한다

### REQ-011 — UI와 개발 표준 우선

- 우선순위/상태: `필수` / `정의됨`
- 담당: 아키텍처
- 연결 모듈: MOD-ARCH, MOD-DELIVERY
- 검증: TC-007, TC-008
- 출처: USER-2026-09-17

인수 기준:

- 기술 선택 전에 품질 속성과 제약이 정의된다
- 현행 유지안을 포함한 대안 비교와 ADR을 거쳐 기술 기준선을 승인한다
- 기능 개발 게이트에 UI·개발 기반 준비도가 포함된다
- 예외에는 기록된 결정이 필요하다

### REQ-020 — 배포·운영 환경의 조기 확인

AI는 기술 스택과 상세 설계를 확정하기 전에 고객에게 배포 위치, 실행 플랫폼, DBMS 제약, 단일·다중 인스턴스, 자동 확장, 워크로드, 가용성·복구, 상태 관리, 보안과 운영 책임을 확인해야 한다.

- 우선순위/상태: `필수` / `구현됨`
- 담당: 제품·아키텍처·인프라
- 연결 모듈: MOD-DISC, MOD-ARCH, MOD-STATUS
- 검증: TC-010
- 출처: USER-2026-09-18

인수 기준:

- DG-001이 TG-001보다 먼저 수행된다
- 설계를 바꾸는 환경 범주와 미결 결정이 배포 프로필에 기록된다
- 미정 사항에는 담당자·기한·영향이 있으며 중대한 항목은 차단된다

AI는 설계 단계부터 트랜잭션 경계, 프록시 AOP, 스레드 전환, 다중 인스턴스 경쟁, 재시도·중복, 스케줄 작업, 자원 병목과 장애 전파 위험을 식별하고 통제와 검증 시나리오를 정의해야 한다.

- 우선순위/상태: `필수` / `구현됨`
- 담당: 아키텍처·품질 보증
- 연결 모듈: MOD-ARCH, MOD-QA, MOD-DELIVERY
- 검증: TC-011
- 출처: USER-2026-09-18

인수 기준:

- 핵심 업무에 측정 가능한 동시성 불변 조건이 있다
- 적용되는 위험 패턴마다 설계 통제와 부정·경쟁·부하·장애 검증이 연결된다
- 로컬 락이나 스레드 컨텍스트를 다중 인스턴스 보장으로 오인하지 않는다

### REQ-031 — 프로젝트별 개발 기반 정본

프레임워크는 기술 스택과 분리된 메타 구조로 개발 표준, 골든 패스와 기한 있는 예외를 관리하고 프로젝트가 선택한 기술 기준선에 맞는 규칙과 실행 검증을 연결해야 한다.

- 우선순위/상태: `필수` / `구현됨`
- 담당: 아키텍처·개발·품질 보증
- 연결 모듈: MOD-ARCH, MOD-DOC, MOD-DELIVERY, MOD-QA
- 검증: TC-024
- 출처: USER-2026-09-18

인수 기준:

- STD, GPH, EXC 레코드가 안정 ID와 기술 기준선, 모듈, 요구사항, 검증을 연결한다
- 계약형과 정책형 표준을 구분하고 기술 스택 구체 규칙은 프로젝트 기준선에서 작성한다
- 예외는 승인, 담당자, 만료일과 보완 통제 없이는 유효하지 않다
