# AIDD 요구 발굴

모듈별 정본 조회·전문 명령·게이트는 [v2 통합 계약](../../../.ai/spec/specialty-integration.md)을 적용한다. 현재 owner/CHG 범위를 먼저 고르고 공통 정의를 참조한다. 쓰기 명령에는 고유 operation을 사용하며 사용자 결정·현재 유효성·실제 실행을 구분한다.

owned-records-v2에서는 `.ai/spec/owned-records-v2.md`의 요구·검토·기준선 계약을 먼저 읽는다. CHG 전체 범위가 설계 진입 단위이며 각 요구의 현재 사용자 수용과 개별/관련 규칙/종단 간 검토가 필요하다. `review-record`로 제시 해시·입력 digest·부분 응답을 기록하고 현재 accepted 대상만 OI/DRQ와 함께 종료한다. 구형 전역 workboard를 직접 쓰지 않는다. 분석 목록과 상세 설계는 구분하며 미정은 임의로 채우지 않는다.

1. 결정해야 할 사항, 고객, 영향받는 사용자, 문제 증거, 기대 성과, 성공 지표, 기한, 제약과 명시적인 제외 범위를 확인한다.
   v2에서는 `.ai/spec/business-discovery.md`를 읽고 SYS 개요·경계, CAP 핵심 업무, ACT 역할/목표, UC 시나리오, BPR 업무 인계·분기·예외·데이터 상태를 먼저 정리한다. UC와 BPR는 서로 보완하며 초안 작성 순서를 강제하지 않는다. CAP를 상세 FEAT로, ACT를 AIDD 수행팀 명부로 혼동하지 않는다. 공통 정의는 참조하고 모듈/주기 범위를 명시한다.
   역할 정의 직후 [접속·인증·접근 계약](../../../.ai/spec/system-access.md)을 읽고 공개/로그인 선행/혼합형, 최초·인증 후 화면, 인증 방식·만료, 권한 확인·강제·부여/회수, 기능·데이터 범위와 거부 동작을 POL(kind=system_access)에 정리한다. ACT/UC.access로 규칙을 참조하고 discovery.access_policies에 등록한다. 모든 시스템에 로그인을 강제하거나 역할마다 공통 로그인 절차를 복제하지 않는다. 비접속 수작업은 사유를 남기며 API/배치에는 가짜 화면을 만들지 않는다. 정책 intent 사용자 검토가 없으면 선행 분석 완료로, 사용 규칙별 요구 출처가 없으면 요구 확정으로 보고하지 않는다.
2. 제품 의도·목적·성과 기준을 합의한 직후 `BEN-TRIAGE`를 수행한다. 이 판단은 모든 프로젝트에 필수지만, 외부 벤치마킹 조사가 항상 필수인 것은 아니다. 유사 사례가 목표·범위·사용자 흐름·운영 방식·기술 선택을 더 잘 결정하게 하는지, 조사 비용보다 잘못된 선택 위험이 큰지 고객과 판단해 필요/불필요와 이유를 ADR 또는 OI에 기록한다.
3. 조사가 필요하면 먼저 고객과 조사 질문, 비교 대상·제외 대상, 평가 기준, 출처 품질, 예산·기한과 조사하지 않을 범위를 합의한다. 합의 전에는 넓은 시장 조사나 제품 추천을 사실처럼 수행하지 않는다. 조사 결과는 `research-note`에 출처·접근일·우리 환경과의 차이·한계와 함께 기록한다.
4. 업무 목적·역할·흐름을 먼저 이해하고, 설계에 영향을 주는 배포 제약을 필요한 시점에 확인한다. 신규 시스템·모듈 또는 중대한 변경이면 온프레미스·클라우드, 실행 플랫폼, DBMS, 단일·다중 인스턴스, 자동 확장, 워크로드, SLO·RTO·RPO, 상태·세션·캐시·스케줄과 운영 책임을 질문해 배포 프로필을 만든다. 기술 질문으로 업무 분석을 대체하지 않는다. 아직 결정할 수 없는 값은 가정으로 숨기지 않고 결정 조건·차단 영향이 있는 미결사항으로 기록한다. 사람 배정과 일정은 프로젝트 운영 도구에서 관리한다.
5. 확인한 미결 결정은 먼저 영향 소유자의 OI에 기록하고 관련 REQ·ADR·CHG 등을 링크한다. 그중 가치가 높은 질문을 한 번에 하나의 일관된 묶음으로 고르고, 고객이 용어를 모를 수 있으면 구체적인 선택지를 제공한다. 질문 전에는 `aidd-decision-management`로 DRQ를 저장한다. 기존 미응답 묶음이 있어도 새 작업의 별도 결정을 새 OI와 묶음으로 보존할 수 있으며 상태·재개 시 우선순위에 따라 선택한다. 요구분석 중 새롭거나 모호한 업무·제품 용어가 나오면 임의로 확정하지 않고 `aidd-terminology` 스킬로 명확화와 프로젝트의 오프라인 결정 흐름을 수행한다.
6. 사실, 고객 결정, 가정, 가설과 미결사항을 구분한다. 관리 대상에는 안정적인 ID를 부여한다.
7. 요구사항을 관찰 가능한 동작으로 표현하고 인수 기준, 부정 사례, 우선순위, 영향 모듈과 검증 링크를 기록한다. 담당자와 일정은 프로젝트 운영에서 정한다.
   v2 요구는 derived_from으로 UC/BPR의 안정 단계 key 또는 SYS·정책·외부 계약 등 출처를 연결한다. 역할별 목표, 정상·대안·예외 흐름, 시스템 담당 단계가 빠졌는지 확인하고 제외/보류에는 사유를 남긴다. NFR에 가짜 UC나 메뉴를 만들지 않는다. intent와 business_flow는 현재 사용자 검토로 기록하고 discovery-check를 확인한다. 미충족이면 초안을 계속 보완하되 요구 확정·설계 진입으로 보고하지 않는다.
8. 오용, 실패, 동시성, 중복·재시도·순서 역전, 부분 성공, 오래된 데이터, 권한, 개인정보, 접근성, 운영성, 마이그레이션과 롤백 관점에서 주요 요구사항을 공격적으로 검토한다. 반드시 지켜야 할 업무 불변 조건과 최종 일관성 허용 범위를 분명히 한다.
9. 트레이드오프에서는 성과 적합성, 비용, 기간, 복잡성, 보안·개인정보, 운영, 종속성, 불확실성과 가역성으로 실행 가능한 대안을 비교한다. 벤치마킹 관측을 우리 환경의 사실로 일반화하지 않고, 추천에는 적용 조건·한계·배제 이유를 붙인다. 추천을 제시하되 고객의 선택은 별도로 기록한다.
10. 고객이 수용·보류·제외를 결정한 내용만 ADR·REQ·OI에 반영하고 DRQ를 해결·보류·철회 상태로 갱신한다. 확인된 검증 결과만 EVD로 기록하며 결정되지 않은 내용을 서술문 속에 숨기지 않는다.

인터뷰와 반대 검토 질문은 [references/interview-playbook.md](references/interview-playbook.md)를 읽는다. 벤치마킹 필요성 판단·조사 범위·비교·추천·결정 반영은 [references/benchmarking.md](references/benchmarking.md)를 따른다. 질문을 한꺼번에 쏟아내지 말고 같은 문서의 질문 배치와 결정 비용 규칙을 적용한다.
