# 적합성 기준

AIDD 적합성 검증은 사용자가 요청한 요건과 스펙이 규칙·스킬·훅·도구에 실제로 구현되었는지를 빠르게 확인하기 위한 것이다. 검증 절차 자체를 제품 요구사항보다 크게 만들지 않는다.

## 기본 원칙

- 정본은 Kit의 `.ai/spec/`, `.ai/manifests/`, `AGENTS.md`와 프로젝트의 현재 `project/.aidd/ssot/`다. fixture, 생성물과 과거 검증 기록은 현재 정본이 아니다.
- 구조 검사만으로 구현 충실성을 단정하지 않는다. 요청 범위의 대표 정상·실패 입력으로 관찰 가능한 동작을 확인한다.
- 보안·권한·신원·서명 검사는 정본 요건에 명시되어 있고 검증 범위에 포함되거나 사용자가 별도로 요청한 경우에만 수행한다.
- 일상 검증은 빠른 구조 검사와 변경 영역 테스트로 끝낸다. 전체 fixture, 전체 테스트, export·new-project 검증은 영향을 받는 경우에만 실행한다.
- 검증 결과 때문에 별도 evidence 파일, 반복 재검토, 승인 게이트를 자동으로 만들지 않는다.

## Kit 원본

Kit 원본은 다음 경계를 만족해야 한다.

- `.aidd-role.json`은 `kit-source`이고 루트에 제품용 `project/`가 없다.
- portable 명세·스킬·훅·도구는 `.ai/`, Kit 관리 전용 파일은 `.aidd-kit-dev/`에 격리된다.
- export는 하나의 허용 목록으로 directory와 ZIP을 조립하고 `.aidd-kit-dev/`와 관리 전용 스킬을 포함하지 않는다.
- provider 스킬 복사본은 portable 스킬과 같고 provider 훅은 공통 훅 계약의 이벤트별 동작에 연결된다.
- 실행 도구와 훅은 Node.js 22 이상과 표준 라이브러리만 사용하며 훅 입력을 UTF-8로 처리한다.
- 훅 격리는 1순위 불변 조건이다. 각 provider·이벤트·책임은 전용 `.ai/hooks/*.mjs` 프로세스를 사용하고 런타임 훅 사이의 공통 dispatcher·공통 라이브러리·상호 import·상호 호출을 금지한다. 한 훅 변경은 다른 훅의 등록 위치·명령·승인 해시를 바꾸지 않는다.
- `new-project`는 `product-workspace` 역할과 유효한 `project/.aidd/ssot/`를 만든다.

## 훅

provider 훅은 세션 요약, 생성물 직접 수정 보호, 용어 정본 변경 뒤의 현행화와 프로젝트 루트의 일자별 append-only 대화 로그를 제공한다. 배선 self-test는 런타임 훅이 아니라 독립된 수동 검증 명령이다. 대화 기록의 `UserPromptSubmit`은 다음 응답에 속한 사용자 원문과 로컬 제출 시각을 임시 보관하며 최종 파일에는 쓰지 않는다. Codex는 `workspace + provider + session_id` 큐에 각 원문의 `turn_id`를 함께 누적해 처리 중 추가 질의나 대체 턴이 앞선 질의를 덮어쓰지 않게 하고, Claude도 같은 키의 큐에 제출 시각 순으로 누적한다. `Stop`은 누적된 사용자 원문과 최종 AI 응답을 `## [{시각}] Codex|Claude`, `### USER`, 선택적인 `### AI PROGRESS (Codex|Claude)`, `### AI (Codex|Claude)`, `---` 형식의 한 블록으로 결합하고, 동시 세션끼리 블록이 섞이지 않도록 잠금 아래 현재 프로젝트 루트의 `chat-history/YYYY-MM/raw/YYYY-MM-DD.md`에 한 번에 추가한다. Claude는 일자 파일이 회전 기준 바이트를 넘으면 첫 파일 이름을 그대로 두고 `YYYY-MM-DD-2.md`부터 번호를 붙인 다음 파일에 이어 쓰며, 블록 하나가 단독으로 기준을 넘어도 빈 파일에 그대로 기록해 누락시키지 않는다. Codex `Stop`은 `last_assistant_message`를 최종 응답으로 사용하고, `transcript_path`에서 큐에 포함된 턴 구간의 `role=assistant`, `phase=commentary` 메시지만 사용자에게 표시된 진행 내용으로 최선 노력으로 읽는다. 숨겨진 reasoning, 도구 호출·출력, 소스 diff와 transcript의 final_answer 복사본은 기록하지 않는다. Codex transcript 형식은 안정된 훅 인터페이스가 아니므로 파싱할 수 없으면 진행 섹션만 생략하고 누적 질의와 최종 응답은 계속 기록한다. 대응하는 사용자 원문과 최종 응답이 모두 있을 때만 기록하고 성공 뒤 임시 큐를 제거한다. Claude Code의 `Stop` 입력에는 응답 본문 필드가 없으므로 Claude `Stop`은 같은 입력의 `transcript_path`에서 큐의 첫 질의 시각 이후 assistant 텍스트 블록만 읽어 마지막 블록을 최종 응답으로, 앞선 블록을 사용자에게 표시된 진행 메시지로 기록한다. thinking, 도구 호출·출력, 소스 diff와 하위 에이전트·meta 레코드는 기록하지 않는다. Claude transcript 형식도 안정된 훅 인터페이스가 아니므로 읽을 수 없으면 진행 섹션을 생략하고 `Stop` 입력의 메시지 필드로 최종 응답을 기록한다. Claude 어댑터는 생성물 보호에서 도구 입력의 경로 필드를 대상으로 판정하고 경로 구분자를 정규화하므로 문서 본문이 생성물 경로를 언급하는 것만으로는 차단하지 않으며, exit 0의 stderr를 모델이 볼 수 없는 provider 제약 때문에 `PostToolUse` 안내를 차단 없는 exit 2로 전달한다. Codex `SessionStart`의 전용 안내 훅은 실행 표면에 관계없이 CLI `/hooks`에서 현재 작업공간 훅을 검토·신뢰했는지 확인하라는 `systemMessage`와 모델용 `additionalContext`를 함께 반환한다. 새 `startup`의 컨텍스트는 첫 사용자 요청에 대한 최종 답변(`final_answer`) 첫 줄에 같은 경고를 표시하게 한다. 접히는 진행 메시지(`commentary`)에 표시한 것은 충족으로 보지 않으며 commentary에 이미 표시했더라도 final_answer에서 다시 표시한다. 이 최종 답변 지시는 세션당 한 번만 적용하며, 이전 assistant의 final_answer에 경고가 있으면 이후 응답에서 반복하지 않는다. resume·clear·compact는 최종 답변 표시를 다시 요구하지 않는다. Claude에는 이 안내를 연결하지 않는다. 이 안내는 Codex 자체 훅 신뢰 기능을 사용하며 AIDD 승인 상태를 별도로 저장하거나 사용자의 답을 기다리거나 작업을 차단하지 않는다. 훅은 AIDD 자체 승인 상태, Git 서명, 외부 trust-root, 일반 shell 권한 검사를 강제하지 않는다. 훅 실패는 해당 자동화 실패만 간결하게 알리고 별도의 정책 승인을 만들지 않는다. Claude 셸 보호는 생성물 경로가 변경 명령이나 리다이렉션의 대상일 때만 차단하므로 읽기와 문서화는 막지 않으며, 인터프리터 인수 안에 숨긴 쓰기는 판정 대상이 아니다.

## 파생 문서

`generate`는 정본의 구조화된 내용을 결정적으로 파생하며 확인되지 않은 사실을 만들지 않는다. 파생 문서 검증은 현재 정본으로 임시 위치에 다시 생성한 결과와 비교해 다음을 모두 확인한다.

- 기대 파일이 모두 존재한다.
- 각 파일의 전체 내용이 현재 renderer 결과와 같다.
- 더 이상 생성 대상이 아닌 파일이 남아 있지 않다.

## 결정 요청 연속성

`workboard.decision_requests`가 없으면 이전 프로젝트 호환을 위해 빈 배열로 취급한다. 존재하는 DRQ는 안정 ID, 단계, 제목, 질문, 열린 OI와 대상 정본 ID, 미응답 영향, 차단 여부, 양의 정수 우선순위, 상태와 순서를 가진다. `draft`, `awaiting_decision`, `deferred`는 적어도 하나의 열린 OI를, `resolved`는 적어도 하나의 닫힌 OI를 참조해야 한다. `awaiting_decision`에는 질문 시각과 답변 주체가 있고, 같은 `asked_at`의 각 묶음은 1~3건과 1부터 이어지는 고유 순서를 가져야 한다. 서로 다른 시점의 미응답 묶음은 함께 존재할 수 있다. `resolved`에는 결정 내용·결정 주체·결정 시각이, `deferred`에는 재검토 조건이, `withdrawn`에는 철회 이유가 있다. 알 수 없는 대상 ID와 불완전한 상태 전이는 검증 오류다.

`status --level executive`는 OI와 DRQ를 구분하고 활성 변경, 차단 미결사항, 답변 대기 건수·묶음 수, 준비·보류 결정, 주요 위험, 게이트 상태와 권장 다음 작업을 요약한다. 마지막에는 차단 여부, 낮은 우선순위 번호, 오래 기다린 시각 순으로 선택한 `awaiting_decision` 질문·선택지·권장안 묶음을 표시한다. `detail`은 나머지 미결사항·결정 대기열·위험·게이트·다음 작업을 펼친다. `bootstrap`은 단계 표시는 유지하되 이미 채워진 정본을 고정 안내 문구로 숨기지 않는다. 차단 DRQ는 관련 변경의 개발 시작과 릴리스 준비를 차단한다. 독립 작업은 기존 DRQ를 해결하지 않고 계속할 수 있고 별도 결정이 필요하면 새 묶음을 추가할 수 있다.
- 정본에 있는 요구사항·결정·절차·추적성 정보가 해당 독자용 문서에 누락되지 않는다.
- 독자별 DLP 필터가 명시된 경우 그 공개 경계를 지킨다.

공통·프로젝트 용어집도 같은 생성·비교 규칙을 따른다. 프로젝트 용어에는 승인 대기 상태를 두지 않으며, 프로젝트의 오프라인 결정 뒤 `term-apply`가 현재 `TRM`과 결정 주체·시각·전후 값·영향을 담은 `TCH`, 파생 문서 생성과 검증을 함께 완료한다. 현재 용어는 통제된 개념 유형, 프로젝트 분류, 정의와 적용 범위를 가져야 하며 예시·관련 용어·혼동 구분이 있으면 참조 대상과 판단 규칙을 검증한다. 제거되거나 이름·key·별칭이 바뀐 이전 용어가 확정 계약·문서·제품 소스에 남아 있으면 검증에 실패한다.

결정 이력은 `history/YYYY-MM/HIS-YYYYMMDD-NNN.json`에 append-only로 저장한다. ID 날짜와 발생 날짜가 같고, 유형·대상 안정 ID·결정 주체·결정·이유가 필수이며 연결 CHG와 `supersedes`는 존재해야 한다. `decision-history.md`는 현재 HIS 전체에서 결정적으로 다시 생성한다. 사람·역할·Git 신원은 이력의 유효성이나 실행 권한을 판정하는 기준이 아니다.

## 실행 수준

- 역할별 빠른 검사: 제품 작업공간은 `validate`, Kit 원본은 관리자 가이드의 `check`로 JSON과 필수 경계를 확인한다.
- 변경 영역 테스트: 해당 요건의 실제 정상·실패 동작만 확인한다.
- 영향 기반 smoke: 생성기, fixture, export, new-project 또는 provider 경계가 영향을 받을 때만 Kit 관리자 절차로 대표 흐름과 파생 문서 전체 비교를 수행한다.

사용자가 AIDD 구현 검증을 요청하면 `aidd-requirement-verification` 스킬을 사용해 이 기준을 적용한다.
