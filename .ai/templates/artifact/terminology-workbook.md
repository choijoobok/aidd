# 용어 확인 카드

이 서식은 요구분석·설계 중 AI가 새롭거나 의미가 모호한 용어를 발견했을 때 활성 팀원이 읽기 전용으로 작성하고 PM에게 한 번에 확인받기 위한 대화용 서식이다. 별도 승인 대기 문서나 제품 정본이 아니며, 오프라인 협업에서는 `term-review` 결과를 그대로 복사해 PM에게 전달한다. 확인된 결과만 `project/.aidd/ssot/terminology.json`에 반영한다.

## 언제 확인하는가

- 같은 표현을 참여자마다 다른 뜻으로 사용할 수 있다.
- 기존 공통·프로젝트 용어와 비슷하지만 범위나 책임이 다르다.
- 요구사항, 데이터, API, 화면 또는 소스 명명에 반복 사용될 개념이다.
- 정의가 달라지면 인수 기준이나 설계 경계가 달라진다.

일회성 표현, 일반적인 일상어, 이미 같은 뜻으로 정의된 별칭은 새 용어로 만들지 않는다.

## PM 확인 카드

| 항목 | 확인할 내용 |
|---|---|
| 후보 용어 | 사용자가 말한 표현과 권장 표기 |
| 영문 key | 코드·데이터·API에서 일관되게 사용할 이름 |
| 개념 유형 | `business` 업무, `product` 제품 동작·정책, `technical` 구현·운영, `external` 외부 표준·제품 어휘 |
| 분류 | 프로젝트 도메인 기준 영역. 필요하면 `상위/하위` 형식 사용 |
| 정의 | 이 용어가 무엇인지 한 문장으로 설명 |
| 적용 범위 | 언제·어디에 이 용어를 쓰는지 설명 |
| 별칭 | 같은 뜻으로 검색·해석할 표현. 문서의 권장 표기는 후보 용어 하나로 통일 |
| 사용 예 | 실제 요구사항이나 설계 문장에서 올바르게 사용한 예 |
| 관련 용어 | 의미상 함께 봐야 할 기존 `TRM` 또는 공통 `AIDD-TERM` ID |
| 혼동 구분 | 비슷한 용어, 핵심 차이, 어느 상황에서 어느 용어를 선택하는지 |
| 공개 범위 | 내부용인지 고객·최종 사용자에게도 공개할지 |

## AI 질문 예시

> 요구사항에서 “서비스 요청”이 반복되는데 기존 “고객 요청”과 같은 뜻인지, 처리 계약이 다른 별도 개념인지에 따라 API와 상태 모델이 달라집니다. 별도 용어라면 `business / 고객지원`, “고객이 지원 조직에 접수해 처리 상태를 갖는 단위”, 고객 요청과의 구분은 “접수·상태 추적 여부”로 등록해도 될까요?

PM이 확인하면 PM은 카드 내용과 승인 의사를 자신의 AI 세션에 전달한다. AI는 별도 확인을 반복하지 않고 관련 정본·문서·소스 주석 현행화, PM 신원의 `term-apply`, 파생 문서 생성과 검증까지 이어서 완료한다.
