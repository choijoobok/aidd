# AIDD AI 수행 계약

## 권한

- 고객은 제품 의도, 사업 우선순위, 위험 수용과 되돌리기 어려운 결정의 최종 책임자다.
- PM·구성원·1인 프로젝트 사용자와 AI의 공통 안내는 `.ai/docs/guides/project-team-guide.md`를 따른다. 이 수행 계약과 충돌하면 `AGENTS.md`가 우선한다.
- `project/.aidd/ssot/*.json`을 프로젝트 정본으로 취급한다. `project/docs/generated/`는 파생 산출물이므로 직접 수정하지 않는다. 제품 소스는 `project/src/` 아래에서 아키텍처에 맞게 관리한다.
- `.ai/manifests/terminology.json`의 AIDD 공통 용어는 수정·재정의하지 않는다. 업무 용어는 `project/.aidd/ssot/terminology.json`에 제안하고 `TIR` 영향 검토와 `TAP` 사용자 승인을 거친다. 승인된 영향을 정본·코드·문서에 반영한 뒤 `term-close`로 종료 이력을 남긴 경우에만 `glossary.md`와 독자별 HTML을 자동 또는 `generate`로 재생성하며 직접 수정하지 않는다.
- 대화, 커밋, 구현 기록, 테스트와 보고서에서 안정적인 산출물 ID를 사용한다.
- 코드와 정본이 다르면 불일치로 보고한다. 코드를 기준으로 요구사항을 몰래 재정의하지 않는다.
- `.aidd-kit-origin.json`은 시작 Kit의 출처만 기록한다. 원본 Kit과 자동 업그레이드·역동기화하지 않으며, 외부 개선은 문제·의도·환경·전제·구현·검증·위험 정보를 검토해 이 프로젝트의 별도 변경으로 구현한다.
- `.ai/templates/`의 조사·결정·화면·매뉴얼·런북 서식은 정본을 채우기 위한 작업 보조물이다. 서식 사본을 별도 제품 정본으로 만들지 말고 합의된 내용을 `project/.aidd/ssot/`에 기록한다. Kit 서식을 고정 포맷으로 강제하지 않으며, 착수 시 사용자와 문서 유형별 독자·필수 항목·근거·승인 기준을 `documentation.json`에서 합의한다. 새 필수 항목은 같은 문서 유형 전체에 소급 적용하고, 확인된 정본 근거가 있으면 자동 반영하며 없으면 미작성·OI로 남긴다. 프로젝트 소개·개요·목적과 의도·주요 기능은 `project.json`에 먼저 기록하고, 생성 HTML 사이트의 홈 화면으로 사용한다.

## 작업 방식

- 한글을 포함한 모든 문서와 소스 코드는 UTF-8(BOM 없음)로 읽고 쓴다. 실행 도구와 provider 훅은 Node.js 22 이상과 표준 라이브러리만 사용하며 훅 입력은 원본 바이트를 UTF-8로 해석한다.
- Codex 세션 시작 시 먼저 `node .ai/tools/aidd.mjs hook-trust-status`를 실행하고, 신뢰 레코드 유무와 무관하게 사용자에게 터미널에서 `codex -C "<현재 루트>"`를 연 뒤 `/hooks`에서 모든 AIDD 훅을 검토·신뢰하도록 안내한다. 이어 `1) 현재 세션 시작 전에 이미 모든 AIDD 훅이 승인된 상태 2) 현재 세션 시작 후 AIDD 훅을 새로 승인한 상태` 두 선택지만 한 질문으로 제시한다. 사용자는 직접 검토·승인한 사실이 참일 때 `1` 또는 `2`만 답해도 승인 사실과 시점을 함께 확인할 수 있다. 자연어 응답도 고정 문구를 요구하지 않고 의미로 처리하되 부정·모순·모호한 답변은 다시 확인한다. Windows Codex 앱에서 2번이면 현재 창의 일반 작업을 금지하고 새 앱 창에서 재시작·승인 상태를 의미상 확인한 뒤 진행한다. CLI에서는 현재 `acknowledge` 훅이 2번 답변을 실제 수신한 경우 별도 재시작 절차를 적용하지 않는다. 훅 리비전이 세션 시작 뒤 변경되면 Windows 앱은 최신 훅을 승인한 새 앱 세션에서 재개한다. CLI는 `/hooks`에서 최신 훅을 승인하고 현재 `acknowledge` 훅이 2번 답변을 실제 수신하면 현재 세션의 리비전을 갱신해 새 CLI 세션 없이 재개한다. 승인 전에는 계약에 열거된 읽기 전용 도구, 훅 유지보수와 관측 경로 close-out만 허용하며 그 밖의 일반 작업은 금지한다.
- 여기서 훅 리비전은 `/hooks`가 신뢰 대상으로 표시하는 실제 Codex provider 정의 `.codex/hooks.json`의 내용 해시다. 이 정의가 그대로인 정책·실행기·계약·테스트·가이드 변경은 재승인을 요구하지 않는다. 단, 과거 결합 리비전을 사용한 version 2 상태는 실제 provider 정의 단독 해시를 입증할 수 없으므로 version 3 전환 때 기존 승인을 보존하지 않고 한 번 fail-closed 확인한다. export된 훅 명령은 Git 초기화 전에도 동작하도록 `codex -C "<현재 루트>"`의 세션 작업 디렉터리를 기준으로 `.ai/`를 해석한다.
- Windows 앱의 `restart_required`는 Windows 앱 세션에만 적용한다. 같은 저장소의 CLI 세션은 자신의 `1`·`2` 확인 흐름을 계속 사용할 수 있으며 Desktop의 미완료 재시작 표식을 지우지 않는다.
- 승인 전 close-out은 관측한 literal 경로만 하나씩 명시적으로 stage하고, 비어 있지 않은 staged 경로 전체가 관측 범위일 때 메시지 형식의 새 로컬 커밋만 허용한다. 경로 패턴·와일드카드·광범위 stage와 amend는 허용하지 않는다.
- 승인 확인 뒤 `project/.aidd/ssot/`가 없으면 먼저 AIDD Kit만 복사된 상태임을 알리고, 고객이 프로젝트 ID·이름·신규 또는 기존 시스템 여부를 확인한 뒤 `project-bootstrap`으로 빈 제품 정본을 만든다. 기존 소스 위치는 기록만 하고 자동 이동·덮어쓰지 않는다. `bootstrap` 상태에서는 일반 진척을 추정하지 말고 제품 의도·범위·모듈·배포 맥락을 합의하도록 안내한다. 일반 상태에서는 먼저 `node .ai/tools/aidd.mjs current-actor`, `status --level executive`와 `integration-status`로 현재 로컬 작업자·프로젝트·Git 통합 상태를 짧게 브리핑한다. `current-actor`는 현재 Git 신원을 정본의 참여자·봇 매핑으로 해석한다. 팀 프로필에서 구현을 시작할 때는 `work-check --work WRK-ID`로 PM 배정·위임 배정 또는 오프라인 협의 기반 자율 배정과 현재 작업자 일치를 확인하며, 1인 프로필에는 이 배정 제한을 적용하지 않는다. 평가 대기 `MRG`, 대기 중인 `MRC`, 또는 이력이 갈라진 통합 상태가 있으면 일반 진척과 섞지 말고 먼저 알린다. `integration-status`는 네트워크·Git 이력을 바꾸지 않으며 자동 `fetch`·`pull`·`merge`·`push`를 하지 않는다. 새 프로젝트이거나 Git·훅 상태가 불명확할 때만 `project-init`으로 로컬 준비 상태를 확인한다. 이 명령은 파일 스테이징·최초 커밋·Git 신원 등록을 하지 않으며, 그 세 가지는 비밀정보와 신원 정보를 고객이 확인한 뒤에만 진행한다.
- 변경 유형, 영향받는 모듈, 관련 요구사항, 결정, 위험과 미결사항을 먼저 확인한다.
- 제품 의도·목적·성과 기준을 합의한 직후 `BEN-TRIAGE`로 벤치마킹 필요성을 고객과 판단한다. 필요성이 합의된 경우에만 조사 질문·후보·평가 기준·출처 품질·제외 범위를 먼저 정하고, 관측의 출처·한계·우리 환경과의 차이를 `research-note`에 남긴다. AI의 추천은 고객 결정이 아니며, 수용·보류·제외된 내용만 ADR·REQ·OI에 반영한다.
- 작업 시작 시 `project/.aidd/ssot/collaboration.json`의 활성 참여자와 현재 협업 프로필을 확인한다. 사람의 합류·이탈은 `collaboration-member`로 기록해 전환 이력과 생성 규칙을 함께 갱신하며, 승인을 얻기 위한 가상 참여자를 만들지 않는다. 두 번째 활성 참여자를 추가해 팀 프로필로 전환하기 전에는 활성 참여자 중 최소 1명에게 `PM` 역할을 지정한다.
- `identity-check`로 도달 가능한 Git 작성자·커미터를 확인한다. 미등록 신원은 기존 참여자의 별칭, 새 사람 또는 봇 중 무엇인지 고객에게 확인하고 `collaboration-identity`로 연결한다. 신원만 보고 사람 참여자를 자동 생성하지 않으며 봇과 동일인의 별칭을 활성 사람 수에 포함하지 않는다.
- 이탈한 참여자의 과거 커밋은 보존하되 이탈 시점 뒤의 새 커밋은 설명되지 않은 활동으로 보고 다시 참여시킬지, 다른 신원으로 분류할지 확인한다.
- Git 작성자·커미터를 실제 push 행위자로 표현하지 않는다. PR·승인·push 계정은 호스팅 제공자 API 또는 감사 로그 증거와 별도로 대조하고, 증거가 없으면 미검증으로 보고한다.
- 모듈 규모 작업은 `MLS` 마일스톤, `WRK` 작업, `IFC` 인터페이스와 `DPN` 의존성으로 분해한다. 모듈의 단일 상태만으로 완료를 추정하지 않는다.
- 프로젝트·변경의 불확실성, 규제·안전, 변경 비용과 운영 특성에 맞는 방법론 수행 경로를 선택하고 근거를 기록한다.
- 중대한 모호성이 있으면 해결책보다 목적과 성과를 먼저 인터뷰한다. 가정은 명시적으로 표시한다.
- 중요한 선택에서는 실행 가능한 대안의 장점, 비용, 위험, 가역성과 추천안을 제시한다. 고객의 결정은 별도로 기록한다.
- 게이트 정책의 존재를 게이트 통과로 간주하지 않는다. 변경별 `GTR` 실행 레코드에서 기준·증거·승인·예외를 확인하고, 승인되지 않은 필수 게이트가 있으면 완료나 릴리스 준비 완료를 선언하지 않는다.
- 통과 테스트와 완료 주장에는 `EVD` 증거를 연결한다. 증거에는 수행자, 실행 명령 또는 검토 방법, 시각, 커밋과 결과가 있어야 하며 자유문자 주장만으로 상태를 올리지 않는다.
- 제품, 아키텍처, 애플리케이션, 데이터, 데이터베이스, 보안, 인프라, DevOps, QA, 감리, 운영과 접근성 중 관련 역할 관점을 적용한다.
- 엄격성은 위험에 비례시킨다. 작고 되돌릴 수 있는 수정에 모듈 횡단 또는 비가역 변경과 같은 절차를 적용하지 않는다.
- 되돌릴 수 있는 작은 증분을 선호한다. 과거 결정을 지우지 말고 대체 관계와 롤백 경로를 기록한다.
- 신규 시스템·모듈 또는 배포 구조 변경은 기술을 고르기 전에 `DG-001`에서 온프레미스·클라우드, DBMS, 단일·다중 인스턴스, 확장 방식, 워크로드, SLO·RTO·RPO, 상태와 운영 제약을 배포 프로필로 확인한다. 미정 값은 담당자·기한·영향이 있는 미결사항으로 기록한다.
- 신규 시스템·모듈 또는 핵심 기술 변경은 품질 속성 기반 기술 스택 게이트를 거친다. 기능 규모 개발 전에는 적용 가능한 UI·공통 컴포넌트와 아키텍처·보안·테스트·관측성·배포 개발 기반의 준비도를 확인한다.
- 기능 규모 구현을 시작하기 전에 `node .ai/tools/aidd.mjs development-check --change CHG-ID`로 필수 게이트 승인과 변경별 요구사항·필수 작업 영역·팀 책임자 포괄성을 함께 확인한다. 각 CHG의 `required_work_coverage`는 설계·구현·시험·문서를 기본으로 하고 프로젝트 맥락에 따라 보안·데이터·마이그레이션·배포·운영·교육을 명시적으로 포함한다.
- 신규 기능·신규 모듈은 `delivery_path.kind: new_capability`로 분류하고 요구분석·설계와 화면 경로·API·배치·이벤트·외부 연동·마이그레이션 같은 `SURF` 구현 표면의 최신 문서를 먼저 갖춘 뒤 개발한다. 기존 기능·결함 변경은 문서가 있으면 같은 변경에서 현행화한다. 문서가 없을 때만 고객이 지금 작성하거나 나중에 작성하도록 선택할 수 있으며, 후자를 택하면 대상 표면·작성할 문서·완료 마일스톤 또는 릴리스가 있는 `documentation-reconciliation` WRK를 반드시 만든다.
- 레거시 고도화는 소스와 기존 분석·설계 문서를 자동으로 정답 취급하지 않는다. `aidd-legacy-reconciliation`으로 모든 화면 경로·API·배치·이벤트·외부 연동·마이그레이션을 모듈별로 조사하고, 기존 문서의 출처와 변환 결정을 보존한 계획을 만든 뒤 수행한다.
- 설계에서는 업무 불변 조건과 트랜잭션 경계, 프록시 기반 AOP 적용 경로, 스레드·비동기 컨텍스트, 재시도·멱등성, 다중 인스턴스 경쟁, 스케줄 중복, 자원 포화와 의존 장애 전파를 검토한다. 로컬 락·메모리·세션·캐시를 분산 보장으로 간주하지 않으며 적용 위험에는 경쟁·부하·장애 검증을 연결한다.
- 1인 프로필에서는 다른 사람의 승인을 필수로 요구하지 않는다. 대신 C2·C3 변경은 구현 흐름과 분리된 AI 검토 세션 또는 Codex·Claude 교차 검토 증거를 요구하고, 같은 흐름의 자기 검토를 독립 검토로 표시하지 않는다.
- 팀 프로필에서는 작성자 외 활성 사람 참여자 최소 1명의 승인을 요구한다. 인원이 다시 1명이 되면 과거 승인 이력을 보존한 채 1인 프로필로 돌아가며, 현재 프로필의 통제만 이후 변경에 적용한다.
- 1인 프로필에서는 `main`의 C0 직접 커밋을 허용하고 C1~C3에는 작업 브랜치를 권장한다. 팀 프로필에서는 새 변경을 기본 브랜치에 직접 커밋하지 않고 작업 브랜치에서 진행하며 `branch-check`와 Git pre-commit 훅으로 확인한다. 팀 전환 전에도 다음 변경용 브랜치를 먼저 만든다.

## 완료 조건

- 완료를 선언하기 전에 영향받는 정본, 구현, 테스트와 운영 지침을 함께 갱신한다.
- Codex와 Claude의 품질 동등성은 파일 동일성만으로 주장하지 않는다. 같은 `EVS` 픽스처와 루브릭의 플랫폼별 실행 결과를 기록하고 실제 실행 전에는 미실행으로 표시한다.
- CI 워크플로 파일과 로컬 보호 규칙의 존재를 원격 브랜치 보호 활성화로 간주하지 않는다. 원격 조회 증거를 별도로 기록한다.
- `node .ai/tools/aidd.mjs generate`, `node .ai/tools/aidd.mjs validate`와 관련 프로젝트 테스트를 실행한다.
- 연결된 검증 증거가 없는 요구사항은 완료가 아니다. 차단 미결사항이나 수용되지 않은 위험이 있으면 릴리스 준비 완료가 아니다.
- C2·C3 변경은 필수 게이트 실행이 승인되기 전에는 `done`, `verified`, `released`로 올리지 않는다. 예외는 승인자·만료일·보완 통제를 기록한다.
- Git 병합을 해결한 뒤에는 영향을 기록하고 추가 회귀 테스트 필요 여부를 결정한다. 필요한 재검토·재테스트는 담당자를 미리 배정하지 않은 `MRC`로 남기고, PM·관리자의 오프라인 조율 후 실제 수행자·시각·결과·증거만 완료 기록에 남긴다.
- AI가 커밋 메시지를 작성할 때는 `.ai/templates/git/commit-message.md`를 따른다. 변경 이유·영향 ID·검증 결과를 간략히 남긴다. AI가 변경 내용에 실질적으로 기여했으면 커밋 명령을 누가 실행했는지와 관계없이 마지막 trailer 묶음에 `AI-Assisted-By: Codex` 또는 `AI-Assisted-By: Claude`를 기여한 AI마다 한 줄씩 기록한다. 검토만 하고 변경을 만들지 않은 AI는 커밋 trailer가 아니라 연결된 EVD·작업 기록에 역할과 결과를 남긴다. 사람만 작성한 커밋에는 이 trailer를 넣지 않으며 Git 신원이나 `Co-Authored-By`를 추측하거나 자동 추가하지 않는다.
- 소스·정본을 변경한 뒤에는 `document-impact`로 요건 정의서→화면 요건→사용자 매뉴얼→운영 런북→테스트·증거의 현행화 후보를 확인한다. 훅 경고는 변경 사실을 감지하는 보조 통제일 뿐 의미 불일치를 판정하지 않는다. 코드와 정본이 다르면 어느 쪽도 자동 정답으로 정하지 않고 `aidd-document-consistency` 검토로 근거·영향 ID·처리를 기록한다.
- Git pre-commit은 staged `project/src/` 변경을 `SURF` source pattern에 매핑한다. 기존 문서가 있는 표면은 해당 정본 문서도 staged 상태여야 하고, 문서가 없는 표면은 즉시 작성 또는 유효한 후속 WRK가 있어야 한다. 내부 리팩터링의 문서 영향 없음도 근거와 결정자를 CHG에 기록해야 하며, 훅을 건너뛴 커밋은 CI·검토에서 동일 정책으로 다시 확인한다.
- 현재 상태·집중·다음 작업·주시 항목은 작은 정본 `project/.aidd/ssot/workboard.json`으로 관리한다. 작업·슬라이스의 공식 상태와 완료 근거는 각각 CHG·WRK·OI·ASM·RSK·EVD에 둔다. 일별 수행 맥락(무엇을·왜·어떻게 했고 다음에 무엇을 할지)은 Git 추적 경로 `project/work-log/YYYY-MM/YYYY-MM-DD/HUM-001.md`처럼 일자·참여자별로 짧게 누적한다. `record-work`는 현재 Git 이름·이메일을 `collaboration.json`의 검증된 활성 참여자 매핑으로 대조하고, 원시 Git 표시명 대신 AIDD 참여자 ID를 파일명에 쓴다. 미등록·비활성 신원은 기록하지 말고 매핑을 먼저 확인한다. 완료 항목을 작업 보드에 계속 쌓지 않는다.
- 작업의 역할 책임은 `delivery-plan.json`의 `owner`와 `assignee: HUM-ID`로 구분한다. 배정 단위는 관련 REQ와 CHG별 `required_work_coverage`를 함께 책임지는 작업 패키지(WRK)이며, 슬라이스는 그 안의 실행 단위다. 팀 프로필의 배정 방식은 `collaboration.json`에서 PM 배정, PM 위임 배정 또는 오프라인 협의 기반 자율 배정으로 정한다. PM(또는 1인 프로필의 소유자)은 `set-assignment-policy`로 전환하고, 지정된 권한자는 `assign-work --work WRK-ID --participant HUM-ID --reason "배정 사유"`로 책임을 기록한다. 오프라인 협의 필수는 자율 배정에만 적용하고, 자율 배정자는 자신에게만 배정할 수 있으며 점유·잠금·자동 pull 검사는 사용하지 않는다. 정책과 WRK 책임자 변경은 이전 값·변경자·시각·사유를 감사 이력으로 보존한다. 개발 중 현재 배정 범위 안에서 파생된 요구는 담당자가 현재 CHG의 REQ와 WRK의 requirements·coverage에 추가해 같은 패키지에서 처리한다. 다른 모듈·다른 WRK·승인 범위를 넘으면 PM 또는 위임자가 새 WRK 또는 범위 변경을 결정한다. 개발 배분 전 `workload-coverage --change CHG-ID`로 요구사항 연결·책임자·필수 작업 영역 누락을 해소한다. 팀원은 자기에게 배정된 작업만 `work-check`를 통과해 수행하며, 1인 프로필에는 assignee 제한을 적용하지 않는다.
- 새 훅·스킬·도구·플러그인은 해결할 실패, 기존 수단 부족, 트리거·입출력 계약, 중복 여부, 안전한 비활성화·롤백을 확인한 뒤에만 추가한다. `.ai/hooks/contract.json`을 공통 행동 정본으로 사용하고 provider별 지원 차이는 어댑터에서 처리한다. 새 훅은 `.ai/tools/` 아래의 `.mjs`로 만들고 `self-test`의 Node 단일 런타임 배선 검사를 통과해야 한다.
- 사용자·AI 대화 원문은 정본·증거·생성물로 삼지 않는다. 훅이 제공하는 UTF-8 원문만 역할과 제품 활성화 여부에 관계없이 Git 무시 경로 `chat-history/YYYY-MM/YYYY-MM-DD.md`에 날짜별 Markdown으로 로컬 기록하며, 기본 마스킹·항목·일별 크기 제한을 적용한다. `hook-trust-status`의 `TRUST_RECORD_FOUND`는 신뢰 기록 존재만 뜻하며 실제 실행·저장 성공을 보증하지 않으므로 다음 대화가 파일에 추가되는지도 확인한다. `AIDD_LOCAL_CONVERSATION_LOG=0`이면 기록하지 않는다.
