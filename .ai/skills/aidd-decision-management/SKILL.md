# AIDD 결정 요청 관리

1. 결정이 필요하다고 도출하면 질문보다 먼저 `project/.aidd/ssot/open-items.json`에 프로젝트 전체 공통 `OI`를 만든다. OI에는 결정할 질문, 상태, 차단 여부와 실제 `REQ`, `ADR`, `CHG`, `WRK`, `IFC`, `GTR`, `REL`, `TRM`, `RSK`, `EXC` 등의 링크를 둔다. 대상 전문 정본에도 필요한 상태·결정 조건·영향을 반영한다. DRQ만 만들고 OI를 생략하지 않는다.
2. 열린 OI들 중 지금 사용자에게 물을 항목을 고른 뒤, 질문을 보내기 전에 `project/.aidd/ssot/workboard.json`의 `decision_requests`에 `DRQ`를 저장한다. ID, 제목, 단계, 열린 OI와 실제 대상 `subject_refs`, 질문, 선택지, 권장안과 이유, 미응답 영향, 차단 여부, 우선순위, 상태와 묶음 내 순서가 필요하다.
3. 질문할 준비만 된 항목은 `draft`, 실제로 최종 답변에서 물은 항목은 `awaiting_decision`으로 둔다. 같은 답변의 질문은 동일한 ISO 8601 `asked_at`과 1부터 시작하는 `sequence`를 사용하며 묶음당 같은 결정을 위한 1~3건으로 제한한다. 여러 시점에 물은 미응답 묶음은 동시에 존재할 수 있다.
4. 사용자가 기존 질문에 답하지 않고 독립적인 다른 작업을 요청하면 기존 OI와 DRQ를 유지한 채 그 작업을 진행한다. 새 작업에서 별도의 사용자 결정이 실제로 필요하면 새 OI와 대상 링크를 먼저 기록하고 새 DRQ 묶음을 추가할 수 있다. 기존 질문을 해결·보류·철회하거나 덮어쓰지 않으며 매 응답마다 질문 전문을 반복하지 않는다.
5. 질문에는 답이 바꾸는 대상, 실행 가능한 선택지, 권장안과 적용 조건, 미응답 시 차단 또는 미뤄지는 범위를 간결하게 밝힌다. 사용자가 모를 수 있는 용어를 풀고 한 번에 모든 미결사항을 쏟아내지 않는다.
6. 상태 브리핑에서는 전체 열린 OI와 연결된 전문 정본, DRQ의 `draft`·`awaiting_decision`·`deferred`, 차단 DRQ와 다른 보류·재검증 상태를 구분한다. 답변 대기 건수와 묶음 수를 빠짐없이 보고하고, 차단 여부·명시적 `priority`·오래 기다린 순서로 권장 답변 묶음을 하나 고른다. 기록된 다음 작업과 권장 흐름을 제시한 뒤 이 묶음의 질문·선택지·권장안을 마지막에 보여준다. 상세 뷰에서는 나머지 미응답 DRQ도 조회할 수 있어야 한다.
7. 답변을 받으면 먼저 대상 정본에 결정을 반영하고 의미 있는 결정은 `HIS`와 필요한 `ADR`·`CHG`·`TCH`에 주체·이유·영향을 기록한다. 해당 OI에 해결 내용과 `closed` 상태를 기록한 뒤 DRQ를 `resolved`로 바꾸고 `resolution`, `decided_by`, `resolved_at`을 기록한다.
8. 사용자가 보류하면 `deferred`와 구체적인 `revisit_when`을, 질문이 무효가 되면 `withdrawn`과 `withdrawal_reason`을 기록한다. 차단 항목을 보류해도 차단 영향은 사라지지 않는다. 일부 묶음에만 답했다면 해당 DRQ만 종료하고 다른 미응답 묶음은 그대로 유지한다.
9. `chat-history/`는 과거 질문 복구의 참고 자료일 뿐 정본이 아니다. 확인한 과거 질문을 DRQ와 대상 정본으로 옮기기 전에는 현재 결정 상태로 간주하지 않는다. 훅이나 문자열 규칙으로 AI 응답을 분석해 정본을 자동 변경하지 않는다.
10. 변경 뒤 `generate`와 `validate`를 실행한다. 저장 실패나 검증 오류가 있으면 질문을 전송하거나 결정 반영 완료를 선언하지 않는다.
