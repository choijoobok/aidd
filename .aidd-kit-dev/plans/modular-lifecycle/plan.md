## 추가 증분 S07A (APR-005)

S07 이후 사용자 요청으로 [시스템·업무 분석 보완](supplements/S07A-business-discovery.md)을 추가했다. S02/S03 승인본을 덮어쓰거나 S04 저장 기반을 재작성하지 않는다. SYS/CAP/ACT/UC/BPR와 사용자 검토·요구 출처·흐름 포괄성, 영향 분석·파생 흐름도·브리핑을 S05~S07에 증분 통합한다. 완료 후 S08을 별도로 승인받는다. 실제 프로젝트 전환·커밋·릴리스는 이 증분 밖이다.

## 목표와 합의한 방향

후속 사용자 요청으로 일반 레거시 역분석의 [S08B 요구·단계안](supplements/reverse-engineering/README.md)을 추가했다. 소스/문서에서 초안을 작성하고 사용자 검토로 모듈별 정본을 채택하는 범위다. S08B-1(설계·초안 생성 핵심) → S08B-2(검토·재분석) → S08B-3(도입 준비/검증)을 제안하며 단계별 구현 승인을 받는다. 이전 AIDD 형식 전용 변환 제외는 유지하고 S09/S10을 완료로 간주하지 않는다.

1. 프로젝트 공통 목적·경계·기준선 아래 모듈이 각각 독립적인 개발 주기를 가진다.
2. 운영 중인 모듈과 신규·변경 개발 주기는 공존한다. 기존 모듈 개발 완료 후에도 새 모듈을 요구분석부터 추가한다.
3. 사용자와 합의한 해당 개발 주기의 전체 요구사항을 구체화·모순 검토·사용자 검토한 뒤 설계한다. 미완성 항목을 임의로 범위에서 빼지 않는다.
4. 요구사항에는 목적·범위·동작·규칙·예외·데이터·접점·품질·인수 기준·관계·미결사항의 적용 여부를 확인한다. 업무 특성이 필수 내용을, 위험이 검토 깊이를 결정한다.
5. 초안의 불완전함은 저장할 수 있다. 구조 검사와 단계 진입 조건을 구분하고, 모르는 내용을 추측으로 채워 통과시키지 않는다.
6. 요구분석에서 기능·메뉴/화면·데이터/속성·외부 접점 목록을 도출하고, 설계에서 상세화한다.
7. 기능 명세·화면 명세·검토 가능한 목업과 인수 테스트가 준비된 작업 단위로 개발한다. 비UI 기능에는 해당 계약을 적용한다.
8. 정의 상태, 검토 유효성, 구현·운영 상태를 구분한다. 승인 당시의 내용과 참조 기준선을 식별하며 과거 승인·테스트 결과를 보존한다.
9. 어느 단계에서든 변경을 발견하면 필요한 앞 단계로 복귀한다. 직접·간접 영향에 따라 수정·재검토·재검증 범위를 계산하고 영향 없는 작업은 유지한다.
10. 정본은 모듈 소유와 공통 소유를 구분하고 독립적으로 변경·검토할 레코드를 작은 파일로 관리한다. 계층 인덱스와 ID 조회를 사용한다.
11. 같은 연결을 여러 파일에서 수작업으로 중복 유지하지 않으며 역방향 조회는 계산한다. 공통 계약·데이터는 소유 정본 하나를 참조한다.
12. 브리핑·게이트·파생 문서는 같은 상태·유효성 판정 결과를 사용한다. 스킬은 수행 절차를, 도구는 기계 판정을 담당한다.
13. 모든 스킬·참조 문서·훅·도구·템플릿·가이드·배포 경계의 영향을 검토하고 유지·수정·교체를 구분한다.
14. 기존 게이트·CHG·WRK·결정·이력 구조를 활용하되 부족한 판정 기능은 보강한다. 장기 설계 결정은 KIT-ADR에 명시한다.
15. 기능 명세의 정본 승격은 현재 정책의 명시적 변경으로 다룬다. 최종 명칭·스키마·경로는 S03에서 결정한다.

## 범위와 경계

- 이번 개편은 Kit 관리 인력·일정·권한·계정 관리 시스템을 만드는 작업이 아니다.
- 루트에 제품 `project/`를 만들지 않는다. 실제 동작 검증은 명시적 fixture 또는 임시 프로젝트에서 수행한다.
- `.ai/spec/`와 `.ai/manifests/`는 portable 계약, `.aidd-kit-dev/`는 관리 계획·변경·결정·회귀 입력이다.
- 기존 프로젝트에 자동 업그레이드·patch 적용·merge·역동기화를 제공하지 않는다. 전환을 채택하는 프로젝트는 자체 변경으로 처리한다.
- Node.js 22 이상과 표준 라이브러리, UTF-8 BOM 없음·LF를 유지한다.
- 일반 CLI 내부 공통 기능과 런타임 훅은 구분한다. 런타임 훅의 provider·이벤트·책임별 격리를 유지하고 공통 dispatcher·공통 라이브러리·상호 호출을 도입하지 않는다.
- 사용자 단계 승인 없이 다음 단계를 시작하지 않는다. 커밋·push·PR·태그·실제 릴리스 준비와 배포는 이번 계획에 대한 동의만으로 실행하지 않는다.
- 큰 비호환 개편은 major 영향도로 추적하지만 버전 번호는 실제 릴리스 준비 요청까지 바꾸지 않는다.

## 단계별 계획

각 단계는 사용자 승인 후 시작한다. 아래 파일명·명령명 중 새로 제시한 것은 설계 후보이며 현재 구현된 능력을 뜻하지 않는다. 실제 확정 경로는 S03에서 관리한다.

### S01 — 계획·승인·재개 기록

- 작업: 전체 계획, 변경 레코드, 현재 상태, 재개 안내, 단계별 승인 절차를 관리 영역에 기록한다.
- 산출물: 이 계획 묶음, KIT-CHG-018, 관리 진입점과 미출시 안내.
- 완료 기준: 단계별 범위·완료 기준·검증이 있고 다음 세션이 현재 승인 범위를 식별할 수 있다.
- 검증: 관리 JSON·링크·단계 ID·인코딩·diff 검사, Kit quick check. portable 변경이 없으므로 제품 테스트·smoke는 불필요하다.

### S02 — 개편 요구사항과 인수 시나리오 정리

- 작업: 합의한 의도를 하나씩 검토 가능한 Kit 요구로 상세화하고 정상·부정·경계 사례, 적용 여부, 모듈 간 관계와 미결 선택을 기록한다. 기존 발견사항을 요구와 연결한다.
- 산출물: 관리 계획 아래 요구사항 목록·상세 기록·추적표·인수 시나리오. 사용자 검토 후 portable 명세의 입력으로 사용한다.
- 완료 기준: 전체 개편 범위가 설명되고 모순·누락·중대한 미결사항이 식별·정리된다. 사용자에게 읽을 요구사항 기준선과 설계 진입 조건을 제시할 수 있다.
- 검증: 목록 포괄성·관계·인수 가능성 검토. 미확정 내용을 승인으로 표시하지 않는다.
- 다음 승인: 요구사항 기준선 수용과 S03 설계 착수를 명시적으로 요청한다.

### S03 — 구조 설계와 전체 영향 목록

- 작업: 모듈·주기·작업 모델, 정본 소유권과 파일 분할, 인덱스, 상태·승인·게이트 유효성, 관계·영향 분석, CLI 경계, 전환·롤백을 설계한다. 모든 스킬·references·훅·도구·템플릿·가이드·생성물·export를 빠짐없이 목록화하고 유지·수정·교체를 판정한다.
- 산출물: KIT-ADR, 저장/조회/전환 계약, 상태 전이·게이트 계약, 명령·파일 영향표, 요구-설계-검증 연결.
- 완료 기준: S02의 모든 요구에 설계·검증 접근이 있고 기능 명세 정본 승격과 기존 계약 대체가 명시된다. 구현을 좌우하는 미결 선택이 해결된다.
- 검증: 정상·실패·재개 흐름을 설계 자료로 대조하고 기존 지원 동작의 보존 범위를 확인한다.
- 다음 승인: 구체적인 설계와 S04 구현 범위를 제시한다.

### S04 — 작은 정본 파일·인덱스·조회 기반

- 작업: 모듈·공통 정본 저장과 레코드/ID 조회, 계층 인덱스 생성·갱신·불일치 검출, 필요한 범위만 읽는 경로, 구조 검증과 쓰기 실패 복구를 구현한다. 대표 다중 모듈 fixture와 초기 생성/검사 연결을 마련한다.
- 산출물: 일반 CLI 내부 저장·조회 기반, 대표 fixture, 관련 portable 계약·문서·테스트.
- 완료 기준: ID를 보존한 분할·이동·조회가 가능하고 중복·누락·낡은 인덱스·부분 실패를 검출한다. 관련 없는 모듈 본문을 읽지 않는 조회 경로를 입증한다.
- 검증: 정상 조회, 존재하지 않는 ID, 중복 정본, 누락/낡은 인덱스, 새 파일 발견, 동시 갱신 충돌·복구의 필요한 대표 테스트와 smoke.

### S05 — 모듈별 주기·요구사항·승인·설계 진입

- 작업: 모듈 운영 기준선과 활성 CHG/WRK를 분리하고 요구사항의 상세화·사용자 검토·개정본 유효성, 주기 전체 범위의 설계 진입, OI/DRQ/HIS 연결을 구현한다. 관련 스킬·템플릿도 같은 단계에서 연결한다.
- 산출물: 요구사항 관리 흐름, 승인 대상 개정본, 요구사항 게이트, 최소 상태 출력과 의미 있는 테스트.
- 완료 기준: 신규 모듈을 기존 운영 상태와 함께 진행하고, 해당 주기의 요구 미완료·미검토·변경 후 미재검토 상태에서 설계 진입을 차단한다. 빈 모듈을 단순 상태 변경만으로 완료시킬 수 없다.
- 검증: 초안 저장, 검토 묶음과 항목 귀속, 승인 없는 통과 거부, 범위 변경, 오래된 승인, 기존 구현을 승인으로 오인하지 않는 사례와 smoke.

### S06 — 기능·화면·목업·개발과 선택적 복귀의 전체 흐름

- 작업: 기능 명세·SCR·목업·테스트·WRK를 연결하고 작업별 개발 진입을 계산한다. 직접/간접 의존, 선행 결과 유형, 현재 입력에 유효한 게이트, 변경에 따른 선택적 재개와 범위별 릴리스 차단을 구현한다.
- 산출물: A 운영 중 B 추가→요구분석→설계/목업→개발→공통 계약 변경→관련 항목 재검토를 수행하는 대표 흐름.
- 완료 기준: UI·비UI 기능의 개발 조건이 판정되고 과거 passed로 후속 실패를 우회하지 않는다. 무관한 모듈의 미결은 차단하지 않고 관련 공통 계약의 미결은 차단한다. 과거 승인·증거·운영 기준선은 보존한다.
- 검증: 선행 작업 blocked, 현재 계약/목업 변경, 공통 데이터 영향 전파, 영향 없음의 근거, 범위별 릴리스, 관련 테스트 재실행과 smoke.

### S07 — 브리핑·파생 문서·매뉴얼·제출물

- 작업: 동일한 상태·유효성 결과에서 프로젝트/모듈/주기/항목 브리핑을 생성한다. 모듈 진입 페이지와 항목별 상세 문서, 변경분과 재검토 이유, 매뉴얼·목업·실제 화면 구분, 제출 범위·버전 고정을 연결한다.
- 산출물: 새 상태 뷰, 상세 문서/사이트, 산출물 목록과 제출 프로필 연결.
- 완료 기준: 운영 기준선과 신규 주기 상태가 함께 보이고 브리핑·게이트·생성 문서의 상태가 일치한다. 모듈 문서는 탐색 진입점이며 상세 문서와 정본을 찾을 수 있다.
- 검증: 현재 정본으로 전체 재생성한 내용·파일 목록 비교, 링크·누락·오래된 문서, 독자별 포함 범위, 필요한 시각·오프라인 확인과 smoke.

### S08 — 전체 스킬·훅·provider 통합 점검

- 작업: S03 영향 목록의 모든 항목을 새 구조와 대조하고 빠진 본문·참조·경로·명령을 갱신한다. 생성물/인덱스 보호와 용어 변경 후 처리 등 필요한 훅만 수정한다. 하위 단계에서 변경한 스킬도 실제 대표 수행 흐름으로 확인한다.
- 산출물: 전체 영향표의 처리 결과, 일관된 스킬·가이드·템플릿, 필요한 독립 훅 변경과 provider 어댑터.
- 완료 기준: 옛 저장 경로와 상태 판정으로 돌아가는 절차가 없으며 훅 격리·대화 기록·배포 경계가 유지된다. 파일 동일성과 실제 AI 행동 검증 결과를 구분한다.
- 검증: sync-providers, quick check, hook self-test, 변경 훅 테스트, 대표 AI 수행 시나리오와 smoke. 실행하지 못한 실제 provider 행동은 미검증으로 표시한다.

### S09 — 새 프로젝트·export·v2 배포 기준 정리

- 작업: export/new-project를 새 기준선에 맞추고 폴더·ZIP을 확인한다. v2 기준 fixture·스켈레톤·CI를 현행화하고 이미 대체된 구형 공개 writer를 영향 검토 후 격리·정리한다. KIT-ADR-011에 따라 이전 AIDD 형식 전용 변환은 구현하지 않는다.
- 산출물: 새 프로젝트 시작 구조, 지원 형식·배포/복구 안내, export 허용 목록/fixture 현행화. migration-plan/migration-build와 버전별 변환·전환 롤백 도구는 제외한다.
- 완료 기준: 신규 프로젝트에서 대표 흐름이 재현되고 미완성 정의를 승인으로 만들지 않는다. 폴더/ZIP 경계와 기존 출력 보호를 유지한다. 일반 레거시 시스템 분석 기능을 구버전 변환과 혼동해 제거하지 않는다.
- 검증: 실제 임시 신규 프로젝트, 폴더/ZIP 경계·기존 출력 덮어쓰기 방지, 지원하지 않는 형식의 안전한 거부, 생성물 전체 비교와 smoke.

### S10 — 전체 인수 확인과 릴리스 준비도 보고

- 작업: S02 요구별 구현·검증·문서 연결을 확인하고 대표 전체 흐름과 남은 오류·한계를 정리한다. 미해결 필수 항목은 수정하거나 미완료로 남긴다.
- 산출물: 인수 결과, 최종 상태/인계 기록, 알려진 제한·호환성·롤백 안내와 읽기 전용 릴리스 계획.
- 완료 기준: 합의한 필수 요구가 실제 증거에 연결되고 단계 미완료·미검증이 숨겨지지 않는다. 충족했을 때만 KIT-CHG-018을 verified로 바꾼다.
- 검증: 변경 전체에 비례한 최종 회귀, provider/배포 경계, 생성 문서 전체 비교. 직전 결과를 유효하게 재사용하고 근거 없이 같은 검사를 반복하지 않는다.
- 종료: 결과를 보고한다. 실제 prepare-kit-release, 커밋·태그·배포는 별도 사용자 요청 전까지 수행하지 않는다.

## 단계 공통 수행 계약

- 각 단계 시작 전 `status.json`의 승인과 현재 파일을 확인한다. 계획 자체는 실행 승인이 아니다.
- 각 단계에서 영향을 준 명세·코드·테스트·가이드·스킬을 함께 맞춘다. S08이 있다는 이유로 깨진 연결을 방치하지 않는다.
- 새로운 질문·미결사항은 관리 상태의 `open_items`와 `decision_requests`에 먼저 기록하고 질문한다. 제품 OI/DRQ용 루트 `project/`를 만들지 않는다.
- 기존 파일 변경이 생기면 소유자를 확인하고 사용자 변경을 보존한다. stage 내부라도 범위가 달라지는 결정은 기록한다.
- 준비도 검사는 초안을 금지하거나 사용자 승인 자체를 기계적으로 만들어내지 않는다.
- 의미 있는 작업 경계와 단계 종료에 체크포인트를 남긴다. 단계 중단은 완료가 아니며 검증 미실행은 미실행으로 기록한다.
- 단계가 너무 크거나 새 사실로 순서 변경이 필요하면 계획을 수정하고 영향·이유를 설명한 뒤 변경된 다음 단계의 승인을 받는다.
- 한 단계 완료 뒤 상태·변경 파일·검증 결과·미완료와 다음 범위를 사용자에게 제시하고 다음 단계 승인 질문으로 종료한다.

## 선행 검토에서 확인한 사실

아래는 2026-09-22 대화에서 수행한 코드 검토와 임시 fixture 재현의 요약이다. 현재 Kit 요구의 정본은 사용자의 합의와 portable 명세이며 fixture 자체가 아니다. 임시 파일은 향후 실행에 필요한 영구 근거로 의존하지 않고 S02 이후 해당 회귀 입력을 정식 테스트로 만든다.

- 지원 확인: 기존 모듈 완료·프로젝트 운영 상태에서 새 모듈 추가, 기존 요구 파일 보존, 알 수 없는 모듈 의존성 거부, 하위 폴더의 requirements 배열 조각 로딩.
- 보완 확인: 빈 모듈 done 허용, blocked 선행 WRK에도 개발 허용, 후속 failed GTR이 있어도 과거 passed 인정, 무관한 모듈 OI/DRQ가 릴리스를 차단, 단일 모듈 조회에서 전체 정본 로딩.
- 코드 확인: 요구사항 검사는 인수 기준 존재와 일부 참조 중심이고 설계 준비는 상위 선언을 신뢰한다. 목업 생성은 제목 수준이며 실제 검토 가능한 화면으로 확장이 필요하다.
- 코드 확인: 요구·UI·표면 외 다수 레코드는 전역 파일에 모여 있고 모듈 생성 문서는 상세를 한 파일에 합친다. 영향 분석은 직접 ID 등장 위치를 찾는 수준이다.
- 기존 검사 결과: Kit quick check와 `.aidd-kit-dev/tests/aidd.test.mjs` 2건 및 reference fixture 생성물 전체 비교 통과. 이 통과가 위 누락 요건을 충족한다는 뜻은 아니다.
- 미검증: 실제 다중 AI 세션의 동시 편집, 대규모 프로젝트 성능, 계정 전환 후 실제 재개, 새 구조의 전체 실행 흐름.
