# AIDD 품질 보증

1. 검토 범위, 변경 등급, 보호 대상 자산·성과와 필수 증거를 정의한다. 위험이 요구하면 주장 작성과 검증의 독립성을 유지하되 사람 역할·승인 권한은 프로젝트 운영에서 정한다.
2. 의도와 인수 기준을 먼저 확인하고 추적성·설계, 구현·실행 증거 순서로 검토한다. 잘못된 요구사항을 코드 테스트 통과로 보완할 수 없다.
3. 모순, 고아 ID, 오래된 생성 문서, 검증되지 않은 승인 동작, 누락된 부정 사례, 안전하지 않은 기본값, 마이그레이션·롤백 누락과 운영 사각지대를 찾는다. 배포 프로필과 실제 토폴로지가 일치하는지, 로컬 락·메모리·세션·캐시를 다중 인스턴스 보장으로 오인하지 않았는지 검토한다.
4. 신원, 인가, 입출력, 비밀정보, 데이터 민감도, 의존 시스템 신뢰, 공급망, 로깅, 가용성과 복구에 오용·실패 분석을 적용한다. 트랜잭션·AOP 프록시 경계, 스레드 전환, 재시도·멱등성, 분산 경쟁, 스케줄 중복, 자원 포화와 장애 전파에는 적용 가능한 경쟁·부하·장애 검증 증거를 요구한다.
5. 병합 검토에서는 양쪽 부모와 해결 결과를 비교한다. 충돌 표식뿐 아니라 상호작용 영향을 찾는다.
6. 발견사항을 영향과 가능성으로 분류하고 정확한 산출물을 인용하며 위반한 요구사항·통제, 결과와 가장 작은 안전한 수정안을 설명한다.
7. 게이트를 암묵적으로 면제하지 않는다. 예외 범위, 결정 주체·이유, 만료, 보완 통제와 고객의 위험 수용을 기록한다.
8. 결정적 검증과 관련 테스트를 실행하되 구조적 성공과 의미적 품질 보증을 구분한다. `passed` 상태의 `EVD`가 실제 명령·방법, 수행 시각, 커밋과 결과를 갖는지 확인하고 게이트 정책 존재를 실행 승인으로 오인하지 않는다.
9. Codex·Claude 동등성 검토에서는 스킬 파일 동일성과 실제 행동 결과를 분리한다. `evaluation-prompt`의 같은 `EVS` 입력을 두 플랫폼에 제공하고 결과 증거를 만든 뒤 `record-evaluation`으로 루브릭 점수와 금지 행동을 각각 기록한다. CI·브랜치 보호는 로컬 구성과 원격 활성화 증거를 구분한다.
10. C2·C3에서 독립 검토가 요구되면 구현 흐름과 분리된 AI 세션, Codex·Claude 교차 검토 또는 프로젝트가 정한 별도 검토를 사용하고 동일 맥락의 자기 검토를 독립 검토라고 주장하지 않는다.
11. AIDD가 팀원 명부·역할·Git 신원·승인 권한을 판정하지 않았는지 확인한다. 보안 신원 검토는 제품 요건이나 사용자의 명시 요청에 포함된 경우에만 별도 범위와 증거로 수행한다.

검토 깊이를 선택할 때는 [references/review-matrix.md](references/review-matrix.md)를 읽는다. 문서 정합성, 추적성, 레드팀과 병합 후 재검증은 [references/consistency-and-merge.md](references/consistency-and-merge.md)를 함께 적용한다.
