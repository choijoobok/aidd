# 모듈별 생애주기 개편 — 재개 진입점

Kit 관리 전용 계획이다. 제품 정본이나 배포물이 아니며 루트에 `project/`를 만들지 않는다.

## 읽는 순서

APR-013으로 축소된 S09와 S10까지 완료했다. [S10 체크포인트](checkpoints/S10.md)와 [인수 결과](acceptance/S10-results.json)를 읽는다. 제출 당시 S02/S03과 S08B 요구안은 불변이며 현재 상태는 status.json이 정본이다. 실제 고객 도입/제품 실행·prepare-kit-release·태그·배포를 수행한 것은 아니다.

현재 범위는 [KIT-ADR-011](../../decisions/KIT-ADR-011.json)을 우선한다. 이전 AIDD 형식 전용 후보 변환은 취소했다. S09는 신규 프로젝트·export·v2 배포 기준 정리로 완료했으며 일반 레거시 소스·문서의 역분석은 제외하지 않았다.

1. 루트 `AGENTS.md`와 [관리자 가이드](../../guides/kit-maintainer-guide.md)를 확인한다.
2. [현재 상태와 단계 승인](status.json)을 읽는다. 다음 작업의 실행 권한은 이 파일과 사용자의 후속 명시적 답변으로 확인한다.
3. [전체 계획](plan.md)에서 현재 단계의 범위·산출물·완료 기준을 읽는다.
4. [변경 정본](../../changes/KIT-CHG-018.json)과 `status.json`의 `latest_checkpoint`를 확인한다.
5. Git 상태와 현재 파일을 대조한다. 미커밋 파일도 현재 작업 결과이며, 대화나 과거 검사만으로 완료를 추정하지 않는다.

## 승인과 단계 종료

- 사용자는 각 단계가 끝날 때 상태를 기록하고 다음 단계의 실행 승인을 요청하도록 지시했다.
- 전체 방향에 대한 동의는 모든 단계의 일괄 실행 승인이 아니다.
- `awaiting_approval`이면 기록된 다음 단계의 승인을 요청하고 기다린다. 사용자의 새로운 승인이 도착하면 그 의미·시각·대상 단계를 기록한 뒤 해당 단계만 시작한다.
- 사용자가 내용을 보완해 달라고 하면 해당 단계에서 보완한다. 명확한 후속 단계 승인 없이 다음 단계로 이동하지 않는다.
- 단계 종료 시 실제 변경·검증·미완료·되돌림 영향을 체크포인트에 적고 `status.json`을 갱신한 뒤 다음 단계의 범위와 승인 질문을 제시한다.
- 승인을 받으면 해당 단계를 `in_progress`로, 완료 기준 충족 후 `completed`로 바꾼다. 예정된 검사나 제안만으로 완료 처리하지 않는다.
- S02 요구사항 검토 후 S03을 요청할 때는 요구사항 기준선 수용과 설계 착수의 의미를 명시한다. 미결 이견이 있으면 S02를 보완한다.
- 새 범위나 이전 단계 재개가 필요하면 영향과 작업 경계를 기록하고 사용자에게 그 재개 단계의 승인을 요청한다. 승인된 현재 단계 내부의 통상적인 수정·검증은 계속 수행한다.

## 계정·세션 전환

- 단계는 여러 세션에 걸칠 수 있다. 한 세션에 완료하려고 범위나 검증을 줄이지 않는다.
- 전환 필요를 알았거나 사용자가 전환을 요청하면 안전한 작업 경계에서 `status.json`과 체크포인트를 갱신한다. 작성 중인 파일, 마지막 통과 검사, 미실행 검사, 실패, 정확한 다음 작업을 기록한다.
- 아직 끝나지 않은 단계는 `in_progress`로 유지하고 실행 상황을 `checkpointed`로 기록한다. 같은 단계의 승인은 명시적 철회가 없으면 계정 변경 후에도 유지된다.
- 새 계정의 AI는 현재 승인된 단계만 이어간다. 다음 단계 승인 대기라면 먼저 해당 승인을 받아야 한다.
- 저장소와 이 관리 파일이 같은 컴퓨터에 남아 있어야 한다. 다른 컴퓨터로 옮길 때는 미커밋 파일도 함께 전달해야 하며 Git 커밋만으로 현재 작업이 모두 보존됐다고 가정하지 않는다.
- 정확한 잔여 토큰을 알 수 있다고 전제하지 않는다. 사용자 전환 요청과 의미 있는 작업 경계마다 기록해 갑작스러운 전환 비용을 낮춘다.

다음 문장을 새 계정의 첫 요청으로 사용할 수 있다.

> `.aidd-kit-dev/plans/modular-lifecycle/README.md`와 연결된 현재 상태·최신 체크포인트를 읽고 이어서 진행해줘. 승인된 현재 단계만 수행하고, 다음 단계 승인 대기라면 먼저 나에게 승인을 요청해줘. 기존 미커밋 변경을 보존해줘.

## 기록 역할

- `plan.md`: 목표·범위·단계·완료 기준. 계획이 바뀌면 이유와 영향 단계를 기록한다.
- `status.json`: 현재 단계, 단계별 실행·승인 상태, 미결 결정, 정확한 다음 작업의 정본.
- [requirements/README.md](requirements/README.md): S02 요구사항 검토본 진입점. 개별 요구·인수 시나리오·정합성 검토·포괄성 표로 연결한다. 사용자 승인 상태와 검토본 해시는 `status.json`에서 확인한다.
- [design/README.md](design/README.md): S03 구조 설계·명령·전체 자산 영향·전환·검증 계획 진입점. 설계안의 수용과 구현 착수는 별도 승인 대상이다.
- `checkpoints/`: 단계 완료 또는 세션 인계에 필요한 짧은 실행 요약. 대화 원문이나 별도 EVD 체계를 만들지 않는다.
- `KIT-CHG-018`: 전체 변경과 릴리스 준비 상태. 일부 단계 완료를 전체 `verified`로 바꾸지 않는다.
- 체크포인트와 승인 기록은 요약만 남기며 사용자·AI 대화 원문을 복제하지 않는다.
- 이번 사용자 요청에 따른 중단은 단계별 승인 지시 때문이며, 추가 인증·신원 검증 정책을 만드는 것이 아니다.
# 현재 실행 결과 (APR-013)

S01~S10을 완료했다. 최신 결과는 [S10 체크포인트](checkpoints/S10.md), [인수 결과](acceptance/S10-results.json), [통합 지도](integration/README.md), [구현 맵](implementation-map.md), [현재 상태](status.json)을 읽는다.

사용자는 설계와 ADR-006~009를 수용하고 S04~S07을 중간 승인 없이 순차 완료하도록 승인했다. 단계별 상태·검증은 계속 기록한다. 아래의 개별 승인 원칙은 S08 이후에 적용한다. 제출된 design 문서는 불변 검토본이며 현재 상태는 status.json이 정본이다.

## 앞단 업무 분석 보완 (APR-005)

후속 사용자 요청으로 S07A 증분을 추가했다. [추가 요구·설계·검증 계획](supplements/S07A-business-discovery.md)과 status.json을 먼저 읽는다. S02/S03 승인 파일은 그대로이며 현재 단계·완료 여부는 status.json을 따른다. S08~S10의 실행 승인까지 확장하지 않는다.

S07A 당시 완료 결과는 [S07A 체크포인트](checkpoints/S07A.md)에 기록했다. 그 뒤 APR-006으로 S08을 진행했다.

## S08 통합 완료 (APR-006)

후속 APR-007의 접속·초기 화면·인증·인가 보완은 [S08A 명세](supplements/S08A-system-access.md)와 status.json을 따른다. 이 보완 승인은 S09 착수 승인이 아니다.

S08 당시 전체 회귀 92/92, provider 동기화·Kit check/smoke·훅 self-test를 통과했고 367개 기존 자산을 10개 조각으로 대응했다. 이후 KIT-ADR-011로 후보 변환을 제외하고 APR-013으로 축소 S09와 S10을 완료했다. 실제 외부 provider 행동 평가는 not_run이며 prepare-kit-release·태그·배포는 별도다.
